# openbmc-aware-harness 设计文档

## 背景与目标

当前仓库是一个 context infrastructure 的参考实现，核心价值在于展示入口文件、rules、docs、contexts 与自动化机制如何协同工作。现在要在 openbmc-aware-harness 下定制一套面向 OpenBMC 开发的独立上下文环境，用于后续单独发布到 GitHub，并服务团队共享使用。

这次设计要解决的问题不是“从零发明一套新结构”，而是“如何在尽量保留当前仓库上下文机制原味的前提下，把真正关键的骨架迁移到一个 OpenBMC 专用、自洽、可发布的子仓里”。

成功标准有三条。第一，第一版仓库已经具备独立使用的启动链路。第二，rules 这层关键知识资产得到高保真迁移，而不是被粗暴重写。第三，仓库边界足够克制，不把与 OpenBMC 无关的运营层和工具层一起拖进去。

## 范围

本次明确要做的内容如下。

- 设计 openbmc-aware-harness 的独立仓库定位与阶段划分。
- 确定第一版需要迁移的核心目录与文件边界。
- 明确 rules、docs、contexts、入口文件的职责分工。
- 明确仓库生成流、会话运行流、回退策略与验证门禁。
- 为后续实施计划提供稳定输入文档。

## 非范围

本次不做以下内容。

- 不直接实现目录复制、文件改写或仓库初始化。
- 不在第一版引入 periodic_jobs 里的 observer 或 reflector 机制。
- 不在第一版整体迁移 tools 目录下的增长分析、邮件、社交发布或 OpenCode 相关工具。
- 不在第一版预置 specs、plans 的历史内容。
- 不把平台、客户、项目差异抽象成可插拔 pack 体系。

## 方案比较

### 方案 A：1:1 镜像仓

- 核心思路：先把当前仓库结构和大部分内容完整复制到 openbmc-aware-harness，再逐项删减和改写。
- 优点：启动最快，和当前仓库的认知模型完全一致。
- 缺点：容易把个人知识资产、运营层目录和无关工具一并带过去，后续公开维护负担更重。

### 方案 B：双阶段产品化仓

- 核心思路：先定义最终要收敛成什么样，再用当前仓库做素材库，按保留、改写、删除三类迁移；第一版先做高保真种子态，第二阶段再做结构和入口文档收敛。
- 优点：既能借现有仓库加速，又能保证最终公开仓边界更干净；适合团队共享基座和后续独立发布。
- 缺点：需要显式区分“种子态”和“收敛态”，设计上比纯复制多一层控制。

### 方案 C：Core + Packs

- 核心思路：先做一个最小核心仓，再把平台、客户、项目差异做成后续叠加的扩展包。
- 优点：长期扩展性最好。
- 缺点：第一版复杂度明显偏高，会把当前任务从仓库定制拉成框架设计。

## 推荐方案

推荐采用方案 B。

选择原因有三点。第一，用户明确要求 openbmc-aware-harness 未来独立发布到 GitHub，最终仓库需要产品化边界，而不是长期维持一个私有镜像。第二，用户同时要求尽量保留当前 rules 体系的原始教义，这意味着第一版不能走“从零重写”的路线，必须保留高保真迁移阶段。第三，当前仓库里确实存在不应进入 OpenBMC 第一版的层，例如 periodic_jobs 和 tools，方案 B 最适合在保真迁移和边界收敛之间取得平衡。

主要 trade-off 也很明确：第一版会存在“入口文件先搬运，内容稍后修订”的过渡状态，因此需要严格区分启动链路的硬一致性和说明性文档的软一致性。

## 关键边界与组件职责

### 阶段划分

- 第一阶段是种子态迁移。目标是把当前 context mechanism 的关键骨架高保真搬到 openbmc-aware-harness，并让它能启动。
- 第二阶段是收敛态修订。目标是当内部边界稳定后，再回头修订入口文件和说明文档，使仓库内容与真实结构完全一致。

### 根入口层

- AGENTS、CLAUDE、Copilot instructions、README、setup guide 在第一阶段整体搬运进入 openbmc-aware-harness。
- 第一阶段它们承担的是“把当前机制带过去”的职责，不要求立刻完全贴合新仓结构。
- 第二阶段再统一修订这些入口文件，使其准确反映 openbmc-aware-harness 的实际边界。

### rules 层

- rules 是第一版最关键的知识资产，也是迁移主战场。
- 迁移策略不是整体重写，而是逐文件判定“原样保留、局部改写、暂不保留”。
- 设计原则是尽量保持当前仓库的原始教义，只修改与 OpenBMC 场景直接冲突或明显不适用的内容。
- WORKSPACE 后续需要改写成 OpenBMC 语境下的路由表，但这属于 rules 审视的一部分，不要求在种子态之前完成。

### docs 层

- 第一版 docs 只迁移 docs/SKILL_ECOSYSTEM.md 作为能力生态说明。
- specs 和 plans 目录可以保留结构，但不迁移历史内容。
- 后续设计文档、计划文档和样例资产从 openbmc-aware-harness 内部逐步新产出，不从当前仓库批量搬历史材料。

### contexts 层

- 第一版 contexts 的关键文件是 contexts/memory/OBSERVATIONS.md。
- 该文件用于保留共享观察与经验沉淀入口，是当前机制的重要组成部分。
- 其他 contexts 子目录不是第一版重点迁移对象，可以暂时不作为必备内容，或只保留空目录占位。

### 自动化与工具边界

- 第一版不迁移 periodic_jobs。当前其中只有 ai_heartbeat 相关 observer 和 reflector 机制，这属于长期知识运营层，不是 OpenBMC 团队共享基座的起步刚需。
- 第一版不整体迁移 tools。现有 tools 目录中的增长分析、邮件、社交发布和 OpenCode 相关脚本与 OpenBMC 固件开发无直接关系。
- semantic_search 具备通用能力，但在本设计中只作为后续可选扩展，不进入第一版核心骨架。
- 第一版的最小自动化入口仅依赖 AGENTS、CLAUDE 与 Copilot instructions，不额外引入 hooks、jobs 或工具链门槛。

### adhoc_jobs

- 第一版保留空的 adhoc_jobs 目录，用作后续一次性调试、验证或临时任务的落点。
- 该目录在种子态只占位，不预置内容。

## 数据流 / 控制流

### 仓库生成流

1. 从当前仓库抽取第一版种子态所需内容：入口文件、rules、docs/SKILL_ECOSYSTEM.md、contexts/memory/OBSERVATIONS.md，以及空的 adhoc_jobs。
2. 明确不进入第一版的目录与能力：periodic_jobs、tools 以及个人知识资产。
3. 在 openbmc-aware-harness 内完成第一轮 rules 审视，建立逐文件处置结果。
4. 在 rules 和目录边界稳定后，进入第二阶段，回头修订入口文件与说明文档。

### 会话运行流

1. 用户或 agent 通过 AGENTS、CLAUDE 或 Copilot instructions 进入新仓。
2. 入口文件触发核心 rules 的启动读取。
3. rules 中的 WORKSPACE 和 skills 引导后续搜索、定位和落盘行为。
4. docs/SKILL_ECOSYSTEM.md 提供能力生态说明，OBSERVATIONS.md 提供共享经验入口。
5. 后续在 openbmc-aware-harness 内新产生的样例、设计和经验沉淀，优先写入 docs 或 OBSERVATIONS，而不是散落在临时目录。

## 错误处理与回退

### 主要失败模式

- 搬运后的入口文件引用了新仓里尚不存在的目录或能力。
- rules 在迁移中被过度改写，导致原有 context mechanism 关键支点丢失。
- 第一步就把 periodic_jobs 或 tools 这类非核心层带入，增加噪音和维护负担。
- 说明文档比实际目录演进更快，出现内容和真实结构不一致。

### 对应处理策略

- 使用“硬一致性圈”和“软一致性圈”管理风险。硬一致性圈只包括启动链路和其强制读取的核心 rules 文件，必须始终自洽。软一致性圈包括 README、setup guide、生态说明和样例资产，允许在第二阶段逐步收敛。
- 对于暂时拿不准如何修改的 rules 文件，默认先保留原义并标记审视状态，不采用先删后补策略。
- 对于第一版不提供的能力，直接声明不支持，不创建半成品替代路径。
- 入口文件修订晚于目录收敛，避免先写一套“看起来合理”的说明，再被真实结构反向打脸。

## 测试策略

### 种子版门禁

- 必需文件与目录是否全部落位。
- 启动链路是否都能解析到真实文件。
- AGENTS 启动后要求读取的 rules 文件是否存在且顺序正确。
- docs/SKILL_ECOSYSTEM.md、contexts/memory/OBSERVATIONS.md 和空的 adhoc_jobs 是否已经在位。

### 收敛版门禁

- 入口文件内容是否与真实目录结构一致。
- skills index 是否不再指向已剔除能力。
- WORKSPACE 是否已经切换为 OpenBMC 语境。
- 至少有一条样例链路能跑通，从入口启动读取，到正确定位目录，再到生成一份文档产物。

### 验证方式

- 第一版以静态文件核对和一次真实 smoke run 为主，不引入复杂自动化测试。
- smoke run 的目标是验证仓库会不会带路，而不是验证所有未来功能都已就绪。

## 未决事项

- rules 目录下各文件的逐文件处置结果仍需在实施阶段系统化整理。
- WORKSPACE 需要落成 OpenBMC 语境下的具体路由表，但其详细内容将在实施阶段结合目标代码布局完成。
- semantic_search 是否在后续作为可选 Tier 2 扩展回归，需要在第一版稳定后再决定。
