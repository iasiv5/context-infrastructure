# cleanup Skill 设计文档

## 背景与目标

- 当前仓库已经有面向 GitHub Copilot 的 [handoff skill](../../m/plugins/iasi/skills/handoff/SKILL.md)，它负责把当前工作整理成可直接粘贴到下一 chat 的续接上下文。
- 用户希望把 Khazix 的 neat-freak 思路改造成更适合 GitHub Copilot 的版本，重命名为 `cleanup`，与 `handoff` 组成“会话交接 + 会话总结”的闭环。
- 这次设计的核心约束不是“最大化自动整理”，而是避免把中间态结论过早写进长期知识系统。
- 成功标准如下：
  - 中途跨 chat 续做时，默认只使用 `handoff`。
  - 正式工件在开发过程中可以正常更新，但这些更新不算 `cleanup`。
  - `cleanup` 只在用户明确表达长期沉淀意图时触发，不作为每轮会话的默认步骤。
  - `cleanup` 采用“硬触发 + 软提醒 + 反触发”的保守触发模型。
  - 当任务尚未稳定但用户显式要求 `cleanup` 时，先提示风险，再允许进入“强制 cleanup”。
  - 强制 `cleanup` 默认仅允许更新仓库内知识载体，不默认写入用户记忆。

## 范围

- 设计 `cleanup` skill 与 `handoff` 之间的职责边界、调用顺序和信息分层。
- 设计 `cleanup` 的触发模型，包括硬触发、软提醒、反触发和资格门。
- 设计 `cleanup` 的两种执行模式：正常 cleanup 与强制 cleanup。
- 设计 `cleanup` 在不同知识层上的默认写入边界，尤其是仓库内知识与用户记忆的区分。
- 设计 `cleanup` 与正式工件更新之间的关系，避免把实现过程中的文档更新误判为一次 cleanup。

## 非范围

- 不改写 [handoff skill](../../m/plugins/iasi/skills/handoff/SKILL.md) 的输出模板和主流程，只要求它继续坚持“工件优先、证据优先”的原则。
- 不要求 `cleanup` 成为每轮 chat 结束时都会自动触发的默认动作。
- 不把 `cleanup` 设计成普通总结、状态同步、review 或 changelog 生成工具。
- 不默认让强制 `cleanup` 更新用户级长期记忆；这类写入必须有额外明确授权。
- 不在本设计中直接进入 skill 实现、补丁编写或 prompt 落盘。

## 方案比较

### 方案 A：每轮交接前都先 cleanup，再 handoff

- 核心思路：每次切换到新 chat 前，先做一次知识沉淀，再生成 handoff。
- 优点：理论上长期知识同步最及时，handoff 依赖的稳定工件更多。
- 缺点：用户流程负担过重；中途结论尚未稳定时，最容易把临时判断错误沉淀到长期知识里。

### 方案 B：绝对 final-only cleanup，所有知识写入都推迟到最后

- 核心思路：中途只允许 handoff，直到任务完全结束才进行任何形式的沉淀。
- 优点：最能保护长期知识不被中间态污染；`handoff` 与 `cleanup` 的边界最硬。
- 缺点：把过多保真压力转移给 handoff 链；正式工件如果也被延迟更新，会导致开发过程不自然，且最终 cleanup 容易变成一次高负荷总清算。

### 方案 C：中途只用 handoff，正式工件照常更新，最终再执行 cleanup

- 核心思路：跨 chat 连续性只由 `handoff` 承担；开发过程中允许更新 spec、README、docs、ADR、runbook 等正式工件，但这些不算 `cleanup`；长期知识整理只在终态 `cleanup` 中完成。
- 优点：同时满足“避免中间态污染长期知识”和“保持开发过程自然”两个目标；把 `handoff`、正式工件更新、长期沉淀三者清晰分层。
- 缺点：需要更精确的触发与权限边界，否则用户仍可能混淆“改文档”和“做 cleanup”。

## 推荐方案

- 推荐采用方案 C。
- 选择原因：它最符合 GitHub Copilot 高频换 chat 的使用节奏，也最符合“长期知识写入门槛高于会话连续性写入门槛”的核心约束。
- 主要 trade-offs：
  - 放弃“每轮都沉淀”的即时性，换取长期知识系统的干净度和稳定性。
  - 允许正式工件在开发过程中持续更新，但要求 `cleanup` 只承担长期知识编辑，不承担普通文档编辑。
  - 为了保留用户控制权，任务未稳定时仍允许进入强制 `cleanup`，但要通过额外风险提示和更严格的写入边界来降低污染概率。

## 关键边界与组件职责

- `handoff`：
  - 负责会话连续性，而不是长期知识沉淀。
  - 输入是当前会话证据、必要的只读仓库事实和已存在的正式工件。
  - 输出是面向下一 chat 的 continuation context。
  - 保持只读，并继续坚持“稳定工件优先引用，弱推断不写死”的原则。

- 正式工件更新：
  - 负责完成当前任务本身，不属于 `cleanup`。
  - 典型对象包括 spec、plan、README、docs、ADR、runbook、integration guide 等正式项目产物。
  - 这类更新应该在开发过程中自然发生，不必等待终态 cleanup。

- 正常 `cleanup`：
  - 负责任务终态的长期知识沉淀与知识体系整洁化。
  - 重点不是追加流水账，而是对仓库内知识载体做去重、删旧、合并、纠偏和必要补充。
  - 默认只在用户明确表达长期沉淀意图，且任务已经达到稳定终点时执行。

- 强制 `cleanup`：
  - 负责处理“任务尚未稳定，但用户在看到风险后仍坚持要求 cleanup”的场景。
  - 和正常 cleanup 共用整体流程，但默认收紧写入权限，只允许更新仓库内知识载体。
  - 用户记忆默认不写，除非用户额外明确要求。

- 知识层分工：
  - 会话连续性层：由 `handoff` 承担，面向下一 chat。
  - 正式工件层：由开发流程承担，面向当前任务交付。
  - 长期知识层：由 `cleanup` 承担，面向未来会话、未来 agent 和长期维护。

## 触发模型

- 硬触发：仅当用户明确表达长期沉淀意图时，才自动进入 `cleanup`。
  - 典型表达包括：`/cleanup`、`cleanup`、`做最终沉淀`、`更新长期知识`、`整理长期记忆`、`收尾并同步文档和记忆`。

- 软提醒：当语义上出现“阶段完成、适合沉淀”的信号时，不自动触发 `cleanup`，只给出建议。
  - 典型表达包括：`这个阶段做完了`、`可以交给别人了`、`新人能直接上手了`、`准备收尾`。

- 反触发：明确表示“继续做”或“切到下一轮继续”的请求，必须优先路由到 `handoff`，而不是 `cleanup`。
  - 典型表达包括：`新开 chat 接着做`、`帮我交接到下一轮`、`总结下当前进展让我继续做`。

- 资格门：即使硬触发命中了 `cleanup`，也要先判断当前任务是否适合做长期沉淀。
  - 判断条件如下：
    - 核心目标已经完成，或已停在稳定可交接终点。
    - 不再依赖下一轮探索来决定主要结论。
    - 已有正式工件足以承载稳定事实。
    - 当前做长期沉淀不会把明显的中间态判断写死。

## 数据流 / 控制流

- 开发中的正常路径：
  1. 用户在当前 chat 中推进任务。
  2. 如果任务需要交付 spec、README、docs、ADR 等正式工件，直接在实现过程中更新这些工件。
  3. 若用户需要切到新 chat 继续同一任务，执行 `handoff`。

- 正常 cleanup 路径：
  1. 用户通过硬触发显式请求 `cleanup`。
  2. `cleanup` 先检查是否满足资格门。
  3. 若满足，则执行终态长期知识整理。
  4. 如清理后还要进入下一阶段，可再生成一次 `handoff`。

- 强制 cleanup 路径：
  1. 用户通过硬触发请求 `cleanup`，但资格门判断当前任务尚未稳定。
  2. `cleanup` 明确提示风险：当前任务仍处于中间态，直接沉淀可能污染长期知识。
  3. 在风险提示后，允许用户坚持继续执行。
  4. 若用户坚持，则进入强制 `cleanup`，默认仅更新仓库内知识载体；用户记忆保持不变，除非用户再次明确授权。

- 提醒但不执行路径：
  1. 若只命中软提醒语义，不自动进入 `cleanup`。
  2. Agent 仅提示“现在适合执行一次 cleanup”，由用户决定是否显式触发。

## 错误处理与回退

- 失败模式：用户其实想继续做当前任务，却误用了 `cleanup` 表达。
  - 处理策略：若请求命中反触发语义，优先路由到 `handoff`；不把它解释成 cleanup。

- 失败模式：用户显式请求 `cleanup`，但任务仍明显处于探索阶段。
  - 处理策略：先提示风险，再允许用户决定是否进入强制 cleanup。

- 失败模式：用户在强制 cleanup 中要求写入用户记忆。
  - 处理策略：默认不写；只有用户再次明确要求时才允许写入用户记忆层。

- 失败模式：实现者把“更新正式工件”误当成“已经做过 cleanup”。
  - 处理策略：在 skill 中明确区分“动作类别”和“意图类别”。同样是改文档，为完成当前任务而改不算 cleanup；为了整理长期知识系统而改才算 cleanup。

- 失败模式：`cleanup` 只根据最后一轮 chat 的文字结论沉淀知识，忽略正式工件和仓库事实。
  - 处理策略：明确要求 `cleanup` 以当前仓库事实和稳定工件为优先证据源，而不是只信最后一轮对话摘要。

## 测试策略

- 触发路由 walkthrough：
  - 用户请求“新开 chat 接着做”时，应路由到 `handoff`。
  - 用户请求“做最终沉淀”时，应进入 `cleanup` 资格门检查。
  - 用户只说“这个阶段做完了”时，应出现 cleanup 建议，但不自动执行。

- 边界 walkthrough：
  - 在开发过程中更新 README、spec 或 docs 时，不应被记录为一次 cleanup。
  - 任务终态执行 `cleanup` 时，应把重点放在长期知识整理，而不是重复正式工件已有内容。

- 强制模式 walkthrough：
  - 任务未稳定时显式请求 `cleanup`，应先看到风险提示。
  - 用户坚持执行后，应进入强制 cleanup。
  - 强制 cleanup 默认不写用户记忆，只允许更新仓库内知识载体。

- 证据优先 walkthrough：
  - `handoff` 应优先引用稳定工件。
  - `cleanup` 应优先读取正式工件、仓库记忆和仓库事实，而不是只依据最后一轮 chat 总结。
