# PLAN PRO MAX Agent 升级设计文档

## 背景与目标

- 当前 [m/plugins/iasi/agents/plan-pro-max.agent.md](m/plugins/iasi/agents/plan-pro-max.agent.md) 基本沿用原生 Plan agent 的思路，重点是研究上下文并生成实施计划。
- 这次升级的目标不是改写 VS Code 宿主绑定层，而是在保留原生工具、内存和 handoff 约束的前提下，吸收 brainstorming skill 的 design-first 方法论。
- 新版本需要先收敛设计、比较方案、显式审批，再进入实施计划，减少“计划很完整但前提不对”的问题。
- 成功标准如下：
  - 保留原生绑定强相关配置，包括工具声明、Explore 子 agent、session memory 路径和 handoff 机制。
  - 把正文协议升级为 design-first 再 planning 的双阶段流程。
  - 设计阶段严格执行一次只问一个问题，优先单选题。
  - 关键判断中加入更强的前提审查和最强反方观点。
  - 未获得用户明确批准前，不能输出实施计划。

## 范围

- 升级 [m/plugins/iasi/agents/plan-pro-max.agent.md](m/plugins/iasi/agents/plan-pro-max.agent.md) 的正文提示词结构与行为协议。
- 在不改变宿主绑定面的前提下，重写 agent 的角色定义、设计流程、审批门槛、回退规则和输出结构。
- 将 approved design 与 implementation plan 合并保存在 `/memories/session/plan.md`，继续沿用原生 Plan agent 的会话工件位置。
- 允许更新与定位相关的文案字段，例如 `name`、`description` 和 `argument-hint`，以体现 PRO MAX 的新职责。

## 非范围

- 不修改与 VS Code 原生绑定强相关的 frontmatter 设计，包括工具声明、Explore 能力、session memory 路径和 handoff 机制。
- 不让该 agent 直接进入实现、补丁生成或代码修改流程。
- 不为该 agent 增加仓库写文件能力，因此不要求它自行写 repo 内设计文档。
- 不把该 agent 改造成代码 review、纯问答或诊断型 agent；这些仍由其他 mode 负责。

## 方案比较

### 方案 A：轻量增强的 Plan Agent

- 核心思路：保留现有计划型定位，只补充少量澄清和方案比较能力，然后直接出计划。
- 优点：改动最小，和原生 Plan 最接近，prompt 体积也最短。
- 缺点：吸收 brainstorming 的力度有限，仍然容易在前提不清时过早写计划。

### 方案 B：Design-first 再 Planning 的双阶段 Agent

- 核心思路：同一个 agent 先执行 brainstorming 式的最小探索、单问题澄清、2-3 方案比较和分段设计确认；用户明确批准后，再进入实施计划。
- 优点：最大化吸收 brainstorming 的方法论，同时保留原生 Plan 的工具和工件形态。
- 缺点：交互节奏比默认 Plan 更严格，首次出计划会更慢一些。

### 方案 C：在计划前半段内嵌设计摘要

- 核心思路：不设独立审批门槛，只把设计比较压缩成计划前置章节，随后直接输出完整计划。
- 优点：表面上仍是单阶段体验，对用户阻力较小。
- 缺点：缺少显式批准门，设计约束容易被跳过，无法真正继承 brainstorming 的纪律。

## 推荐方案

- 推荐采用方案 B。
- 选择原因：它能在不动绑定层的前提下，把 brainstorming 最有价值的部分带进 Plan agent，包括设计先行、一次一个问题、方案比较、分段确认和显式批准门。
- 主要 trade-offs：
  - 牺牲部分“立即出计划”的速度，换取更高的前提正确率。
  - 保留 `/memories/session/plan.md` 作为唯一工件，意味着设计不会以 repo spec 的形式由 agent 自动落盘，但这符合当前不改工具绑定的约束。

## 关键边界与组件职责

- 宿主绑定层：保持原生约束不变，继续提供工具、memory、Explore 与 handoff 能力。
- 角色定义层：把 agent 从“直接产计划”升级为“设计优先的高级规划 agent”，但仍明确禁止实现。
- 适配判断层：先判断请求是否真的是规划问题；若是实现、review 或纯解释任务，则停止硬做计划。
- 探索层：仅做最小必要的上下文探索，优先读取最相关文件和边界，不做大范围漫游。
- 澄清层：严格遵守 one question at a time，优先单选题，其次多选，最后才是开放题。
- 方案比较层：在关键设计判断前，给出 2-3 个方案，并加入推荐方案与最强反方观点。
- 设计确认层：按架构边界、组件职责、控制流、错误处理、测试策略分段呈现设计并逐段确认。
- 批准门：只有用户明确批准设计后，agent 才能进入计划阶段。
- 计划生成层：把已批准设计与实施计划一起整理进 `/memories/session/plan.md`，并向用户展示可执行计划。
- 修订回退层：若用户修改设计假设，回退到设计阶段；若用户只改执行细节，则停留在计划阶段修订。

## 数据流 / 控制流

- 关键输入：用户的目标、约束、成功标准，以及代码库中与目标直接相关的最小上下文。
- 关键处理步骤：
  1. 验证请求是否适合进入 planning 流程。
  2. 进行最小必要探索，识别现有边界和现实约束。
  3. 通过单问题澄清补齐目标、约束和成功标准。
  4. 输出 2-3 个设计方案，给出推荐方案和最强反方观点。
  5. 分段呈现推荐设计，逐段确认。
  6. 在得到用户明确批准后，将“Approved Design”和“Implementation Plan”写入 `/memories/session/plan.md`。
  7. 在 refinement 中根据用户反馈决定回退到设计阶段还是只修计划。
- 关键输出：
  - 设计阶段输出：被分段确认的推荐设计。
  - 批准后输出：结构化实施计划，包含步骤、依赖、并行关系、验证、相关文件和范围边界。

## 错误处理与回退

- 失败模式：用户请求本质上不是规划任务。
  - 处理策略：直接指出不适配，不硬套 planning 流程。
- 失败模式：请求同时覆盖多个独立子系统。
  - 处理策略：先拆分子项目，只推进第一个子项目的设计与计划。
- 失败模式：目标、约束或成功标准仍不清晰。
  - 处理策略：继续执行单问题澄清，不提前产出计划。
- 失败模式：用户没有明确批准设计。
  - 处理策略：停留在设计阶段，不写实施计划。
- 失败模式：用户在批准后推翻关键设计假设。
  - 处理策略：回退到设计阶段，重新确认后再更新计划。
- 失败模式：前提薄弱但用户表达很强势。
  - 处理策略：保持更强硬的专业风格，明确指出前提问题，并给出最强反方观点与推荐方向。

## 测试策略

- 绑定兼容性检查：对比升级前后的 frontmatter，确认工具声明、Explore、session memory 路径与 handoff 机制保持不变。
- 正向场景 walkthrough：
  - 目标模糊时，agent 是否一次只问一个问题。
  - 设计存在多种实现方向时，agent 是否给出 2-3 方案、推荐方案和最强反方观点。
  - 设计未批准时，agent 是否停在设计阶段。
  - 设计批准后，agent 是否能稳定生成结构化实施计划。
- 负向场景 walkthrough：
  - 实现型请求是否被正确拒绝为非 planning 范畴。
  - review 型请求是否不会被错误地导入 planning 流程。
  - 多子系统请求是否会先拆分而不是强行规划全局。
- 文案质量检查：确认 prompt 中的 stop conditions、回退条件和输出结构没有互相冲突。
