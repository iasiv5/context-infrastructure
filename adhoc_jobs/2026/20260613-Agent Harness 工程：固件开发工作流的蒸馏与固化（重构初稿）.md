先做一个简短的背景衔接。去年 12 月 24 号，我们做过第一次内部技术分享，那次的主要目的，是让大家对 Coding Agent 这类工具建立一个基本认知，知道它们能做什么、为什么能帮到固件开发。

那次之后，专案没有停在科普。今年 3 月 22 号，我们选定了 Venice OTS 平台正式启动试点，要求 BIOS 和 BMC 的代码尽量由 AI 来生成，工程师聚焦 Review，在真实项目里摸索 AI 的能力边界。到今天 6 月 17 号，试点跑了将近三个月。所以今天这场，不是再讲一遍 AI Coding 是什么，而是汇报这三个月我们沉淀出了什么方法、产出了什么成果、看到了什么数据。试点到 8 月结束，年底我们会做一次全面回顾，评估要不要在未来的项目里全面推广。

在正式开始之前，我先把今天整场的核心判断抛出来，后面所有内容都是在论证这一句：模型会写代码，Harness 让它在固件流程里写对。

模型这几年的生成能力涨得很快，写一段代码不是难事。但固件开发的难点，从来不是写不出代码，而是写出来的代码能不能进我们的仓库、过我们的验证、达到我们的交付标准。今天要讲的 Harness，做的就是这件事。

## P3 聪明的新同事：AI 能力强，但不懂固件

### PPT 主文案

左侧：

```
AI 像一个很聪明的新同事：
能力很强，
但你不给他项目资料、不告诉他团队规矩，
他就只能自己瞎摸索。
```

右侧，Venice 试点真实翻车：

```
· i2c 拓扑：AI 把设备挂在错误节点
· PLDM 固件升级：未在用的流程被误判为正在使用
· 共同点：AI 看得到静态代码，
  分不清哪些是 runtime 真正在跑的路径
```

### Speaker Notes

先说一个大家都有感触的现象。AI Coding 工具现在很普及，大家或多或少都在用。补几行代码、写个函数，通常没什么问题。但要让 AI 产出真正能进生产、能上板的固件代码，尤其是 BIOS、BMC 这种跟硬件强相关的代码，稳定性就差很多。

问题出在哪？我们分析下来，不是 AI 不够聪明，而是它对真实的固件开发场景不够了解。它不知道我们的代码仓库长什么样，不知道团队的开发规范，更不知道工程师这些年踩过哪些坑。这些经验一直留在工程师脑子里，AI 读不到，自然就做不对。

打个简单的比方，AI 就像一个很聪明的新同事，能力很强，但你不给他项目资料、不告诉他团队做事的规矩，他就只能自己瞎摸索。

这不是比喻，是 Venice 试点里真实发生的事，我举两个翻车案例。有个同事让 AI 处理 i2c 拓扑，AI 把设备挂在了错误的节点上。还有同事在看一段 PLDM 固件升级的代码，里面有个目前没在用的流程，AI 误以为它正在被使用，差点带偏方向。这两个错误的共同点是，AI 看得到静态代码，但分不清哪些是 runtime 真正在跑的路径。能力强，但不懂我们的上下文。

## P4 固件开发为什么特别需要 Harness

### PPT 主文案

三张卡片：

```
① 仓库规则深
不懂 OneTree 的 recipe / layer / machine、Single Source Policy，
AI 就按社区习惯写，进不了我们的仓库。

② 验证链路长
模型说 done，不等于 build pass / boot pass / smoke pass。
每一段都要过。

③ 质量门禁硬
固件交付要证据充分、风险可控，有明确的 Definition of Done。
```

底部收束：

```
通用 Agent 看到的是互联网共识；
我们要补回来的是项目里的真实语境。
```

### Speaker Notes

为什么固件开发尤其需要解决这个问题？我归纳三个最关键的特性。

第一，仓库规则深。不懂 OneTree 的 recipe、layer、machine 覆盖关系，不懂 Single Source Policy，AI 就会按社区习惯写，写出来的代码进不了我们的仓库。

第二，验证链路长。模型说 done，不等于 build pass、boot pass、smoke pass。固件的验证是一整条链路，每一段都要过。

第三，质量门禁硬。固件交付不是代码写完就行，要证据充分、风险可控，有明确的 Definition of Done。

这三个特性决定了，通用 Agent 看到的是互联网上的通用共识，我们要补回来的，是项目里的真实语境。这就是 Harness 要干的事。

## P5 三条路径：把经验导入工具

### PPT 主文案

上半部分，三条路径：

```
① 自己训练专用模型（微调 / 后训练）—— 投入重、维护贵
② 从零搭建固件专用 AI 工具 —— 投入重、维护贵
③ 基于成熟工具，导入我们自己的经验 ★ IEC 选这条
```

右侧标注：

```
我们的优势不在 AI 算法，
在这么多年积累的固件开发经验。
```

下半部分，一句定义：

```
Coding Agent = 模型 + Harness

Inner Harness —— 厂商内置，我们难直接干预
Outer Harness —— 团队自建，BU6 的发力点
```

### Speaker Notes

那怎么给 AI 补上这些经验？业界通常有三条路径。

第一条，自己训练专用模型，通过微调或后训练，让 AI 从底层开始学固件开发。第二条，从零搭建一套固件专用的 AI 编程工具。这两条路都有价值，但对 IEC 来说，投入太重，维护成本也太高。

我们选的是第三条，基于成熟的 AI 编程工具，导入我们自己的经验。原因很简单，我们的优势不在 AI 算法，也不在 Agent 开发能力，而在这么多年积累下来的固件开发经验。把这份经验喂给成熟的工具，性价比最高。

这里我做一个定义上的区分，方便后面理解。一个 Coding Agent，等于模型加 Harness。模型是能力核心，厂商给的，包括系统提示词、工具调用这些，我们叫它 Inner Harness，这一层我们很难直接干预。外面还有一层，是项目规则、领域知识、工作流、验证门禁，这一层是团队自建的，我们叫它 Outer Harness。BU6 今天讲的所有东西，都在 Outer Harness 这一层。一句话，我们不卷模型，我们建 Outer Harness。

## P6 蒸馏与固化：从个人 prompt 到团队 harness

### PPT 主文案

左侧，两个动作：

```
蒸馏  把隐性经验抽取成 AI 可读的载体
固化  让经验进入默认流程，下次自动继承
```

右侧，固化四层阶梯：

```
L1  个人可复用    Prompt / 本地配置     经验随人走
L2  项目可继承    AGENTS.md / README    新人 clone 即得
L3  工作台化      CLI / 工作台 / build   Agent 能操作环境
L4  流程门禁化    CI / AI PR Review      流程强制执行
```

底部，实证：

```
两轮调查发现，团队使用模式自然分成三层，
正好对应 L1 到 L3。
```

### Speaker Notes

Outer Harness 怎么建？两个动作，一个是蒸馏，一个是固化，正好对应今天的标题。

蒸馏，是把散落在工程师脑子里的隐性经验抽取出来，变成 AI 能直接读的载体。固化，是让这些经验不只在对话里飘着，而是进入团队的默认流程，下一次任务自动继承。

固化有四个层级，从低到高是一条阶梯。L1，个人可复用，比如你自己常贴的一段 prompt，经验随人走，人走了就没了。L2，项目可继承，写进 AGENTS.md 和 README，新人 clone 仓库就能拿到。L3，工作台化，Agent 不只能读规则，还能操作环境、触发构建。L4，流程门禁化，CI、AI PR Review、发布 checklist，流程强制执行，不靠个人自觉。

这条阶梯不是我们拍脑袋想出来的，Venice 试点的调查数据正好印证了它。我们对团队做了两轮调查，发现大家的使用模式自然分成了三层：第一层还在调提示词，第二层开始用任务拆分、文档先行、OpenSpec 这些流程约束，第三层已经把经验沉淀成 Skill 和工作台。这三层，正好对应阶梯的 L1 到 L3。也就是说，团队正在自发地沿着这条阶梯往上走。

## P7 四个落地场景

### PPT 主文案

四象限或四行，每行标对应的阶梯层级：

```
① 读懂代码库      AGENTS.md + 模块文档          L2
② 规范驱动开发    规格先行、落盘                L2→L3
③ AI 代码审查     本地 Skill + 服务器 AI 初审    L4
④ 经验包同步      Plugin 一键分发               L3→L4
```

底部：

```
不是 PPT 概念，是 Venice 上正在跑的工程。
```

### Speaker Notes

沿着这条阶梯，我们已经落地了四个具体场景，覆盖了 L2 到 L4。

第一个，读懂代码库，对应 L2。我们在 BMC 仓库里写入了 AGENTS.md 全局规则，把不同模块的结构整理成 Markdown。AI 写代码之前，就知道哪些功能对应哪些文件，不用每次重新探索。

第二个，规范驱动开发，跨 L2 到 L3。我们引入了规格驱动开发的流程，让 AI 写代码之前，强制先确认需求、设计和实现要素，并且以文档方式落盘。这样 AI 输出的代码是有据可依的，不是凭空生成。

第三个，AI 代码审查，对应 L4。我们在本地引入了 Code Review 的 Skill，同时在 Git 服务器上，让每一笔代码提交先经过 AI 初审，再由资深工程师做人工终审。在 Venice 试点里，BIOS 和 BMC 的 PR 已经实现了 AI 初审全覆盖。

第四个，经验包同步，跨 L3 到 L4。我们把规则、指南、Skill、Spec 用 Plugin 的方式统一打包，工程师一键同步就拿到同一套 AI 能力。新员工第一天，就能和团队其他同事站在同一个起点。

这四个场景，不是 PPT 上的概念，是 Venice 上已经在跑的工程。

## P8 ob-harness：从读规则到能动手

### PPT 主文案

上半部分，ob 命令回路：

```
ob init  →  ob build  →  ob status  →  ob start-qemu  →  ob stop-qemu
初始化       出镜像       看状态         拉起 QEMU 验证     停实例
```

一句话：

```
一条 ob 命令，覆盖开发、编译、验证的完整回路。
```

配图位（两张，二选一或都放）：
- ob 命令回路示意图
- 左手 Agent 对话、右手 Terminal 的协作截图

下半部分，自证：

```
ob-harness 自身：11 份设计文档 + 12 份实施计划
靠 brainstorming / writing-plans / grill-with-docs 跑出
代码 100% AI-made

用 Harness 方法，做出了一个固件 Harness。
```

脚注：

```
ob-harness 是 BMC（OpenBMC）侧标杆，BIOS 可类比、待建。
```

### Speaker Notes

讲到这里，我想花一点时间，专门讲一个工程落点。前面四个场景里，读懂代码库和规范驱动，主要还是让 AI 读规则。但固件开发光读规则不够，还得能动手操作环境。所以我把这两个场景往前推了一步，做了一个 OpenBMC 的固件开发工作台，叫 ob-harness。

ob-harness 把 OpenBMC 开发里最繁琐的环境搭建，收进了一个 ob 命令。init 一条命令初始化环境，从克隆仓库到 externalsrc 注入全跑完；build 出镜像；status 看工作区状态。最新版本还加了 start-qemu 和 stop-qemu，一条命令拉起 BMC 仿真，Agent 编完代码能自己起 QEMU 验证，不用烧到主板。这一条 ob 命令，覆盖了开发、编译、验证的完整回路。

它最有意思的用法，是左手 Agent、右手 Terminal。Agent 的对话和 Terminal 的命令共享同一份上下文。你不用再把一长串编译错误手动贴给 Agent，Agent 也不用隔一层猜你的环境是什么状态。人和 Agent，真正在同一个现场协作。

这里我想强调一点。ob-harness 这个工具本身，就是用我们今天讲的这套方法论做出来的。它的 11 份设计文档、12 份实施计划，是靠 brainstorming、writing-plans、grill-with-docs 这几个 skill 跑出来的，代码 100% 是 AI 生成的。换句话说，我们用 AI Coding 加 Harness 的方法，做出了一个固件开发的 Harness。这是方法论不是空谈的一个直接证据。

也要诚实说一句，ob-harness 目前是 BMC 侧、也就是 OpenBMC 的标杆，BIOS 侧可以类比，但还没做。不过这个工作台的结构是通用的，BIOS 沿着同样的思路也能搭起来。

## P9 Venice OTS 三个月：数据说了什么

### PPT 主文案

核心数字：

```
AI 代码比例
第一轮（5/09）  平均 57.8% · 中位 50%
第二轮（5/25）  平均 69.7% · 中位 80%

24 人可配对：平均 +11.6 pp · 11 升 12 平 1 降

BMC 团队  平均 83.3%（接近常态化）
BIOS 团队 平均 53.6%（任务依赖型）
```

底部，诚实口径：

```
两轮问题设计不完全一致 · 工程师自评数据
当趋势参考，不当严格 KPI。
```

### Speaker Notes

方法论讲了这么多，到底有没有用？我们看 Venice 试点的数据。

我们对团队做了两轮调查，5 月 9 号一轮，5 月 25 号一轮。第一轮，AI 辅助生成代码的比例，平均 57.8%，中位数 50%。第二轮，平均升到 69.7%，中位数升到 80%。24 个能配对比较的同事里，平均提升了 11.6 个百分点，11 个人提升、12 个持平、1 个下降。

这里我要把口径说清楚。两轮调查的问题设计不完全一样，第一轮问的是近一个月，第二轮问的是近两周，而且都是工程师自评的数据，不是 commit 和 PR 的客观统计。所以这组数字，更适合看成趋势参考，不能当成严格的 KPI 考核。我特意把这个分寸讲清楚，因为在座有不少搞质量的同事，数据怎么来的、能说明什么、不能说明什么，比数字本身更重要。

分团队看，差异很明显。BMC 团队平均到了 83.3%，已经接近常态化。BIOS 团队平均 53.6%，呈任务依赖型，做 debug、review、工具开发时 AI 用得多，做核心功能代码时比例会下来。这个差异是真实的，也说明 AI 的收益跟任务类型强相关。

## P10 质量写进默认路径

### PPT 主文案

```
固件质量的终极保障，
不是某个人特别仔细，
而是系统默认不让错误通过。

· 每一笔 PR 过 AI 初审 —— 一道质量门禁
· 翻车案例沉淀进 AGENTS.md / review checklist
  —— 下次自动检查

质量不靠人记，靠写进默认路径。
```

### Speaker Notes

今天这场分享，也是我们质量文化系列活动的一部分，所以我想用质量的语言来谈 Harness 的意义。

固件质量的终极保障，不是某个人特别仔细，而是系统默认不让错误通过。Harness 做的就是这件事。Venice 试点的 AI 代码审查，每一笔 PR 都过 AI 初审，这就是一道质量门禁。前面讲的那些翻车案例，i2c 拓扑挂错、未用流程被误判，正在被我们一条条沉淀进 AGENTS.md 和 review checklist，变成 AI 下次自动检查的规则。

错一次，我们要做的不是只修这一次的输出，而是修一个让同类错误下次更难发生的机制。质量不靠人记，靠写进默认路径。

## P11 收束与引出案例

### PPT 主文案

接下来的主战场，

而是 BU6 自己的 AI Coding Harness。

下半部分，首尾呼应：

持续把经验教给 AI，
