## P3 《Harness Engineering：固件开发工作流的蒸馏与固化》封面
首先由我来介绍如何用 Harness Engineering 蒸馏和固化固件开发的常用工作流程。

## P4 
去年 12 月 24 号，我们做过第一次内部技术分享，让大家对 Coding Agent 建立了基本认知，知道它们能做什么，以及为什么可以辅助工程师进行固件开发。

今年 3 月 22 号，我们挑选 Venice OTS 平台启动了 AI Coding 试点。要求大家在试点项目中将 BIOS 和 BMC 的代码尽量交给 AI 来生成，工程师聚焦 Review，在真实项目里摸清 AI 的能力边界。到今天 6 月 17 号，试点跑了将近三个月。今天这场汇报的就是这三个月我们沉淀出了什么方法，产出了什么成果，看到了什么数据。等到年底试点结束，我们还会做一次全面回顾，评估 AI Coding 是否适合在后续项目中全面推广。

这里要先解释一个前提：大语言模型这几年的代码生成能力提升很快，生成完整的功能代码已经是基本操作。但固件开发的难点在于生成的代码是否符合团队的要求、是否会破坏项目中其它功能的相关依赖、是否达到BU6的交付标准。所以我们需要一套机制，来约束和引导 AI 的输出，让它生成符合我们要求的代码。

## P5 AI 能力强，缺的是固件上下文
AI Coding 工具大家或多或少都在用。补几行代码、写个函数，通常没什么问题。但要产出能进生产、能上板验证的固件代码，尤其是 BIOS、BMC 这类跟硬件强耦合的代码，AI 的输出质量就不稳定了。

试点中我们发现，问题的根源是 AI 缺少固件开发的上下文。仓库结构、团队的开发规范、工程师这些年积累的经验，这些信息留在工程师脑子里，或者散落在内部文档中，AI 读不到，自然做不对。

Venice OTS 平台上有两个典型案例。第一个，有同事让 AI 处理 i2c 拓扑，AI 对原理图的识别出了错，又缺少对应的硬件拓扑知识来纠偏，最终把设备挂到了错误的节点上。第二个，有同事在审查一段 PLDM 固件升级代码，里面有条当前未启用的路径，AI 因为没看全所有函数调用链，误判为正在使用，差点误导开发判断。

## P6 三条路径：把经验导入 AI
那怎么给 AI 补上固件开发的上下文和经验呢？业界通常有三条路径。
第一条，自己训练专用模型，通过微调或后训练让 AI 从底层学习固件知识。
第二条，从零搭建一套固件专用的 AI 编程工具，部分 IBV 厂商比如 AMI 也在往这个方向投入。
这两条路都有价值，但对 IEC 来说投入太重，维护成本也太高。
所以我们选择了第三条路线：基于成熟的 AI 编程工具，导入我们自己的工程经验。
这条路径的核心思路，和当前业界对 Coding Agent的主流共识一致：那就是 Coding Agent 等于模型加 Harness。Harness 原意是马具——就是套在马身上，用来控制和引导方向的装备。Harness Engineering 对应过来就是驾驭工程。
Coding Agent 内部的系统提示词、工具调用、任务编排这些能力，我们叫 Inner Harness，这一层由厂商控制，我们很难直接干预。外面一层是项目规则、领域知识、工作流和质量门禁，由团队自建，我们叫 Outer Harness。
BU6 目前定制的所有内容都在 Outer Harness 这一层，最终目的是用工程经验 约束 和 引导 模型的输出。

## P7 蒸馏与固化：从个人 prompt 到团队 harness
Outer Harness 怎么建？两个动作：蒸馏和固化。
蒸馏 —— 是把散落在工程师脑子里的隐性经验抽取出来，变成 AI 能直接读取的载体，通常是 Markdown 一类的结构化文档。
固化 —— 是让这些经验进入团队的默认流程，下一次 Agent 启动编程任务时自动继承。
固化分四个层级。
L1，个人可复用，比如工程师自己常用的一段 prompt，打包成斜杠命令或自定义智能体。
L2，项目可继承，把项目规范写进 AGENTS.md 和 instructions，跟源码一起维护，新人 clone 仓库就能拿到。
L3，平台化分发，通过插件系统打包整套 Skill 和 Workflow，Agent 安装后直接加载团队规则和领域知识。
L4，流程门禁化，CI、AI PR Review、Firmware Release Package Checklist 等自动化流程强制执行，质量门禁由流程保障而非个人自觉。
Venice 试点项目成员的使用模式也大体分成三层：第一层还在优化发给 AI 的提示词；第二层开始用任务拆分、Plan-First 以及 S.D.D 规范驱动等流程来约束 AI 的输出；第三层已经把经验总结成 Skill、Workflow 和规范文档，沉淀到插件或工作台中。

## P8 四个落地场景
我们在 Venice OTS 平台上已落地四组场景。
第一，教 AI 读懂代码库，对应 L2。我们在 BMC 仓库里写入了 AGENTS.md 全局规则，把各模块的结构整理成 Markdown。AI 在写代码之前就能定位功能和文件的对应关系，省掉每次重新探索仓库的过程。
第二，规范驱动开发，跨 L2 到 L3。我们引入了规格驱动开发流程，AI 写代码之前强制先确认需求、明确设计边界和功能细节，并以文档形式落盘。生成的代码有据可依，每一步都能追溯到对应的规格文档。
第三，AI PR 审查，对应 L4。我们在本地引入了 Code Review Skill，同时在 GitLab 服务器上让每一笔代码提交先经过 AI 初审，再由资深工程师做人工终审。Venice OTS 项目中，BIOS 和 BMC 部门的 PR 已经实现 100% AI 初审覆盖。
第四，经验包同步，跨 L3 到 L4。我们把规则、指南、Skill、MCP 用 Plugin 方式统一打包，工程师一键同步就拿到同一套 AI 能力基线。在这个基础上，我们还在搭建一体式开发平台，让固件开发上下文的加载过程进一步自动化。

## P9 ob-harness：一体式固件开发平台
前面四个场景中，读懂代码库和规范驱动主要是让 AI 读规则。固件开发还需要 AI 能操作环境：比如触发编译、运行仿真、采集验证结果等。基于这个需求，我们搭了一个 OpenBMC 的固件开发工作台，叫 ob-harness。
ob-harness 的设计围绕三个层面展开。
第一，上下文自动加载。Agent session 启动时自动读取项目规则，包括 AI 身份、用户身份、沟通风格、目录路由、技能索引，Agent 一启动就具备完整的仓库上下文。
第二，环境操作流程固化。把 OpenBMC 开发里最繁琐的环境搭建固化到 ob 脚本中：ob init 完成代码下载和子仓库 checkout，一键初始化；ob build 完成 machine 选择和镜像构建；ob start-qemu 和 ob stop-qemu 启动和关闭 QEMU instance，配置仿真验证环境。
第三，人机共享工作区。Agent 与 Terminal 共享同一份上下文，编译报错、环境状态这些信息 Agent 能直接读取。ob 脚本支持 CLI 模式和 Menu 交互模式：CLI 模式供 Agent 调用（省 Token），Menu 模式供工程师手动操作，新人也能直接上手 OpenBMC 的开发。
这里值得多说一句：ob-harness 本身也是用 AI Coding 做出来的。它的几十份设计文档和实施计划都是通过 /brainstorming、/writing-plans、/grill-with-docs 这三个 Skill 生成，代码 100% 由 AI 产出。我们用 AI Coding 加 Harness 的方法，做出了一个“持续进化”的固件开发 Harness 平台。
目前 ob-harness 覆盖的是 OpenBMC 开发场景。后续传统的 SPX BMC 以及 BIOS 的 Harness 工作台也可以沿同样的思路搭建。

## P10 Venice OTS 三个月：数据说了什么
我们来看 Venice 试点的数据。
上个月对团队做了两轮调查，5 月 9 号一轮，5 月 25 号一轮。
第一轮，AI 辅助生成代码的比例平均 57.8%，中位数 50%。
第二轮，平均升到 69.6%，中位数升到 80%。均值提升 11.8 个百分点，中位数提升 30 个百分点。中位数的跳升说明增长是由中间层整体抬升驱动的，不是少数高值拉动。
分团队看，BIOS 团队提升幅度 +12.7pp，略高于 BMC 的 +11.0pp，但绝对值仍差近 30pp：BIOS 54.8%，BMC 83.3%。BIOS 团队仍处于追赶阶段。
两轮调查之间变化最大的一项是上下文管理。第一轮调查时，这是最大的共性痛点，团队里没有人有成型的应对方案。第二轮时，团队已经验证了至少三种可操作的 workaround：会话及时handoff、文档先行、人机接力开发。这是两轮之间最关键的能力进展。
AI 领域知识不足仍然是当前最突出的瓶颈。BIOS 和 BMC 的闭源代码、SPX 旧框架、硬件依赖逻辑，这些场景下 AI 错误率偏高，短期内靠模型升级无法解决，需要持续通过 AGENTS.md 和其它 Harness 组件补齐领域知识。
另外，两轮调查中仍有部分成员稳定处于 30% 以下的低使用率区间。这部分同事的阻塞点需要逐人分析具体场景，针对性解决。

## P11 质量与 Harness
数据告诉我们进展和差距，但比数字更重要的是背后的机制。今天这场分享也是质量文化系列活动的一部分，所以最后，回到质量这个话题。
固件质量的终极保障是系统级的约束，用流程本身阻止错误产生，而不是依赖个人的工作细致程度。Venice 试点的 AI PR Review 机制就是一个例子，每一笔 PR 都经过 AI 初审，这本身就是一道客观门禁。前面提到的 i2c 拓扑挂错、未启用的代码路径被误判，这些案例正在被我们逐条沉淀进 AGENTS.md 和 Review Checklist，变成 AI 下次自动检查的规则。
每次出错，我们就去修订对应机制，让同类错误在下一次触发时被流程自动拦截。Harness 的核心就在这里：质量保障写进平台，由流程承载。

## P12 总结
过去半年，从第一次分享建立认知，到 Venice 试点验证方法，有一个判断越来越明确：BU6 接下来的核心投入方向是 AI Coding Harness。模型会继续变强，各家很快都会用上同等水平的 SOTA 模型，真正拉开差距的是谁能把固件开发经验更有效地蒸馏、固化、分发出去。我们的目标是持续把工程经验教给 AI，让它从一个生成能力强但缺少固件上下文的工具，逐步成长为团队可依赖的固件专家。
