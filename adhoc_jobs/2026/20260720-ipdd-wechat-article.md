# 别让 AI 跑太快：强模型时代，最贵的成本是回头改

## 越聪明的模型，越容易掉进这个陷阱

用 AI 写代码，最痛的翻车往往不是代码写错了，而是**它还没跟你对齐需求，就自顾自地把活干完了**。

你随口扔个大概方向，它 30 秒内就给你洋洋洒洒糊上几百行代码。眼看快跑完了你才发现：**一个原本一句话就能拍板的业务决定，被它擅自在底座里脑补成了另一套逻辑。** 

这就是强模型时代的陷阱：**由于 AI 的执行成本变得极度廉价，那些当初被糊弄过去的前置讨论，最终都会以满盘返工的形式惩罚你。** 报错的 Bug 好修，但走岔的架构、被抹平的模糊取舍，要拉回来重写简直是灾难。

在今天，**真正昂贵的不再是敲键盘的执行部分，而是回头改。**

为了从结构上根治这个问题，我强行把动手写代码这件事往后推了两步。这套我日常高频使用、**专门用来按住 AI 防脱缰**的开发流，我给它取了个代号：**I.P.D.D**（Implementation-Plan Driven Development，实施计划驱动开发）。

## I.P.D.D 四步法：把决策权夺回来

I.P.D.D 的核心并不是去束缚 AI 的能力，而是**强制把算力消耗在动手前的思考与排雷上**。实操起来就这四步：

### 1. 动手前，先拷问细节（`/grill-with-docs`）

这是 Matt 的原版 skill。不管大方向多清晰，我都会把它作为起手式，第一件事就是**让 Agent 把我输入的任务需求里的盲区和分支假设全部拷问出来**。

每次它只抛一个问题，并附带推荐方案；能拿到的代码底层依赖，它会自己先去查；但**只要遇到必须由人拍板的决策点，它一定会停下来等我点头，绝不越俎代庖**。

在这一通追问中，更有实战价值的一点是，它会顺手把项目里的黑话收敛进 `CONTEXT.md` 文档，把核心取舍记入具体的 ADR（架构决策记录）。**一次普通的对话，就这么沉淀成了下一次能直接复用的决策资产。**

### 2. 写代码前，先出明文计划（`/writing-plans`）

这是我基于 Superpowers 版本深度做了中文适配的专属 skill。

细节全盘敲定后，依然不允许马上写代码。我要求它**先交出一份明文的实施计划**。拿到计划后的交叉评审环节同样至关重要，我会把它发给另一个独立的顾问 Agent 去反复挑刺，把潜在的决策偏差和风险死角全部压平。

### 3. 水到渠成的无脑执行

拿到一份干干净净、排过雷的剧本后，剩下的才是交回给主力 Agent 去敲代码。

这一步反而成了全流程里最没有技术含量、确定性最高的一环。前置的脏活累活全干完了，此时新建一个 Agent 会话去执行这份自含上下文的实施计划，完全就是顺水推舟。

### 4. 闭环杀招：让独立视角交叉火力

代码落地后，再请刚才的顾问 Agent 回来过一遍产物，对齐并收敛双方意见。

很多人为了图省事会砍掉这一步。但这正是 I.P.D.D 能够确保交付质量的分水岭：**你最终拿到的，不再是某一个模型盲目自信的单方输出，而是经过独立视角交叉火力测试后的硬核成果。**

## 杀鸡不用牛刀：日常开发的克制

这套流程听着有点重，真放到日常里，我是这么切分的：

1. **小修小补，直接口喷开干。** 换个 Logo、修 UI 错位、填个显而易见的报空指针，千万别上什么流程，直接发指令让它搞定。
2. **重构或多分支需求，老老实实走完整 I.P.D.D。** 比如涉及跨文件的接口拆分，或者起底层的核心组件。

这里的判断硬指标只有一条：**这次改动里，有没有藏着一旦猜错就得推倒重来的决策盲盒？** 有的话，请把 I.P.D.D 请出来压阵。

## 写在最后：AI 踩油门，你握方向盘

I.P.D.D 并不是什么高高在上的重型框架，它是 对人机协作习惯的一次重新校准：**动手前先把坑问清楚、顺手把对话沉淀成文档，再把执行和评审彻底切分。**

现在的模型已经太会写代码了，它们最不缺的就是读秒交卷的速度。我们的任务，已经不是去教它怎么写某个具体的函数；而是**把干体力的油门放心地交给 Agent 去踩，但决定生死存亡的方向盘，必须牢牢握在自己手里**。




摘要：AI 写代码速度越快，需求没对齐带来的“大返工”代价就越惨痛。本文提出 I.P.D.D 四步法，通过强制剥离“决策、计划审阅与落代码”，将算力消耗在前置排雷上。把干体力的油门交给 AI，把决断的方向盘留给自己。
