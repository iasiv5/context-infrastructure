# 用一行 Prompt 驱动 AI 持续重构你的代码库

> 当 AI Coding Agent 已经能写代码，谁来决定"写什么"？ob-harness 仓库展示了一种有趣的答案。

## 问题：AI 会写代码，但谁来决定改什么？

我们已经有 Claude Code、GitHub Copilot 这些强大的 Coding Agent。但如果你打开一个有一定复杂度的代码库，对 AI 说"帮我优化一下"，得到的往往是表面修补——提取个函数、改个变量名、加点注释。

**真正的架构优化需要回答一个更难的问题：当前代码库中，哪个模块最值得深化？**

ob-harness（一个 OpenBMC 开发工具链）的作者用一组可组合的 Claude Code skills 给出了一套可复现的工作模式。

## 核心：一行 prompt 触发的架构审查

整个工作模式的入口是一个只有一行内容的 prompt 文件：

```
读取并遵循 .claude/skills/improve-codebase-architecture/SKILL.md
来深入分析仓库内容，只提供一个最重要、最紧急、最值得今天就开工的优化任务给我！
```

这就是 `pick-one-arch-task.prompt.md` 的全部内容。它不做任何技术工作——它只做**路由**：触发 `improve-codebase-architecture` skill，并施加一个约束——**只给出一个最优解，不要罗列**。

## 三个 Skill 组成的重构流水线

被触发后，三个 skill 像流水线一样接力：

### 第一步：improve-codebase-architecture — 找到"浅模块"

这个 skill 不是让 AI 凭直觉找问题。它有一套明确的设计词汇：**module、interface、depth、seam、locality**。用"删除测试"判断一个模块是不是浅的（删掉它会让复杂度集中还是只是搬走？）。最终产出一个 HTML 可视化报告，展示候选重构点的 before/after 结构图。

关键约束：**这一步只做分析和呈现，不写一行代码。**

### 第二步：grill-with-docs — 拷问设计

用户选定一个候选后，进入"grilling"（拷问）阶段。AI 变成一个极其严格的架构师，**逐个问题、一次一个**地追问：

- 这个接口的边界在哪？
- 旧调用怎么清零？保留还是删除？
- 缺失输入时怎么兼容？fallback 是谁拥有？
- 测试怎么锁住行为不变？

这个阶段同步产出两个文档工件：
- **ADR（Architecture Decision Record）**：记录关键设计决策和否决理由
- **CONTEXT.md 术语表**：为每个新概念定义精确定义，标明"Avoid"的别名

从仓库可以看到，14 条提交中 ADR-0006 和 ADR-0007 就是在这个阶段诞生的。

### 第三步：writing-plans — 拆成可执行计划

设计被拷问通过后，`writing-plans` skill 把它拆成 **2-5 分钟粒度**的任务清单，每个任务都有：
- 明确的文件路径
- 先写失败测试、再写实现的 TDD 循环
- 精确的验证命令和预期结果

仓库的 `docs/plans/` 目录里有 33 份这样的计划，最早从 5 月 31 日开始，平均每天产出 2-3 份。计划文件命名就是日期+特性，非常规整。

### 第四步：实现 + 回归锁

计划执行时，每个改动都配套写测试。不只是功能测试——还有**结构回归锁**和**调用次数锁**：

```bash
# 结构锁：确保旧调用清零，不被悄悄加回来
grep -c "resolve_qb_vars" lib/commands.sh  # 应为 0

# 调用次数锁：确保优化确实减少了调用
assert_eq "bitbake -e called exactly once" "$call_count" 1
```

作者甚至把这个模式本身沉淀成了一个新 skill（`bestpractice_09`），让"非功能性改动怎么写测试"成为可复用的能力。

## 实际循环：以 QEMU launch profile 为例

看 14 条提交中最完整的一个循环：

1. **6/30** `bdaed4e` — docs: 制定 QEMU launch profile 重构方案（ADR-0007 + 实施计划）
2. **7/1** `0cae680` — feat: 实现 QEMU launch profile 重构（4 层测试矩阵）
3. **7/1** `575abf8` — docs: observer 记录这次重构（ai-heartbeat 自动观测）
4. **7/1** `4e1998e` — docs: 同步 README、CONTEXT、exit_contract 等文档

把分散在 4 个函数（`resolve_qb_vars`、`detect_soc_type`、`derive_qemu_machine_name`、`find_ast2700_bootloaders`）里的 QEMU 启动决策收口到单一入口 `resolve_qemu_launch_profile`。这不是提取函数——这是把一个**浅模块**（interface 和 implementation 一样宽）深化为**深模块**（简单接口隐藏复杂实现）。

## 为什么这个模式值得注意

1. **路由 > 内容**：`pick-one-arch-task` 本身不含任何技术逻辑，它只是一个路由器。真正的智能在 skill 里，prompt 只负责"触发 + 约束"。

2. **文档是流程的副产物，不是额外负担**：ADR 在 grilling 过程中自然产生，实施计划在 writing-plans 中自动写好。你不需要"记得写文档"。

3. **回归锁 > 人工 review**：不依赖人记得检查"旧代码是否清零"，结构测试自动守护。

4. **可持续**：`ai-heartbeat` 定时让 AI 观察仓库变化，更新 observer 记录。这是一个**自维护**的系统，不是一次性的。

## 结语

这个工作模式的本质是：**把架构决策从 AI 的"直觉"搬到了一个有纪律的流程里**。AI 不再是"帮你写代码的工具"，而是一个被 skill 框架约束的架构伙伴——它能发现问题，但在动手前必须经过拷问、出文档、写计划三道关。

一行 prompt 背后，是一整套工程纪律。
