# ob-harness：新增固件基线测试框架

在固件开发中，功能“基线”是一台设备能否达到验收标准的硬性防线。它规定了设备的基础契约：例如必须按规范开放特定的 Redfish 服务，或者必须拦截未授权的越权访问。

以往这些底线要求往往躺在零散的 Excel 表格或需求文档里。开发者写完代码，需要手动启动环境、敲击请求命令来逐个点检。这种依赖手工的验证方式阻力极大，更导致底线功能在高速的产品迭代中经常发生静默退化。

为了让基线验收从“人治”走向“法治”，`ob-harness` 在最新版本落地了一套全新的自动化测试框架，核心交付入口是一条极简命令：`ob test-qemu`。

## 配置文件：将抽象基线确权翻译

新框架的第一步，是把文档里的人类语言翻译成机器随时可执行的诊断配置。开发者无需编写繁琐的测试脚手架代码，所有验证逻辑都被沉淀为清晰的 YAML 声明。

在这个系统下，每个机型的基线验证由两份核心文件定义：

其一是 **`ar_probes.yaml`（探针定义）**。它将产品需求条目直接映射为具体的动作请求和落位断言。例如，针对一个账户查询接口，直接配置下发特定的 Redfish 请求，随后由框架校验返回的状态码，或检查某个特定的 JSON 节点字段是否如期填充（如 `json_path_exists`）。

其二是 **`applicability.yaml`（适用性声明）**。并非所有特性都能在当前模拟器环境跑通（例如部分强依赖 Web 前端横幅的需求在后端模拟时无从验证）。借助该声明，开发者能为用例主动标记 `skip`（跳过）或 `xfail`（预期报错），并附上锁定原因。测试工具只考能考的题，截断无效报警干扰，让状态监控彻底脱离主观人脑记忆。

## 双轨设计：斩断用例跨界污染

建立自动化靶场后，随之而来的风险是环境混叠污染。

在工程实际里，内部仓库中通常拉取了大量的私有定制机型（Custom），而工作台上同样存在纯正的开源机型（Community）。如果测试工具不考量环境身份、盲目发考卷，极易出现用私有标准去测评开源版本库的荒谬场景，并由此衍生出无法自证代码清白的死循环。

为解决身份串台，`ob-harness` 实行了强硬的物理隔离双轨制设计：
系统将开源社区机型的标准集统一安置在 `tests/baseline/` 目录下，而所有的内部改造或试作靶场的基线配置文件则圈定在 `contexts/baseline/`。

验证一经发起，测试框架即嗅探本地 `manifest` 身份表，精准锁定当前开发台的归属：你是社区开源分支，就仅查验 `tests/` 体系下的**统一卷**；你是私有分支版本，则限定进入 `contexts/` 加载**定制用例**。这杜绝了测试标准的被动降级与横向污染。

## TDD 测试驱动工作流：用红绿灯引导代码编写

将基线沉淀为确定性的配置文件并配齐隔离机制后，重点就不再是“如何做验证”，而是“如何用测试来牵引开发”。固件迭代顺理成章地开启了测试驱动开发（TDD）的流线化闭环。运用 `ob-harness`，落地一个新特性的规范姿势已经转变为：

1. **确立靶标（主动亮红灯）**：动手写业务代码之前，先在 YAML 基线里定标新接口的请求行为及预期的 JSON 状态值。此时执行测试，框架必然因接口未实现而全线报错。
2. **对标编码（实现核心功能）**：带着清晰的靶子，开发者切入项目的 C++ 或 Python 源码中，实打实地完成协议应答与控制逻辑。开发者不再凭空猜想功能边界，而是纯粹为了让用例通过而编码。
3. **挂载与驱动验收**：运行 `ob start-qemu` 在纯净镜像内一键热起当前编译的固件产物，随后打出 `ob test-qemu <机型>`，将控制权毫无保留地交给自动化考官。
4. **判准离场（绿灯确认）**：探针发回的数据若完美匹配 YAML 契约，框架抛出 Exit 0 退出，标志功能真正收口。若依然失败，则循环修改逻辑，直到红灯转绿。

在这个闭环里，具备硬约束退出码纪律的框架成为了最好的工程脚手架。
只有对齐契约的才下出通行证（Exit 0）；指标发生偏差则判作未达基线无情回绝（Exit 1 直接截停）；而那些因为宿主网络抖动等原因产生的崩盘抛错同样被剥离识别成环境异变（Exit 3 中断）。

## 结语

把合规验收条款剥离出人类头脑、锁定成机器定轨执行文本，本就是工程建设的核心要领。`ob test-qemu` 把固件基线的准入防波堤架设到了开发台前。它依托 YAML 纯文本配置映射和无容忍的路径双向隔离机制，不仅为产品拦住了静默退化，更让研发团队从源头掌握了确定性交付的基石。
