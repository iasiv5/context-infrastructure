# AI 采纳的阶梯（Steps of AI Adoption）

> **作者**：Boris Cherny（Claude Code 作者，Anthropic）
> **原文发布**：2026-07-16，以 Claude Artifact 形式发布
> **原文链接**：<https://claude.ai/code/artifact/bfdfaef9-bc62-4dfe-ba9e-c58a26c9accf>

---

## 写在前面

Boris Cherny 是这样开场的：

> 我每天都会和其他公司的工程师聊天，听到的话都一样：**总有一个人用 Claude 把产出做到了 10 倍，而组织里的其他人还没跟上。**
>
> 观察各个团队采纳 AI 的过程，我反复看到同样的阶梯。我把它画了出来。

他的核心判断是：把一个人拉到 10 倍、和把整个组织拉到同一水平，差的**不是"再多买点 token"**，而是**每一级阶梯各自的瓶颈和护栏**。

> 走过这些阶梯，并没有唯一正确的路径……在每一级上，光有 token 是不够的——你需要找到并拆掉**下一组瓶颈**，同时建好**下一组护栏**。

需要留意一处细微差别：Cherny 在帖子里说"反复看到同样的 **4 步**"，但 artifact 本身给出的是 **0–4 共 5 个级别**——因为 **Step 0 是"还没真正开始"的起点**，真正意义上的"四步"是 1–4。

---

## 五级阶梯一览（速查表）

| 级别 | 名称 | 你的角色 | ~Agent 数 | 解锁的能力 | 主要瓶颈 |
| --- | --- | --- | --- | --- | --- |
| **0** | **受限 Gated** | — | **0** | — | 遗留安全体系、"每个 token 多少钱"的思维、没有审批通路 |
| **1** | **辅助 Assisted** | 你 + agent（结对） | **~1** | 占满一下午的活 → 会议间隙做完 | 你的注意力；必须逐条审改动 |
| **2** | **并行 Parallel** | 编排者 | **~10** | 整队几周的积压 → 一个下午 | 审多路产出；提示与转向 |
| **3** | **有监督的自治 Supervised autonomy** | "管理者的管理者" | **~100** | 后台维护持续在跑 | 对闭环的信任 + 决策吞吐；token 效率 |
| **4** | **AI 原生 AI-native** | 按意图转向的 VP | **1,000+** | 跨季度迁移 → 启动后盯进度 | 规模化地识别并自动化工作；按任务定护栏 |

Anthropic 自称整体处于 **Step 3**；Cherny 说他个人已到 **Step 4**。

---

## Step 0 — 受限（Gated）：0 个 agent

**它长什么样**
只有较旧、或较轻较快的模型获得批准。延迟因 AI 网关和自定义鉴权层层叠加。**没有 MCP 治理**。内部对 AI 工具的访问被审批流程卡住。Claude 生成的代码或 artifact **没有可上线的 IT 路径**——产出只能停留在本地。

**当前瓶颈**
遗留的安全与审批流程；组织优化的是"把每个 token 的成本关进笼子"，**而不是产出结果**；采购决策中**缺乏技术声音**。

**Cherny 列出的对应工具**
- Claude.ai 聊天（不是完整的 agent 栈）
- SSO/SCIM + 基于角色的访问
- 组织级预算上限
- 在**既有的审批 / IAM 体系**内部署
- 数据治理包（data governance package）

**如何迈向 Step 1**
靠的是**高管或采购方的对齐、逐级上抛阻碍、以及"如何安全地启动 Claude"的框架**——而不是买更多席位。

> 在这个阶段，组织里常常出现一种撕裂：某个工程师已经 10 倍产出，而组织架构图上仍写着"未批准"。这正是 Cherny 开场所描述的那种落差。

---

## Step 1 — 辅助（Assisted）：约 1 个 agent，监督式结对

**它长什么样**
**一个工程师，一个 agent**——一个快速的结对编程伙伴。你一次只跑一个会话，合并前**几乎逐条审查改动**。

**解锁的能力**
过去要占满**一个下午**的改动，现在能在**两个会议之间**做完。

**当前瓶颈**
**你的注意力**，以及**低信任**。没有一个你信得过的**自我验证闭环**，你就觉得自己必须读完每一行——于是工作停留在**同步**状态：你盯着 Claude 干活，而不是去开下一个任务。

**对应工具**
- Claude Code（桌面版、CLI、IDE）
- Claude Cowork、Claude Design
- 通过 Anthropic、Bedrock、Vertex 或 Microsoft Foundry 调用 API
- Claude Code 分析仪表盘 + Analytics API
- Compliance API（企业版）
- **Plan mode**（计划模式）——在改动前先审查意图
- 按席位设的支出上限、集中管理的模型 / effort（推理努力程度）设置与策略
- OpenTelemetry 导出至 SIEM / 可观测性平台

**护栏**
Plan mode、支出上限、集中化策略、OTel 接入既有技术栈。

**如何迈向 Step 2**
1. 同时跑**多个 agent**；
2. 搭建一个你信得过的**自我验证闭环**——测试、构建、lint、以及**在真实开发环境里的 e2e**；
3. 开启 **auto mode**，避免被权限弹窗阻塞；
4. **自动化代码审查**。

---

## Step 2 — 并行（Parallel）：约 10 个 agent，编排者

**它长什么样**
一个工程师在**独立的 worktree 或 git checkout** 上编排 **5–10 个 agent**，在会话之间来回切换。Claude 在你看到 diff 之前就**自查工作**——测试、构建、lint、安全扫描。**Auto mode 始终开启**。**自动化代码审查和安全审查默认开启**。Claude 写大部分代码；你审查的是**最终 diff，而不是每一次敲键**。维护类积压开始缩减。

**解锁的能力**
过去要**整个团队花几周**的积压，现在是**一个工程师一个下午**的编排活。

**当前瓶颈**
**审查产出**——六路 diff 而不是一路。以及**提示与转向**，当你同时应对多个会话时。

**对应工具**
- Auto mode
- Agent view（CLI + 桌面版）
- Claude Code Review、Claude Security Review
- Claude Code on Mobile、桌面版的云执行
- Claude Teams / Enterprise
- Claude Tag（单一任务）
- **Worktree 隔离**（CLI + 桌面版）
- Remote control——从手机监控 agent
- 团队用量分析
- 自动 lint、测试、类型检查
- Claude 驱动的 e2e 验证（Chrome 扩展、iOS / Android 模拟器 MCP）

**护栏**
仍需人工合并；**人工代码与 agent 代码同一道质量门槛**；在 `settings.json` 中**预批准安全的 bash 和 MCP 命令**。

**如何迈向 Step 3**
1. 给 Claude **上下文拉取**能力——代码、wiki、讨论；
2. 当 agent 触及**其他团队的代码**时，修复"能动性 + 代码审查速度"；
3. 把工作拆成 **loop（循环）和 routine（例行程序）**；
4. **让 Claude 启动 Claude**——subagent 扇出。

> 到了这一级，"审查的单位"悄然变化：从"打进去的 token"变成"harness 产出的整段结果"。

---

## Step 3 — 有监督的自治（Supervised autonomy）：约 100 个 agent，组织树

**它长什么样**
Claude 写**全部或几乎全部**代码。**"你读代码了吗？"**这句话，变成**"模型缺了什么上下文，下次怎么补？"**。**主动式维护**在后台运行——过去要等"哪个有空的人"来做的清理，现在**持续在跑**。

**解锁的能力**
过去要你**手动启动**的工作，现在**主动开始**。

**当前瓶颈**
**对闭环的信任**，以及**团队决策吞吐**。agent 树**深到无法逐一照看**——在闭环赢得广泛信任之前就扩大 agent 数量，就是陷阱。规模下的 **token 效率**需要 OTel 或 Analytics，以及"**先实验，PMF 之后再控成本**"的文化。

**Cherny 的检验标准**：
> "这件事，本来是不是某个工程师会做的？"

**对应工具**
- Subagent + worktree 隔离
- Routine、`/loop`、`/batch`、`/goal`
- 动态工作流（dynamic workflows）
- Claude Tag——监控某个频道或数据源，启动任务
- 自动代码 + 安全审查
- Agent 沙箱化
- **`CLAUDE.md` 与 Skills** 用于固化标准——Skills 注册表
- 从团队用量中调优 **auto mode 分类器**
- token 控制：模型选择、**advisor**、LSP、**lazy Skills**（按需加载）对比臃肿的根 `CLAUDE.md`

**护栏**
沙箱化、编码化的标准、成本监控、把主动式 routine **限定在边界清晰的流上**（bug 分诊、依赖升级、迁移）。

**如何迈向 Step 4**
对领域用例做**规模化自动化**——代码迁移、fuzzing、造功能、反馈修复。

---

## Step 4 — AI 原生（AI-native）：1000+ agent，按意图转向

**它长什么样**
闭环**彻底闭合**。**大多数 agent 由 Claude 而非人来启动**。成百上千个 agent 在跑；你**按意图转向**、**按例外监控**。

**解锁的能力**
一个**跨度长达一整个季度**的迁移，变成一个你**"启动后去盯进度"**的工作流。

**当前瓶颈**
在规模化下**识别并自动化工作**，同时**为每种工作类型执行正确的护栏**——而不是一刀切的策略。

**对应工具**
- **Claude Agent SDK**——以编程方式构建和调度 agent
- Claude Tag 在**大多数 Slack 频道**中活跃，自动回复
- 面向自动化的**成本控制**
- 面向自动化的**模型选择**（批量用便宜的模型，判断用前沿模型）

**护栏**
按工作流设成本上限、基于例外的监控、把**"自动化车道"**（迁移、分诊）和**"人工把关车道"**（生产部署、安全敏感的重构）分开。

> Cherny 写道 Anthropic 正在推向 Step 4；他**个人**于 2026-07-17 声称已到 Step 4。这更像**内部 dogfooding 信号**，不保证你的团队没有 Step 2–3 的 harness 投入就能照搬。

## 跨阶梯的进阶要点（Cherny 在 X 上的补充）

除表格外，Cherny 在 X / Threads 的帖子里点明了**通往更高层级的具体前置条件**：

| 主题 | Cherny 的建议 |
| --- | --- |
| **验证** | 给 Claude **端到端自查工作**的方法 |
| **权限** | 权限用 **auto mode**；**预批准安全命令** |
| **审查默认值** | **自动化代码审查 + 安全审查默认开启** |
| **多 agent UI** | CLI、桌面版、iOS 上的 **Agent view**——用来管理多个 agent |
| **后台红利** | 在**后台**修复和维护；团队聚焦于**建造** |
| **没有通用路径** | 每个团队都不同——**打破瓶颈**，而不是只买 token |

## 一句话总结

**Boris Cherny 的《AI 采纳的阶梯》**（2026-07-16）为 Claude Code 团队命名了**五个成熟度级别**：受限（0）→ 辅助（~1）→ 并行（~10）→ 有监督的自治（~100）→ AI 原生（1000+）。每一级都定义了**你的角色、解锁的能力、瓶颈、对应工具和护栏**。

推动你向前的**不是 token 本身**——而是**验证闭环、auto mode、自动化审查、worktree 隔离、routine 和成本监控**。Anthropic 整体处于 Step 3，Cherny 个人声称 Step 4。请**按行为而非按许可证档位**来给自己的团队定位。

---

### 常见的自我误判

| 误判 | 现实 |
| --- | --- |
| "我们买了企业版，所以是 Step 3" | Step 0–1 看的是**行为**，不是 SKU——一个被监督的会话仍只是 Step 1 |
| "我们开了 10 个 Cursor 标签页，所以是 Step 2" | Step 2 需要**自我验证、auto mode、自动化审查**——而不只是并行的聊天 |
| "我们开了 `/loop`，所以是 Step 4" | 没有**信任 + 成本控制**的主动式 loop，最多是 Step 3——常常只是"多烧 token 的 Step 2" |
| "有一个 10 倍工程师，说明组织很先进" | 这正是 Cherny 的开场观察——**没有护栏的个人英雄主义，会拉大**内部的不平等 |

到 Step 3 及以后，反复用 Cherny 那个问题问自己：**这件事，本来是不是某个工程师会做的？是，就自动化；不是，就保留人工把关。**
