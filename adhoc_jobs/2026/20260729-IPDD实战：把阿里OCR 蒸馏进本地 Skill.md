# IPDD实战：把阿里OCR 蒸馏进本地 Skill

阿里开源的 Open Code Review (OCR) 架构引发热议。作为 CLI 形态的专业级 Agent，它天然契合 CI/CD 流水线。本文演示另一套玩法：通过 IPDD (Intent & Plan Driven Development) 流程，将大厂的顶尖设计“蒸馏”进个人本地的 `/code-review` 工作流中。

## 第一步：对齐意图

动工前，用 `/grill-with-docs` 消除认知偏差，锁定两个原始目标：
1. 提取阿里 OCR 中有价值的设定，融入本地 `/code-review` skill。
2. 产物需满足硬性 `/writing-great-skills` 与 `/darwin-skill` 质量要求

> [截图：Agent 对齐意图与首个提问]

**首轮碰撞直击核心：重效率还是保底线？**
Agent 揪出代码审查领域的哲学冲突：OCR 追求更低的噪音影响，不在意百分百覆盖率；而本地审查则要发挥兜底作用，宁可错杀也必全量标注。事实摆齐后，我选择保留本地 Skill 的设计哲学。

确立主基调后，后续边界收敛变得水到渠成：

> [截图：Q2 引入证伪式自检]
**Q2：拒绝静默失败** —— 我选择引入自证伪（falsify）机制，一旦自否决直接触发降级，并留存审计日志查证。

> [截图：Q3 适用范围边界]
**Q3：面向未来解耦** —— 我选择不引入物理范围限定。考虑到模型能力的迭代速度，不提前设限以防形成负面约束。

> [截图：Q4 固件专项 Checklist]
**Q4：防御指令膨胀** —— 我选择采纳正反双面写法，但仅锁定高频误报区，以避免 instruction sprawl（指令膨胀）。

> [截图：Q5 大 Diff 风险清单]
**Q5：大 Diff 风险清单** —— 我选择不建独立 Phase 流程，直接将核查逻辑吸收进现有工作流。

> [截图：Q1~Q5 总结总览]
完成五轮对撞审查，第一步意图对齐结束。

## 第二步：生成计划

切入 `/writing-plans`，将意图拆解生成实施计划。

> [截图：Agent 输出的实施计划草案]

初稿落盘。激活顾问 Agent，开启红蓝对抗式的深度评审：

> [截图：R1 顾问 Agent 深度评审报告]
**R1**：顾问 Agent 对计划草案提供详尽的漏洞排查与评审意见。

> [截图：R2 执行 Agent 对峙与修正]
**R2**：执行 Agent 吸收合理点并给出修改方案，同时指出评审意见中的不合理要求。

> [截图：R3 第二轮深水区对抗]
**R3**：顾问 Agent 再次施压。

> [截图：R4 最终妥协一致]
**R4**：经过四次对抗博弈，三方终于对所有的边界案例达成一致。

## 第三步：执行与验收

## 后记

在深水区业务的 Agent 协作中，惊艳的能力涌现与彻底的失控翻车，往往只有一墙之隔。要想既享受模型的创造力，又不被拖入无尽的瞎聊泥潭，利用 IPDD 流程前置锁死【意图】与【执行计划】就是最强解法。它是斩断认知偏航、将大厂顶尖工程经验安全无损榨取进本地工作流的必备兵器。
