# 从 GitHub 到 IPDD：约束凭什么越做越薄？

狂堆 MCP、狂写花哨 Prompt、狂造细分 Skill，试图用层层魔法搞定 AI 开发，结果往往陷入维护地狱。和 Agent 协作时，人最大的诱惑总是再加一层约束。

本周 GitHub 官方博客发布《The harness is all you need (mostly)》https://github.blog/ai-and-ml/github-copilot/the-harness-is-all-you-need-mostly/。作者给出清晰建议：与其每天追新概念，不如把手上的 harness 用熟用透。其给出一套八步循环——做原型、进 plan 模式、Autopilot 跑实现、rubber duck 交叉验证、提交——全程零额外配置。

I.P.D.D（Intent & Plan Driven Development）在流程层的演进也导向同一终点：不再层层堆叠 SDD 文档，锁死前置意图和一份实施计划即可。

两张药方同月开出，共同指向反对过度封装。

## 工具层做减法，流程层也做减法

GitHub 的八步循环是工具层的减法：不用加新配置，harness 原生的 plan 模式、Autopilot 和 rubber duck review 足以胜任。

我的工作流演进史同样如此。早先信奉 Plan First，人工事无巨细地指挥；后来启用 SDD，改一个字段都要落地多份厚重文档，引发团队抵触；最后走到 IPDD，回归一份实施计划这个最小约束。

一边断舍离插件配置，一边断舍离繁文缛节。结论一致：伴随模型变强，约束应当升维。它不是越做越厚，而是越做越锋利。

## 共同内核：降方差

两者的底层逻辑完全一致：锁定变量，降低方差。

Agent 协作的发散和失控，往往源于过多约束把成本和方向悄悄拉偏。稳住质量的唯一解是强制收敛变化量。
**换模型、改上下文、临时跳步、省掉审批**，每一个动作都是纯粹的方差注入；每堵死一个，交付轨迹就收敛一分。

GitHub 建议同一个 session 别换模型以保住 prompt cache 折扣，这是降方差在降本层面的体现。
IPDD 则在流程上放大了这一机制：动手前，用 `/grill-with-docs` 拷问意图与边界，将领域术语锁进 `CONTEXT.md`；生成的计划交由顾问 Agent 执行红蓝对抗。
危险决策变量提前封死，后续的编码就变成了确定性的机械执行。

两边都将 grilling 作为 plan 阶段的起手式。博客推荐 grill-me skill；而 `/grill-with-docs` 不仅拷问边界，还能顺手将对抗细节沉淀为团队决策资产。

## 严肃工程的 mostly 余量

博客标题留了一个 mostly 作余量。应对大众场景，原生八步循环足够。

但在严肃工程深水区，原生循环存在不足。写 Web 表单，步骤乱了顶多 UI 错位；在 BMC 固件中跨文件拆分核心接口，Agent 如果脑补错边界，破坏面难以估量。

这部分 mostly 的余量，正是 IPDD 发力之处：剥离决策权与执行权，强制计划通过多轮对抗式审查，并在交付前由独立顾问 Agent 执行多维度的成品查验。

## 写在最后

无论是工具还是流程，方向都是别再盲目增加 Agent 的约束层。把该锁的变量锁死，该放的油门放掉。
如今的模型不缺交卷速度，缺的是动手前清醒的判断和边界底线。

方向握在手里，油门交给它。
