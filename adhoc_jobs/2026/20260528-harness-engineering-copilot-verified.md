# 同一个模型，为什么团队效率能差十倍？

> F1 车队之间，引擎功率差距通常不大。真正拉开名次的，是空气动力学、轮胎策略和进站节奏。AI 编程也是同一个道理。

团队引入 AI 编程工具时，最先比较的通常是模型。Claude、GPT、Gemini 谁更强，benchmark 谁高 2 个点，往往会直接影响采购和推广。这个动作不奇怪，但它回答的只是“引擎选哪台”，回答不了“整台车怎么搭”。

Anthropic 提出 Harness Engineering，讨论的正是后一个问题。规范怎么写，流程怎么接，工具怎么进来，团队经验怎么沉淀，决定的已经不是单次问答质量，而是代理能不能稳定进入开发流程。AI 从聊天框变成工程系统，靠的是 harness。

## 第一部分：Anthropic 说的 Harness，到底在说什么

Anthropic 把 Claude Code 外面的关键扩展层分成七个组件：CLAUDE.md、Hooks、Skills、Plugins、MCP Servers、LSP、Subagents。这个排列对应团队落地 AI 的常见顺序：先把共识写清楚，再把流程接上，再把专业能力和外部系统拉进来。

**CLAUDE.md 是入口。** 它写的是项目怎么组织，什么能改，什么不能碰，测试怎么跑，常见坑有哪些。没有这份文档，模型只能靠通用先验猜代码库；有了它，代理才会带着项目语境做判断。写进这份文档的内容，就是代理默认携带的上下文。

**Hooks 把流程约束变成自动动作。** 拦截危险操作只是其中一部分，比如阻止误删、限制高风险命令、强制确认敏感写入。更关键的，是把原来靠工程师记忆维持的动作固化下来：编辑后自动跑格式化和最小单测，会话开始时注入当前分支和构建目标，会话结束时检查有没有留下明显烂尾。流程一旦程序化，边界和回路就不再靠记忆维持。

**Skills 处理上下文预算。** 安全审查、发布流程、日志分析、文档更新、板级 bring-up，各有各的知识和步骤。把这些全部塞进全局指令，只会让上下文越来越臃肿。Skill 的做法是按需加载：遇到相关任务，再把对应的指令、脚本、样例和资源带进来。平时不占空间，需要时能往下钻。

**Plugins 解决分发。** 资深工程师本机上积累出一套 Skills、Hooks、MCP 配置，不等于团队已经拥有它。只有当这些组件能被发现、安装、更新、共享，个人经验才会变成组织资产。Plugin 把这些零散组件变成一个可分发的包，让新成员上手时直接站在现成流程上。

**MCP Servers 处理的是工作边界。** 内部文档、缺陷系统、构建日志、硬件测试平台、版本数据库，大量关键信息都在仓库外。没有 MCP，模型只能等人复制粘贴；有了 MCP，它才能主动取数、主动调用工具。企业环境里，AI 能不能从代码助手走到工作助手，往往就看这一步。

**LSP 和 Subagents 属于效率层。** LSP 给模型的是 IDE 语义能力，不再只是字符串匹配，而是定义跳转、引用追踪、符号理解。Subagents 给的是上下文隔离，把大范围探索和精确执行拆开。前者负责读很多文件、摸清问题，后者负责带着结论落修改。这样主会话不会被探索阶段的噪音塞满。

**七层放在一起，核心问题只有一个：怎么把规范、自动化、工具和团队经验一层层接到模型上。** 模型会继续变强；没有 harness，代理的工作边界还是停在聊天框附近。

## 第二部分：换到 VS Code + GitHub Copilot Chat，怎么落地

**VS Code + GitHub Copilot Chat 已经能把这七层大致搭起来。** 规范层有 `AGENTS.md`、`CLAUDE.md`、`.github/copilot-instructions.md` 和按路径生效的 `.instructions.md`；Hooks 有 `.github/hooks/*.json` 和完整的生命周期事件；Skills 已经是标准 `SKILL.md` 体系；Plugins 和 marketplace 也已经进入 VS Code 的 Agent plugins 机制；MCP、LSP、Subagents 同样都在。短板已经不在入口有没有，而在团队是否把这些入口接进日常流程。

**只把 Copilot 当成补全和聊天，就会漏掉它现在已经具备的定制层。** 规范、自动化、技能、分发，这几层都已有接口，只是成熟度还不完全一致。团队之间的差距，更多会出现在这些能力怎么组织、怎么组合、怎么沉淀上。

**固件团队可以按一条很短的路线落地。** 先把 `AGENTS.md` 和 instructions 写清楚：目录规则、工具链版本、构建入口、生成物边界。然后上 Hooks，先做三件基础动作：拦高风险命令、编辑后自动格式化、编辑后自动跑最窄的一层校验。接着把传感器驱动调试、串口日志分析、编译报错归因、发布前检查这些高频动作沉淀成 Skills。等这些跑顺了，再接 MCP，把缺陷系统、日志平台和文档搜索拉进来。团队规模再大一点，再把现有 Skills、Hooks、MCP 配置打成 Plugin 分发。

**模型越来越像公用基础设施。** 团队之间的差距，会更多地出现在 harness 上：规范有没有写进仓库，流程有没有自动化，经验有没有做成可复用组件。谁先把这些接好，谁就更容易把同一个模型用出十倍效率。

---

摘要：

为什么同样用 Claude Code 或 GitHub Copilot，有的团队像开挂，有的团队像在陪聊？问题往往不在模型，而在模型外面的 harness。Anthropic 讲清楚了这套七层扩展结构，我也顺手把它对应到 VS Code + Copilot Chat 里，看看固件团队到底该怎么落地。
