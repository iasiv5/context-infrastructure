# ob-harness 的持续重构引擎：pick-one-arch-task 工作流揭秘

大家手里的 AI 编程助手写代码已经足够顺手。但如果让它们面对一个有历史包袱的项目，丢出一句「帮我优化一下」，拿到的常常只是表面修补：提取函数、换变量名、加段注释。真正的系统演进需要回答一个更难的问题：在当前数万行代码里，哪个模块最必须深化？

我在维护 `ob-harness`（一个面向 OpenBMC 复杂环境的本地开发脚手架）时，用一组相互串联的 AI Prompt 和 Skill，把日常架构重构变成了一道高确定性的流水线。

这一切的起点，是仓库里一个单行指令文件 `pick-one-arch-task.prompt.md`：

> 读取并遵循 .claude/skills/improve-codebase-architecture/SKILL.md
> 深入分析仓库内容，只提供一个最重要、最紧急、必须今天开工的优化任务给我！

这个指令的核心在于物理限制。常规询问下，大模型会吐出几十条泛泛的建议。强制要求「只挑一条」后，AI 必须在底层依赖、可维护性或失效逻辑之间做取舍，给出一个具体能落地的执行点。它不做任何代码修改，只负责路由。

抓住重构锚点后，我不会立刻让 AI 改代码，而是走完一套由三个 Skill 和双 Agent 组成的审查链路。

**第一阶段，寻找浅模块。** `improve-codebase-architecture` 会基于模块深度、接口、边界和局部性等概念扫描代码。它依靠「删除测试」来判断：如果删掉某个模块会让复杂度分散到各处，说明它具备抽象意义；如果删掉只等于把一堆长代码搬移到别处，这就是个浅模块。这步寻找重构机会并梳理结构关系，明确目标，但不写代码。

**第二阶段，极端输入追问。** 选定改造目标后，直接进入 `grill-with-docs` 审查环节。此时 AI 会扮演高度挑剔的评审人，一次抛出一个问题对现状进行压力测试：接口边界设在哪？如果碰到边缘状态怎么办？旧调用究竟是立刻下线还是暂时保留？经过这种多轮澄清对抗，原本单薄的直觉往往会被打磨成一份坚实的架构决策记录（ADR）和明确的约束说明。近期提交里的 ADR-0006 和 ADR-0007 就是在这轮追问中立住的。

**第三阶段，制定执行计划与双 Agent 对抗验证。** 确认设计没有遗漏后，调度 `writing-plans` 技能，把改造方案打散成几分钟粒度的任务清单。每一步都清晰标明修改的文件路径，并要求先明确验证用例、再动手改实现。更关键的是，在这整个计划执行和代码修改过程中，我会引入「顾问 Agent」与负责执行的「主力 Agent」同台。基于 1M 级别的超大上下文容量，让顾问 Agent 针对生成的分步计划和最终修改代码进行多轮对抗性 PK。两者自动辩论、互相纠偏，直至事实合一，最大程度消除了逻辑漂移与重构事故。

计划落地期间，除了常规功能验证，我还会在测试侧加上防回归的结构锁。比如重构剔除旧方法后，明确在脚本中补充一条 `grep -c '旧函数名' 对应文件` 并断言输出必定为 0。这样做直接切断废弃代码被无意加回来的风险。

以上机制的效果，清晰印刻在仓库最近 14 条核心提交里。在这短短几天内，工作流驱动着把分散在四个不同入口的 QEMU 启动决策，安全地收拢成了单一处理入口 `resolve_qemu_launch_profile`。整个过程中，代码不仅填补了固件镜像就绪等功能盲区，把原先性能偏低的聚合记录全部替换成了细粒度查询接口，顺带把散落在底层库里的异常退出逻辑也理得一清二楚。

系统演进不再依赖个人记忆和瞬时直觉。用极简的 Prompt 限制大模型随意发散，用高压对话逼出严谨设计，用多 Agent 对抗对齐方案，最后用步骤明确的计控台管理爆炸半径——在一行 Prompt 背后建立严格的重构纪律，这便是 `ob-harness` 能够持续进化且不至于腐化的运作方式。

**摘要**：复盘我在 `ob-harness` 中用单行 Prompt 驱动持续重构的实践。从锁定唯一靶点切入，串联浅模块发掘、极限追问与任务拆解；依托长上下文引入双 Agent 对抗纠偏，配合代码防回归锁，把凭感觉的重构彻底升级为高确定性的演进流水线。
