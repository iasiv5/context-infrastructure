# 治好 AI 的失控病：小团队如何跑通 Harness

阿里云开发者公众号前几天那篇《数据研发 Multi-Agent 架构的 Harness 工程实践》在技术圈刷了屏。里面把当下 AI 工程的核心痛点说得很透：LLM 负责理解和创意，但 Harness 负责约束和验证。

Harness 原意是马具。模型就像一匹烈马，能力再强，如果没有缰绳和笼头，拉车时绝对会把你带进沟里。阿里文章甚至系统性地总结了 Harness 工程的六大支柱，非常精彩。

不过，阿里的样本全是大厂数仓级的多智能体系统。同样的问题，如果落到一个在 Linux 编译机上苦哈哈等两小时 bitbake 的固件工程师手里，这套“马具”到底长什么样？

我维护的开源工作台 `ob-harness` 恰好是这个命题的一个微缩样本。这篇不聊高大上的词汇，就聊聊在真实苦逼的 OpenBMC 开发里，我们怎么用代码给大模型套上笼头。

## 一、最让人崩溃的瞬间：看着 AI 听话且勤奋地“疯狂拆家”

把几 GB 的 OpenBMC 源码、错综复杂的 Yocto 编译环境丢给平时看着无所不能的 AI Agent，它的翻车姿势绝对能让你血压飙升：

* 你让它排查一个编译错误，它跳过环境检查直接敲了全局重编，结果你等了两小时发现它连 machine 都没初始化选对；
* 看到一行代码不对，它自作主张把你老老实实写好的 recipe 文件全给重构了；
* 碰到报错栈太长，它抓不到根因，最后总结一句干巴巴的“编译失败，请查阅日志”甩你脸上。

这其实不是模型变蠢了。核心原因在于：那些口口相传的环境依赖、硬件拓扑以及不能乱碰的红线，随着对话拉长，被它的上下文窗口无情地“漂移”掉了。二十分钟前你刚叮嘱过“AST2600 只能用特定的 defconfig”，二十分钟后它忘得一干二净。

人类的短时记忆靠不住，LLM 同样扛不住这种长程约束。你需要把这些约束从对话框里抽出来，变成硬核的工程机制。

这是 Harness Engineering 想要解决的事情，也是 ob-harness 的底色。

## 二、绝不惯着大模型：把大厂的云端架构，按扁成四招本地“必杀技”

阿里文章里列了六大支柱（身份、编排、上下文、门禁、恢复、进化），听起来像个庞大的软件工程命题。但在我们这个面向 OpenBMC 的小型终端工作台里，它们被揉成了几招刀刀见血的机制。

**第一招：划死红线，直接剥夺大模型的“自由意志”**

对于一个容易闯祸的 Agent，第一步就是教它规矩。在 ob-harness 里，我们用一个极其严格的 `AGENTS.md` 文件锁死了它的物理边界。

只要 AI 用编辑器打开仓库，这套规则就成了它的思想钢印：你是 OpenBMC 开发助手，遇到“怎么做”先去查预设的 Skill 索引，绝不许凭空猜测；所有文档产出必须老老实实写进 `docs/` 目录，不许随口敷衍。

进一步，固件项目庞大，AI 如果不经意间在根目录跑一条查询搜索，可能把几 GB 的历史编译产物扫出来，直接把 Token 挤爆。所以我们在项目级文件里硬性拦住全盘搜索，通过多层渐进式文档让它“需要看什么，才被允许读什么”。

这就覆盖了 Harness 理论里的 Identity（身份）和 Context（上下文）。

**第二招：收缴危险发令枪，用一条短命令替换 AI 的瞎摸索**

AI 会乱敲命令，是因为你没给它现成的铺装路。

我们设计了一条名为 `ob` 的 CLI 命令。初始化环境、构建镜像、看工作区状态、启动 QEMU，全被压缩进类似 `ob init` 或 `ob build` 的短命令里。

这段几千行的脚本，本身就是最大的防护网。比如下源码时，它顺手就把平台检测、SoC 型号解析、SSH key 刷新，甚至缓存目录一并搞定。这意味着“复杂的前置检查”全部被机器代劳了，AI 不需要发挥聪明才智，只管触发扳机。这便是最硬核的 Orchestration（流程编排）。

**第三招：注入暗器“退出码 3”，教 AI 看见红灯必须主动踩刹车**

这是固件命令行场景里最精彩的一个设计，也是我认为比对聊流 Agent 更高明的地方。

在日常验证阶段，编译跑几小时、启停仿真器，试错成本极高（对应 Gate 门禁）。如果 AI 遇到缺失前置条件，它很容易乱猜或者彻底放弃。

对此 `ob` 给子命令设了一条死规矩，退出码严格分四档：0 是成功，1 是真报错，2 是用户取消。关键在于**独创的退出码 3：前置缺失**。

当指令因为“环境没初始化”抛出 3 时，它会同时附带一行精准的修补提示。Agent 一旦捕获到 3，它立刻知道这不是硬失败，会自动回头去敲那行补救指令。
这等于在 Agent 眼皮底下画了一条单行道。有了它，AI 遇到撞墙就能稳定回退、自行修复。这就是最直接的 Recovery（故障恢复）。

**第四招：把痛觉写进基因，打造永不再犯错的“记忆飞轮”**

人会犯第二次错，但系统不能。Harness 理论里最高阶的环节是 Evolution（进化）。

在 ob-harness 里，我们用最质朴的脚本实现了大厂的飞轮：内置的周期自检脚本会定期触发，让 Agent 观测整个仓库的坑点，提炼后直接回写到公理文件中。
加上严格执行的 ADR（架构决策记录），今天 AI 踩了雷，明天这段痛的领悟就变成了下个 Agent 启动时的前置教材。

## 三、写在最后：不叠大厂“架构 Buff”，小团队靠什么驾驭 AI？

也许有人会问：既然阿里的样本是庞大的数仓体系，一个小巧的固件本地工作台有必要搞这么周密吗？

恰恰是因为轻便，它才更说明问题。
在本地编译机、Token 预算紧张、极度依赖命令行的特定环境里，大型云端 Agent 框架那一套太重了，反而跑不动。ob-harness 用几组 Markdown 文档、一份包含退出码契约的 Shell 脚本，把阿里的六大支柱在小场景里跑得通透无比。

开源项目的魅力不在于摊子铺得多大，而在于机制是否极其锋利且通放自如。如果你在自己的业务里也遭遇了“让大模型上产线立刻就失控惹祸”的困境，无论你的团队是一千人还是你一个人，这套机制都值得你认真抄一遍作业。

让大模型在天上飞，但必须用缰绳把它死死拴在地面的打卡机上。这就是 Harness Engineering。
