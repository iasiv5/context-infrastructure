《Harness Engineering：固件开发工作流的蒸馏与固化》 演讲稿

🔹 P1 封面 —— 各位主管、各位同事，大家下午好。我是 Iasi，目前负责 BU AI 辅助编程专案的规划与落地。今天是我们专案的第二次内部技术分享，主题是《AI 赋能固件开发——质量提升实践专场》，同时也是质量文化系列活动的一部分。

🔹 P2 —— 今天的分享分三个部分。第一部分由我来讲解如何使用Harness Engineering针对固件开发工作流进行蒸馏与固化；第二部分，四位专案组同学会分享各自的质量实践案例；包括XXX；最后是 Q&A 环节。

🔹 P3 —— 我们直接开始。

🔹 P4 —— 首先，快速回顾一下专案的进展。去年 12 月 24 号，我们做了第一次的内部技术分享，让大家对 Coding Agent 建立了基本认知。今年 3 月 22 号，我们选定 Venice OTS 平台启动了 AI Coding 试点，要求 BIOS 和 BMC 的代码尽量交给 AI 来生成，工程师聚焦设计方案审核。
三个月过去了，我们发现：对固件开发而言，代码编写并非主要挑战。关键要看 AI 的产出——是否遵循BIOS、BMC的架构与编码规范、是否正确反映硬件规格与平台约束、是否达到可交付的质量标准。
因此，我们需要一套能够约束和引导 AI 输出的工程机制来达到以上目标。

🔹 P5 —— 在讲如何约束 AI 的产出质量之前，我们先看看AI Coding 工具目前的一些问题：
如果我们只是用AI去做代码补全，或者写几个功能函数，效果确实很好。
但你让它把一个BIOS的基线功能，从零开始开发到测试通过，AI 的输出就没有那么稳定了，

我们分析发现，不是因为模型还不够聪明，而是它不了解我们的代码仓库结构、编码规范，也不知道工程师之前踩过哪些坑。这些信息 AI 读不到，自然写不出能用的代码。

举两个实际的例子。
一个是工程师让 AI 根据 I2C MAP 做 Device 配置，AI 缺少硬件拓扑知识，把设备挂错了 BUS，并且地址的冲突也没发现。另一个是让 AI 重构 PLDM 固件升级流程，AI 没看全某个函数的完整调用链，把一条没在用的路径判定为正在使用，直接把方案设计带偏了，最终只能重新做计划。

所以问题不是 AI 不能参与固件开发，是它缺少对我们场景的理解。那怎么把这些经验喂给它呢？

🔹 P6 —— 业界通常有三条路径...
第一条，自己训练专用模型，通过微调或后训练让 AI 从底层学习固件知识。
第二条，从零搭建一套固件专用的 AI 编程工具，像 AMI 这样的 IBV 厂商已经开始做了。
这两条路，对我们来说投入太重，维护成本也太高。
所以我们选了第三条路线：基于成熟的 AI 编程工具，导入我们自己的工程经验。
这个思路其实就是现在业界的共识：一个好的 Coding Agent，就是好的模型加上好的 Harness。
Harness 这个词，原意是马具，套在马身上来控制方向、引导发力。
用在 AI Coding 里，就是约束和引导 AI 输出的那套工程机制。
模型会越来越强，各家最终都会用上差不多水平的模型。真正拉开差距的，是 Harness 做得好不好。
那 Harness 具体长什么样？
（翻页）

🔹 P7 —— 模型外的所有软件基建的合集就叫harness。
它分为两层。
内层叫 Inner Harness，是 AI 编程工具自带的能力，比如：系统提示词、工具调用、任务编排。这一层由工具厂商控制，我们改不了。
外层叫 Outer Harness，包括：项目规则、领域知识、工作流以及质量门禁。这一层完全由我们自己建，BU做的所有定制都在这一层。
那 Outer Harness 怎么建？靠两个动作：蒸馏和固化。
蒸馏，就是把散落在工程师脑子里的隐性经验抽取出来，变成 AI 能读的结构化文档，一般就是 Markdown。
固化，就是让这些经验进入团队的默认流程，下次 Agent 干活的时候自动继承，不用每次手动喂。
蒸馏靠积累，固化靠机制，两个动作不断循环，Outer Harness 就是这么长出来的。那固化的方法有哪些呢？（翻页）

🔹 P8 —— 固化不是一步到位的，它通常分为四个层级。
第一层，个人可复用。把常用的 prompt 打包成斜杠命令或自定义智能体，下次直接调。
第二层，项目可继承。把开发规范写进 AGENTS.md 和 instructions文件，跟源码一起上传到git。新人 clone 仓库后，Agent 就能自动拿到规则，不用从头摸索。
第三层，平台化分发。把 Skill 和 Workflow 通过插件系统打包，安装即生效，团队规则一键同步。
第四层，流程门禁化。通过 CI/CD 系统、AI Review hooks，质量门禁由流程强制执行，不靠个人自觉。
我们在 Venice OTS 平台上已经落地了四组场景，接下来逐个展开。
（翻页）

🔹 P9 —— 第一个场景是，教 AI 读懂代码库。我们在 BMC OneTree 仓库里写入了 AGENTS.md 全局规则，把各模块的结构整理成 Markdown。AI 动手之前就知道代码在哪、该往哪写，不用每次从零摸索仓库。
第二个场景是，规范驱动开发。AI 写代码之前，强制先确认需求、明确设计边界，以文档形式落盘。代码每一步都能追溯到对应的规格文档。
第三个场景是，AI PR review。工程师在本地用 Code Review Skill 做自查，提交到 GitLab 后再过一轮 AI 初审，最后由资深工程师做人工终审。目前 Venice OTS 项目中，BIOS 和 BMC 的 PR 已经实现 100% AI 初审覆盖。
第四个场景是，经验包同步。我们把规则、指南、Skill、MCP settings用 Plugin 的方式统一打包，工程师一键安装就拿到同一套开发规则和工具。在这个基础上，我们还正在搭一个一体式开发平台，后面会重点展开。

🔹 P10 ——（核心功能）
前面四个场景，主要解决的是规则和流程的问题。但固件开发还需要 AI 能操作环境，比如：触发编译、运行仿真、采集验证结果。基于这个需求，我们搭了一个 OpenBMC 的开发工作台，叫 ob-harness。
它目前有三个核心功能。
第一，上下文自动加载。Agent 启动时自动读取项目规则和仓库上下文，快速进入开发助手的角色，开箱即用。
第二，环境操作的流程固化。OpenBMC 开发中最繁琐的环境搭建，全部固化到 ob 脚本里—— 用ob init、build、start-qemu 等命令一口气搞定。
第三，人机共享工作区。Agent 和工程师共享同一份环境状态，编译报错 Agent 能直接读到，人机之间可以灵活交互。
（翻页）

🔹 P11（设计原则）
ob-harness 有一个核心设计原则：同一个入口，服务两类用户。
CLI 模式默认给 Agent 用，Menu 交互模式给工程师用。Token 富余的时候，尽管差遣 Agent；Token 紧张的时候，多用交互模式，碰到脏活再召唤 Agent 帮忙。奢俭由你。
目前核心命令有四条：
    ob init 完成代码下载和初始化，
    ob build 完成 Machine 选择和镜像构建，
    ob start-qemu 和 ob stop-qemu 管理 QEMU 仿真环境。
每一条都是把原来手动操作的流程固化下来。
值得一提的是，ob-harness 本身就是用 AI Coding 做出来的——
它的设计文档、实施计划、代码，100% 由 AI 产出。
相当于我们用 Harness 的方法做了一个 Harness 平台，并且还在持续进化。
目前它覆盖的是 AMI Onetree BMC 的开发场景，后续有机会扩展到 SPX BMC 和 BIOS。

🔹 P12 —— 这一页，我们来看 Venice 试点的数据。
上个月我们做了两轮成员自查，发现团队使用 AI 生成的代码占比平均值从 57.8% 升到了 69.6%，中位数从 50% 直接跳到 80%。中位数涨得比均值还快，说明并不是个别人拉高了平均分，而是中间这批同事整体都在提升。
在第一轮调查时，Agent 的上下文管理问题是最多人提到的共性痛点，没有成型的方案解决。到第二轮，团队已经找到了至少三种应对方法，比如：会话 handoff、文档先行、人机接力开发。这是两轮之间最关键的能力进展。
最后再看右下角，团队的AI能力熟练度分布：大部分同事集中在 L1和L2，少数到了 L3。接下来的重点，是帮更多人尽快进阶到 L2 和 L3 。

🔹 P13 （质量与 Harness）
数据看完了，最后讲一个更根本的东西——质量。今天本身也是质量文化活动的一部分。
固件质量的终极保障，不是靠某个人的工作特别仔细，而是系统级的约束——默认不让错误通过。
在Harness 做的也是这件事情。
Venice 试点里，每一笔 PR 都会通过 AI 初审，这本身就是一道门禁。
前面提到的 I2C 挂错、PLDM 路径误判，我们已经把避坑经验逐条写进 AGENTS.md 和 最佳实践里面，下次 AI 就会自动检查。

🔹 P14 总结
过去半年，从分享建立认知，到 Venice 试点验证，有一个判断越来越明确：只要我们持续把固件开发经验蒸馏、固化、分发给 AI，AI 就能不断成长——从一个简单的工具，逐步成长为团队可依赖的固件专家。
这条路没有终点，但方向已经确认。接下来就是一步步把 Harness 做深、做厚。
