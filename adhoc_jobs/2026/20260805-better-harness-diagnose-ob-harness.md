# 给 AI 工作台做体检：为什么你的安全门禁总比契约窄一圈？（未发表）

你怎么知道给 AI 套的“笼头”真在干活，而不是只在文档里显得严密？

我维护着一个面向 OpenBMC 固件开发的 AI 工作台：[ob-harness](https://github.com/iasiv5/ob-harness)。它包含退出码契约、Stop hook、know-how 记忆和多层自测试，乍看武装到了牙齿。

当一个 harness 去审视另一个 harness，哪些设计真正有效，哪些盲区原形毕露？这是对 AI 工程能力的一次真实检验。

## 一行提示词，切入 Agent Work Loop

本地打开 ob-harness 仓库，向 Claude Code 下达指令：

```text
/goal-driven  安装  https://github.com/QoderAI/better-harness，然后调用 better-harness skill 分析 ob-harness 项目的 AI 编码工作流，并生成基于证据的报告！
```

better-harness 不写代码。它把项目里的 rules、skills、hooks、命令以及会话证据，收束为 Agent Work Loop 的五个切面：

1. 任务理解：agent 是否清楚目标、边界和完成标准
2. 可控执行：工作是否跑在可复现的支持路径上
3. 改动验证：改完有无证据证明功能正常
4. 可靠交付：执行速度是否绕过了验收与回滚
5. 经验沉淀：本次任务是否让下一次更稳

这五维，是所有试图“把 AI 钉在业务流上”的开发者必须回答的问题。

## 体检现场：前半场图文相符，后半场暗藏盲区

诊断报告给 ob-harness 打出 **65 / 100** 分。拆解五维，断层清晰：

| 维度 | 分数 | 核心判断 |
| --- | --- | --- |
| 任务理解 | **82** | 启动加载、能力清单、记忆分层确立了清晰意图与边界 |
| 可控执行 | **74** | 退出码契约与验证路径到位，权限边界依然偏软 |
| 改动验证 | **58** | 自检工具齐全，自动门禁触发面太窄 |
| 可靠交付 | **56** | 交付闭合发生在系统盲区，缺乏记录 |
| 经验沉淀 | **55** | 沉淀通路齐备，缺少可比窗口证明改进真正在发生 |

前两维高分印证了项目初衷：依靠 `AGENTS.md` 启动守卫、`ob --help` 权威清单、三层记忆结构以及退出码 `0/1/2/3` 契约，规避了 Agent 的盲目猜测。意图、权威上下文与作用边界显式可恢复。

但改动验证仅得 58 分。报告的判断直切要害：**任务理解扎实，主要缺口集中在变更验证的最后一公里。**

## 致命 Finding：门禁宽度窄于文档契约

报告开出的 3 条 finding 中，核心盲区浮出水面：

**Stop hook 自检门禁只覆盖 `ob/lib`，`know-how` 与 `tools/*.py` 改动收口不到验证。**

对比文档承诺与实际代码，落差一目了然：

- 📝 **文档承诺**：`tools/ob_check.sh` 是一站式自检工具，改完 ob / know-how 必跑。
- 🔍 **实际代码**：Claude Code 会话结束时触发的 Stop hook，正则表达式仅拦截了 `ob` 和 `lib/*.sh`。

这意味着，改动 `tools/exit_contract.py` 或 `rules/knowhow/*.md` 时，会话 Stop 根本不触发自检。契约违规与知识漂移，在被抓住前就已落盘。

Harness 工程里隐蔽的失败从来不是零门禁，而是**看似全覆盖，实际只罩住了最顺手的那一小块**。

> [截图 - Finding 1 详情：Stop hook 覆盖面窄于 mandate]

另外两条 Low 级 finding 同样精准：
1. **失败路径缺少 Fail-Closed 守护**：Stop hook 阻塞决策依赖未受保护的 `python3`。一旦 Python 环境挂掉，脚本直接 `exit 0`。门禁最怕装死放行。
2. **长文件缺乏渐进式披露**：`handoff` skill 长达 141 行，未拆分本地引用。强迫 Agent 一次性吞下全文，极易丢失尾段约束。

这暴露出前半段“让 agent 懂事”虽有成效，后半段“让改动强制过闸”依然漏风。

## 抛开分数，体检背后的工程价值

这份报告的核心工程价值在于三点：

**第一，绝不拿“缺乏证据”粉饰太平。**
市面上的看板极易把“没观察到”粉饰为“测试通过”。better-harness 反其道而行：没捕获到闭合样本，就如实标记未观察。流畅度结论严格基于已复核样本，强制倒逼系统补齐可观测性。

**第二，将残缺收束为精准的可修复行动。**
没有空洞的口号，每条 finding 皆有清晰的 owner、验证路径和局部 AI 修复提示词。以 Stop hook 修复为例，报告直接界定了正则表达式的扩展范围，并要求保持静态语义不变。下一刀砍哪里，板上钉钉。

**第三，对齐工作流 (Loop)，而非单点输出 (Node)。**
ob-harness 解决 Agent 怎么少闯祸；better-harness 检验这套约束、门禁与沉淀是否真正形成闭环。上一次勒马，有没有变成下一次的肌肉记忆？这决定了工程进化的速度。

## 自测指南：你的工作流“漏气指数”有多高？

若你的仓库同样堆满了 `AGENTS.md`、skills、hooks 和脚本，却不清楚哪段在闭环、哪段是摆设，用这四个标准自查：

1. **加厚前半场**：Agent 启动时，是否清晰查阅了能力清单和退出码契约？
2. **校验触发面**：自动化测试与规范检查的宽度，是否严格等于文档写明的范围？
3. **闭环 Fail-Closed**：阻塞决策的底层依赖失效时，工作流是阻断运行，还是悄悄放行？
4. **沉淀有效性**：写在 know-how 目录里的经验，究竟有没有在后续任务中自动唤醒并避坑？

单靠人脑 review 难以覆盖全链路，引入自动化诊断工具跑一次客观分析，是打破信息茧房的最快路径。

## 结语

ob-harness 把 AI 钉在固件开发流程上。
better-harness 检查这根钉子有没有穿透、有没有松动、松动后系统能否自我发现。

AI Coding 进入深水区，真正拉开差距的是对工作环的可观察、可验证、可演进。谁能拿出硬证据证明“门禁宽度等于契约宽度”，证明“失败时绝不静默放行”，谁才能真正驯服大模型这匹烈马。

分数不高，但缺口终于从“感觉不对”变成了精确的工单任务。
