# ob-harness 实战：砍掉 Agent 过度设计，内置 Goal-Driven 提示词

AI Coding 步入实战深水区后，让 Agent 敲出代码已不再是门槛；防范它随时发作的过度设计，才是日常交锋的重头戏。

在 ob-harness 下，Goal-Driven 提示词能让系统通过 goal 与 criteria 自主收敛（详见上篇实战）。但随着使用频次增加，跨会话复制粘贴的摩擦成本随之显现。将其内置为和 ai-heartbeat 平级的独立斜杠命令，能省去启动任务的准备时间。

动手前，用 `/grill-with-docs` 锁死意图：

> /grill-with-docs 我最近在频繁使用 lidangzzz 的 Goal-Driven 提示词模板，觉得效果不错，打算把这个模板内置到 ob-harness，省去每次手动复制到会话窗口的操作。梳理可行的设计思路，之后与我确认。可参考本仓库 ai-heartbeat、pick-one-arch-task、sediment 等斜杠命令的设计方式，方案需要同时适配 Claude Code 以及 GitHub Copilot；Goal-Driven 提示词模板内容参考文档：https://github.com/lidangzzz/goal-driven/blob/main/readme_cn.md

## 第一阶段：常规边界对齐 (Q1~Q4)

前四轮交互，核心是拉齐新命令的功能底线。

**Q1：交付形态**
Agent 给了多个推荐，我选择依赖最小的“模板组装器”方案。同时要求补齐关键卡点：未输入参数时，分两次弹窗追问 goal 与验收标准。组装完成后，允许自由选择当前会话继续或另起新会话。
> [截图：Q1 Agent 首轮推荐]
> [截图：我对 Q1 的补充反馈]

**Q2：追问逻辑归属**
智能追问逻辑的内聚程度必须克制。共享一份契约指令，具体追问节奏交给不同 Agent 让各自的 LLM 发挥，不在某一端写死。
> [截图：Q2]

**Q3：门禁 UX 处理**
针对输入不达标情况，接受 Agent 先做引导式改写的建议（MVP 务实策略），延后 UX 规范优化。
> [截图：Q3]

**Q4：命令层级**
敲定作为仓库级命令沉淀，与 ob-harness 一同发布，闲置时不占用新会话上下文。
> [截图：Q4]

## 第二阶段：阻断过度设计 (Q5)

确立归属层后，Agent 暴露了严重的过度发散倾向：试图为主线外的配置新增一整套治理动作。

如果听任它发挥，仓库里会多出一份冗余的 SKILL 文档、一份无效的 ADR 记录，甚至还要横生枝节去修改全局的 `03_WORKSPACE.md` 路由。这正是大模型在工程化中的典型坏味道——把小需求张罗成大工程。

面对这份臃肿的方案，我直接挥刀收紧边界：

❌ **拒绝扩散**：不新增 skill，不新增本地 know-how
❌ **拒绝形式主义**：不新增 ADR，不改 ATTRIBUTIONS
❌ **拒绝越权**：不变更 03_WORKSPACE.md 路由
✅ **锁定唯一目标**：只新增两组斜杠命令，完成模板组装器

## 后记

日常开发中，`/grill-with-docs` 有两层用法。表层用于常规意图对齐和边界收敛；深层则是作为防波堤，给 Agent 的过度设计做减法。本文 Q5 环节正是防范发散的典型示范。

工程师视角下的最小可用形态，永远比大模型自我加戏的大而全更具维护价值。放任 Agent 堆砌废弃文档和无效代码以满足其表现欲，是对长线项目极其危险的污染。
