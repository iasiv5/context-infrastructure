# Claude搭配GPT-5.4，Copilot这波左右互搏能干掉多少Bug？

程序员圈子里一直有个古老的玄学：**“橡皮鸭调试法”（Rubber Duck Debugging）**。就是当你遇到死活解不开的Bug时，只要桌上摆只小黄鸭，对着它把代码逻辑逐行念一遍，往往讲着讲着你自己就豁然开朗了。

就在这两天，GitHub官方发布了一篇很有意思的博客，正式介绍了Copilot CLI里的一个新机制：**Rubber Duck（小黄鸭）**。只不过这一次，他们给AI也配了一只“电子鸭”。

https://github.blog/ai-and-ml/github-copilot/github-copilot-cli-combines-model-families-for-a-second-opinion/

不知道你平时用AI写代码有没有遇到过这种情况：Agent在最开始定方案（Plan）的时候就带了点方向性的偏差，结果它越写越自信，洋洋洒洒几百行代码改下去，最后跑不通。更搞心态的是，当你让它“检查一下自己写的代码”，它看半天告诉你“没毛病”——**这就叫「一本正经地在错误的道路上狂奔」。**

看完了这篇官方博客和行业分析，最大的感受是：**单模型瞎卷的时代快过去了，Agent架构终于走向了“多模型协作”的实用阶段。**

### 为什么AI也需要外援Review？

在过去，解决Agent幻觉的主流做法是**自我反思（Self-reflection）**。大白话就是让大模型写完代码后，自己再看一遍。

但这有个致命的逻辑漏洞：**自己查自己的卷子是查不出错的。**

因为同一个模型家族有着固定的训练数据、相似的系统性盲区和偏见。如果你用Claude Sonnet 4.6来写代码，再让它自己来Check，它大概率会自动忽略掉同类型的Edge Case。

怎么破？**刻意引入外部视角，搞跨家族审查**。这就是Rubber Duck的核心思路。官方给出的硬核配对表是这样的：

| 主编排模型（负责干活） | 审查模型（负责找茬） |
| :--- | :--- |
| Claude Sonnet | **GPT-5.4** |
| Claude Opus | **GPT-5.4** |
| Claude Haiku | **GPT-5.4** |

也就是说，让Claude的细腻代码能力去干苦力写实现，碰见架构规划或者需要严谨批判的时刻，让OpenAI的硬核逻辑来**找茬**。

###跑分惊艳：省钱还强的小妙招

这就带来了一个极大的优势：**更高的性价比。**

官方在难度极高的开源仓库基准测试 **SWE-Bench Pro** 上跑了分，拿到了一个相当惊人的数据：

**Claude Sonnet 4.6搭配GPT-5.4 (Rubber Duck)，直接填补了中杯Sonnet 4.6和超大杯Opus 4.6之间74.7%的性能差距。**

简单算笔账你就懂了：你可以用更便宜、更快的Sonnet模型来干粗活，在关键节点让GPT-5.4来把关，最后的代码质量极其接近全程用极其昂贵的Opus 。更夸张的是，在涉及3个以上文件、70步以上操作的高复杂度长链路任务中，这个“互搏组合”的拦截效果最为显著（提高了3.8%~4.8%）。

### 真实场景能拦住什么Bug？

比起跑分，我更关心拿它干活到底稳不稳。官方给出的几个真实Issue拦截案例，确实是程序员看了会捏把汗的那种：

* **防范架构级翻车（OpenLibrary异步调度器）**：主Agent写的调度器会在启动时立即退出（执行零次任务），而且里面居然还藏了个无限循环。小黄鸭在定架构的Plan阶段一眼看穿并当场拦下。
* **找出一行代码的血案（Solr搜索词典）**：主Agent在循环里静默覆盖了`dict`的同一个 Key，导致四个搜索分类丢了仨，全程还不抛任何异常。如果这代码上了线，排查起来绝对让人绝望，但由于两个模型的思考链路不同，小黄鸭精准捕获。
* **跨文件冲突背锅（NodeBB 邮箱验证）**：修改验证逻辑时，主Agent停用了对某个Redis Key的写入，但完全忽略了还有三个其他文件在等着读这个Key。如果不拦住，用户的确认UI和清理逻辑一上线就会静默崩溃。

这些都是如果不做深度Code Review，必定**炸服**的高级Bug。

### 最佳使用姿势与触发机制

要用这个新功能并不难。你只需要安装最新的 [GitHub Copilot CLI](https://github.com/features/copilot/cli)，然后在命令行里敲：

```bash
/experimental on
```

这只“小黄鸭”的唤醒机制很克制，不复杂改动系统架构，而是复用了现有的Task Tool。它主要在以下几个高杠杆的黄金节点跳出来：

1. **主动触发 - 写完Plan之后**：这是目前收益最大的阶段。方案歪了直接重做，防止错误狂飙。
2. **主动触发 - 复杂实现之后**：找找有没有遗漏Edge Case的角角落落。
3. **主动触发 - 陷入死循环时**：如果Agent自己报错卡死，会乖乖求助小黄鸭打破僵局。
4. **被动触发 - 测试代码执行前**：防止大模型写那种只会**全绿 Pass**的废话单元测试。

当然，身为包工头，随时可以强行下达指令：`"Critique your work"`（评审一下你的工作）。Copilot会调用小黄鸭推理，再老老实实把哪里改了以及为什么改展示给你。

### 说实话，我对多模型协作的看法

这一系列骚操作，释放了一个清晰的明确信号：**大模型单纯靠怼Context窗口的独奏时代行将结束，多模型协作（合奏）逐渐成为新范式。**

这就像是一个团队里，哪怕执行力强的初级架构师堆再多，也代替不了一个眼光毒辣的老兵来做深度Code Review。

不过目前它也有很明显的局限：
* **Token与延迟代价**：多调一个模型，意味着双倍的Token成本消耗和更长的等待时间。
* **配对的局限**：目前主要只能Claude系列干活，GPT系列把关，期待后续放开更多自由组合（毕竟，未来各家的竞争可能会变成“谁更适合当包工头”和“谁更适合当质量质检员”）。

最后调查一下：**你平时写代码遇到过AI过于自信结果弄出一堆Bug的情况吗？对这种“用魔法打败魔法”的多模型审查怎么看？欢迎在评论区聊聊！**
