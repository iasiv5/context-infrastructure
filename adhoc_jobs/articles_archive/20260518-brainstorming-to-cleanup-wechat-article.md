# 从 brainstorming 到 cleanup：我用 14 轮对话把 GitHub Copilot Skill 补成闭环

最近我在做一件看起来不大、但我自己觉得很关键的事：把卡兹克的 neat-freak skill 改造成适合 GitHub Copilot 使用的版本，重命名为 cleanup，并且和我之前已经做好的 handoff skill 组成一套真正闭环的工作流。

表面上看，这像是一次普通的 skill 迁移和适配；但真做进去之后我很快发现，最难的根本不是改提示词格式，也不是补几份 reference 文档，而是要先把一件事想清楚：handoff 和 cleanup 到底分别负责什么，它们在整个会话流程里应该按什么顺序出现。

如果这个边界不清楚，后面所有实现都只是在堆功能。你做出来的不是工作流，只是两个名字不同、职责重叠的命令。

这次我没有直接开写，而是先按一条我越来越认可的路线走：先用 brainstorming 把设计想透，再让 writing-plans 把设计拆成可执行步骤，最后才进入 cleanup skill 的具体改造。结果也证明，这套顺序在中等复杂度的改造任务里，是真的省事。

## 这次实操，真正想补上的是什么

我前面已经把 GitHub Copilot 版的 handoff 做出来了。它解决的是会话接力问题，也就是把一轮对话里还不稳定、但已经足够继续工作的上下文，整理成下一轮还能接着跑的材料。

但 handoff 不是终点。一个工程型工作流不能只有“往前传”，还要有“往下沉”。那些已经收敛成稳定事实的知识、约束、文档和经验，最终还是要沉淀到长期载体里。cleanup 要解决的，就是这个问题。

我对这套分工的最终定义很简单：

- handoff 负责带着不稳定但足够继续工作的上下文往前跑。
- cleanup 负责把已经收敛成稳定事实的东西沉淀到长期载体。

这两句话看起来很轻，但其实决定了整个 skill 的触发策略、输出边界、默认写入范围，甚至决定了用户愿不愿意真的把它用起来。

## 真正的拉扯，不在实现，而在顺序

第一轮 brainstorming 之后，Agent 基本认同了我想做“handoff + cleanup 闭环”的大方向。但很快，分歧就出来了。

Agent 更倾向于在过程中发现“稳定长期事实”时，就顺手做一次 checkpoint cleanup；而我的直觉很明确：前期无论开多少轮会话，都优先只用 handoff 交接，等整个任务完成、结论真正定型之后，再做一次 deep cleanup。

原因也很现实。第一，如果每一轮会话都要先沉淀、再交接，用户流程负担会明显变重。第二，中途结论往往还在抖动，过早沉淀只会污染长期知识。第三，所谓“什么时候算稳定”本身也是一种额外判断，而判断成本最后还是落在用户身上。

所以第二轮到第五轮，对话的核心其实都围绕这一点在来回拉扯。Agent 试图说服我保留中途 checkpoint，我则一直坚持只保留终态 deep cleanup。直到后面，我们才算把分工真正对齐。

## brainstorming 最值钱的地方，不是给答案，而是逼你把边界说清楚

这次我对 brainstorming 的体感其实更强了。它最有价值的地方，不是一次性甩给你一堆方案，而是很懂“苏格拉底心法”：一次只逼你回答一个关键问题。

在 cleanup 这个任务里，这种节奏特别有用。因为它不会让你一下子冲进实现细节，而是不断把你拉回到真正需要先定的几个判断上：要不要硬触发？要不要保留软提醒？用户显式调用时系统该不该继续拦？默认允许更新哪些正式工件？范围是在仓库内，还是连仓库外知识也一起动？

第六轮到第九轮，基本就是在把这些设计边界一层层钉住。最后收敛下来的方案，我自己是满意的：触发策略保守，必要时以手动 /cleanup 为主；对硬触发的副作用增加软提醒；如果用户已经显式调用，就提醒到位但不替用户做决定；默认可更新范围限定在仓库内文档与记忆。

这几个点如果不先想清楚，后面哪怕代码和文档都写得很漂亮，产出的也大概率只是一个“看起来很完整”的 skill，而不是一个真正顺手、真正不扰民的 skill。

## 从设计文档到实施计划，这一步真的别省

等边界收住之后，事情就顺了很多。Agent 先把 spec 设计文档落到 docs/specs 下面，再进入 writing-plans，把前面已经达成共识的内容拆成具体实施步骤、文件职责和验证方式。

这一段我反而觉得是很多人最容易跳过、但最应该保留的一步。因为很多“以为自己想清楚了”的需求，真正一写计划就露馅了。你会发现原来哪些文件要改、哪些 reference 要带、验证是跑冒烟还是跑 eval、哪些是这次必须做、哪些可以后移，这些事如果不在计划阶段摊平，实施阶段就会开始不断返工。

当时整个链路大概就是这样：

```text
/brainstorming
  -> 产出设计文档：docs/specs/<YYYY-MM-DD>-<topic>-design.md
/writing-plans
  -> 产出实施计划：docs/plans/<YYYY-MM-DD>-<feature>-implementation-plan.md
按计划执行 cleanup 改造与开发
```

对我来说，这三步连起来的意义很明确：brainstorming 负责把问题想透，writing-plans 负责把动作排顺，真正动手时就不容易东一榔头西一棒子。

## 最后 3 轮，看起来像收尾，实际上是在补工程完整性

很多这类任务，做到能跑就会收工。但这次我最后反而盯得更细，因为我不想把 cleanup 做成一个“功能看着有了，但资产不完整”的半成品。

第十二轮，我明确追问了两个问题：cleanup skill 的 reference 目录为什么没一起移植过来？致谢章节为什么不把 neat-freak 的原始地址带上？这两个问题都不大，但都非常像真实工程里最常见的漏项。主逻辑对了，边角却没收干净。

第十三轮，Agent 解释了为什么前面没有带 reference 资产；我这边的决定也很直接：要移植，但要做 GitHub Copilot 语境下的适配删减，而不是机械照搬。这个判断我认为也很关键，因为“完整迁移”和“合理迁移”不是一回事。前者只是搬运，后者才是适配。

第十四轮，就是最后的冒烟测试和收尾。到这里，这个 skill 才算真的从概念走到了一个可交付状态。

## 这 14 轮对话，分别解决了什么

为了方便你后面往文里插截图，我把这 14 轮的作用压缩成一个清单。你完全可以把每一轮截图跟下面对应的小结放在一起，整篇文章会更有“实操复盘”的感觉。

1. 第 1 轮：确认大方向，cleanup 要和 handoff 组成闭环，而不是单独存在。
2. 第 2 轮：首次正面讨论 handoff 和 cleanup 的先后顺序，以及流程负担问题。
3. 第 3 轮：明确坚持只保留终态 deep cleanup。
4. 第 4 轮：继续围绕 checkpoint cleanup 的必要性做拉扯。
5. 第 5 轮：最终把 handoff 与 cleanup 的职责边界定清。
6. 第 6 轮：确定保守触发策略，并接受部分手动触发。
7. 第 7 轮：针对硬触发副作用，补上软提醒机制。
8. 第 8 轮：明确用户显式调用 /cleanup 时，系统只提醒，不越权替代。
9. 第 9 轮：限定默认可更新范围为仓库内文档和记忆。
10. 第 10 轮：把设计落成 spec，正式结束纯讨论阶段。
11. 第 11 轮：从设计切换到 writing-plans，并按计划进入开发。
12. 第 12 轮：补查漏项，追 reference 资产与致谢来源。
13. 第 13 轮：决定移植 reference，但做 Copilot 适配删减。
14. 第 14 轮：做冒烟测试，正式收尾。

## 我对这次实操的最终判断

如果让我把这次经验压成一句话，那就是：中等复杂度的改造任务，真的很适合先 brainstorming，再 writing-plans。

原因并不玄乎。很多需求一开始只是“我想做某个东西”，听起来方向没问题，但一旦往下追问：边界是什么、谁负责什么、什么时机触发、默认改哪里、验证怎么做，马上就会暴露出一堆还没想透的地方。这个时候直接开写，后面十有八九要回头返工。

而 brainstorming + writing-plans 这套串联，恰好把这两个坑拆开处理了。前者解决“到底该怎么想”，后者解决“接下来该怎么做”。对 cleanup 这次改造来说，这不是流程装饰，而是效率来源。

最终做完之后，cleanup skill 已经归档并上传到 GitHub：

- handoff: https://github.com/iasiv5/m/tree/main/plugins/iasi/skills/handoff

- writing-plans: https://github.com/iasiv5/m/tree/main/plugins/iasi/skills/writing-plans

如果你最近也在折腾 Agent 工作流，或者也在想怎么把“会话接力”和“经验沉淀”补成一个真正顺手的闭环，我建议你试一次这种做法：别急着写，先把设计逼清楚；别刚有点想法就到处沉淀，等结论真的稳定了，再做一次干净的 cleanup。

很多时候，拉开差距的不是模型多强，而是你有没有把工作流里的边界、顺序和收尾认真设计过。
