# 大模型越强，FDE 为什么反而更值钱了

这两天我连续刷到三条消息。

OpenAI 砸 40 亿美元，专门成立 OpenAI Deployment Company。

Anthropic 把 Applied AI 团队和 FDE 一起塞进 FIS，去做金融犯罪相关的 Agent。

Google Cloud 也在大规模招 FDE。

我当时就愣了一下。

因为这三件事摆在一起，味道太明显了。

过去两年，AI 公司最爱讲的，是模型。

谁更强，谁上下文更长，谁推理更稳，谁价格更低。榜单一更新，行业就热闹一轮。

但最近这个风向，已经不是单纯比发动机了。

开始比修路了。

你想想看，再强的模型，如果进不了企业的权限系统，接不上老旧数据库，过不了审计，扛不住流程里的各种例外，那它在会议室里再惊艳，到了生产环境也还是会卡住。

这就是我看到 FDE 这波招聘时最强烈的感受，企业 AI 的战场，真的在从模型能力，往部署能力那边拐。

（正文插图说明：OpenAI、Anthropic、Google 押注 FDE 的信息卡片，三列排版，重点突出 40 亿美元、FIS、数百名 FDE 这几个信号。）

很多朋友第一次听到 FDE，会下意识把它理解成驻场实施。

我自己的感受是，只这样理解，低估它了。

FDE，Forward Deployed Engineer，你可以先把它理解成离客户最近的产品工程师。

不是去现场装个系统、配个接口就走。

而是要钻进客户真实业务里，把那些写不进 PRD 的东西，一点点拎出来。

比如一家银行说，我想用 Agent 提高反洗钱效率。

这句话听起来很明确，对吧。

可项目真开起来，问题马上就来了。

哪些数据能给模型看，哪些字段必须脱敏，哪些判断一定要人工复核，风险分层怎么算，报告写到什么程度才算合规，模型如果误判了，锅算谁的。。。

这些东西，没有一条会老老实实写在产品说明书里。

它们藏在流程里，藏在旧系统里，藏在法务和审计的红线里，也藏在一线员工那些说不清但真的很重要的经验里。

所以 FDE 干的，不是简单的技术接入。

它干的是翻译。

把客户嘴里那个我就想提升效率，翻译成一套能跑、能查、能审、能复盘的系统。

说真的，这类活儿很脏，也很难。

但 Agent 时代，偏偏最缺的就是这种人。

因为 Agent 这玩意，跟普通软件不一样。

普通软件更像工具，你点一下，它动一下。一个报表系统，只要查数、筛选、导出做得稳，它就已经有价值了。

Agent 更像实习生。

你给它一个任务，它要自己找资料、调工具、串系统、产出结果。做好了，效率确实很爽。做歪了，整个流程都可能被它带偏。

这也是很多企业嘴上说着想上 Agent，身体却很诚实地先踩刹车的原因。

不是他们保守。

是谁也不敢把审批、客服、财务、风控这些流程，直接交给一个边界还说不太清的家伙。

你如果是甲方技术负责人，你也会怕。

数据怎么接。

权限怎么管。

AI 出错怎么办。

结果谁来背书。

一层一层往下问，最后你会发现，企业买的根本不只是一个模型接口，它买的是一整套把不确定性关进笼子里的能力。

这时候你再说，接个 API 就行了，谁敢信？？？

（正文插图说明：Agent 进入企业流程的示意图，中间是 Agent，左边放数据和工具，右边放权限、审计、人工复核，用几条红线标出风险节点。）

回到 FDE 这块，位置就在这儿。

有人得真的进现场。

去看那条流程到底怎么跑，去问那个老系统为什么没人敢动，去弄明白哪个动作能自动化，哪个动作必须留给人。

你坐在办公室里，看十份需求文档，真不一定看得出来。

Palantir 早年那套打法，之所以一直有人反复拿出来聊，就是因为它很早就把这件事吃透了。

复杂行业，尤其是政府、金融、能源、制造这种地方，需求往往不是先定义清楚再开发。

很多时候，是先进去解决问题，边做边把问题定义清楚。

这套方法放到今天的 Agent 上，反而更成立了。

因为 Agent 离业务太近了。

离权限近，离责任近，离事故也近。

你会发现，大家以前以为企业买 AI，买的是一个大脑。

现在真跑起来才知道，企业先买的往往是一双能下地干活的手。

然后才是脑子。

这也是为什么 OpenAI、Anthropic、Google 会同时盯上 FDE。

它们不是突然爱上了重交付。

而是终于承认了一件很现实的事，模型不是终点，进系统才算开始。

（正文插图说明：FDE 从现场问题走向平台能力的转化图，左边是客户现场的脏活累活，右边是沉淀出来的组件、模板和行业方案。）

顺着上面的再聊聊，FDE 这个岗位看起来很美，但也确实有坑。

如果每个客户都要长期驻场一支团队。

如果每次项目都高度定制。

如果同样的问题反复靠人肉兜底。

那这条路走着走着，就很容易从产品公司滑成咨询公司。

这个分界线，我觉得特别重要。

FDE 到底是在给产品找方向，还是在拿人力补产品的洞，差别非常大。

怎么判断呢，我一般会看三件事。

第一，后面的项目，有没有明显比前面的项目更快。

第二，现场写出来的代码，有没有慢慢变成通用组件。

第三，不同行业里反复出现的问题，有没有沉淀成模板、评估方法和标准流程。

如果这三件事都没有发生，那就危险了。

那不是复利。

那是堆人。

（正文插图说明：产品复利和高级外包的对照图，左边写越做越轻，右边写越做越重，中间用时间轴拉开差异。）

我一直觉得，很多人喜欢把 FDE 说成 Agent 时代的 PMF 密码，这个话听着挺带劲，但说实话我也不敢把话说满。

FDE 不是 PMF。

它更像探路队。

或者说，先去河里趟水的人。

为什么我这么说。

因为真正的 PMF，应该是客户可以相对低成本地采用，产品能够反复复用。

团队不需要每来一个客户，就从头造一遍轮子。

如果一个产品离不开大量工程师长期陪跑，那它离真正成熟，还是有段距离的。

但这不代表 FDE 不重要。

恰恰相反，在 Agent 这波浪潮里，它可能是最诚实的一种求真方式。

你在客户现场，哪些需求是真的，哪些只是发布会上好看，哪些流程能标准化，哪些坑根本不能绕，这些东西一下就露出来了。

FDE 的价值，不是把一个项目做完。

而是把项目里反复出现的真问题，带回去长成产品。

这才是复利的起点。

对企业客户来说，这里面还有个很现实的问题。

如果厂商真的派了 FDE 进来，你该怎么接。

坦率地讲，我觉得至少要盯住三件事。

项目做完之后，你自己的团队能不能接住。

关键知识，有没有留在你自己的体系里。

下一个场景，要不要还能复用这次留下来的东西。

如果这三件事答不上来，那你买到的更像一次漂亮交付，不太像能力建设。

这话听着可能有点刺耳。

但企业做 Agent，真不能只问，这个项目能不能成。

更该问，做完这个项目之后，我们能不能更容易做成下一个。

（正文插图说明：甲方技术负责人评估 FDE 的检查清单图，重点放接得住、留得下、能复用这三件事。）

说到底，FDE 这波热起来，不是在告诉我们又出现了一个新岗位。

它更像一个信号。

AI 公司开始补最难的一课了。

这让我想起 SaaS 刚进企业的那些年，大家一开始都以为自己卖的是软件，后来才发现，真正难卖的其实是流程重组和组织信任。

今天的 Agent，只是把这件事又抬高了一个维度。

上半场，拼的是模型，谁更强，谁更快，谁更便宜。

下半场，拼的是谁更懂现场，谁更懂流程，谁能把模型从演示台上拽下来，塞进企业每天真实运转的系统里。

所以再回头看 OpenAI、Anthropic、Google 那三条消息，我反而一点也不意外。

风向确实变了。

不是因为模型突然不重要了。

而是因为模型终于要下场干活了。

## 文章摘要

OpenAI、Anthropic、Google 同时押注 FDE，背后不是岗位包装，而是企业 AI 的竞争正在从模型能力，转向部署能力。FDE 不只是驻场工程师，它更像带着产品下场修路的人，决定 Agent 能不能真正走进生产环境。
