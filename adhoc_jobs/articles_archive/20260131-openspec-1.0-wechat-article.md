# OpenSpec 1.0 发布:从"线性僵化"到"灵活迭代"的革新

你是否经历过这样的场景:精心制定了详细的需求文档,编码过程中发现问题,却发现很难回头修改规划?或者团队成员在不同阶段工作,却无法看到彼此的进度?

这些是传统开发工作流的典型痛点——线性、僵化、无法迭代。

OpenSpec 1.0 正是为了解决这些问题而诞生。今天,我们来深入了解这个规格驱动开发工具的核心变革,以及它如何通过新的OPSX命令让开发工作流变得灵活而高效。

---

## 核心理念:fluid not rigid

OpenSpec 1.0 的设计哲学可以概括为一句话:**fluid not rigid, iterative not waterfall, easy not complex, built for brownfield not just greenfield, scalable from personal projects to enterprises.**

简单来说:
- **fluid not rigid** - 灵活而非僵化,适应你的开发节奏
- **iterative not waterfall** - 迭代而非瀑布,支持边做边学
- **easy not complex** - 简单而非复杂,降低学习成本
- **built for brownfield** - 不仅适合新项目,也能融入现有代码库
- **scalable** - 从个人项目到企业级应用都能适用

## 工作流的根本性变革

### 旧工作流:线性且僵化

在OpenSpec 1.0之前,工作流是这样的:

```
PLANNING ────────► IMPLEMENTING ────────► DONE
    │                    │
    │   "无法返回"      │
    └────────────────────┘
```

这个流程的问题显而易见:
- 一旦进入IMPLEMENTING阶段,很难返回修改PLANNING
- "全有或全无"的方式,不够灵活
- 无法在编码过程中迭代规划文档

### 新OPSX工作流:灵活且迭代

OpenSpec 1.0引入了全新的基于动作的工作流:

```
proposal ──► specs ──► design ──► tasks ──► implement
    ▲           ▲          ▲                    │
    └───────────┴──────────┴────────────────────┘
           在学习时随时更新
```

关键变化:
- **基于动作而非阶段** - 任何时候都可以执行任何操作
- **工件依赖关系** - 依赖关系是指南,不是门禁
- **支持迭代** - 学习过程中可以随时更新工件
- **细粒度控制** - 10个精心设计的命令,满足不同场景

## 10个OPSX命令快速上手

OpenSpec 1.0引入了10个新命令,取代了旧版的3个命令。让我们重点了解核心命令的用法。

### 核心命令:日常开发必备

#### 1. /opsx:new - 开始新更改

```
/opsx:new [change-name] [--schema <schema-name>]
```

创建一个新的更改文件夹,准备开始工作。

**示例:**
```
你: /opsx:new add-dark-mode

AI:  Created openspec/changes/add-dark-mode/
     Schema: spec-driven
     Ready to create: proposal
```

#### 2. /opsx:ff - 快速生成所有规划文档

```
/opsx:ff [change-name]
```

当你需求明确,想快速进入实施阶段时使用。

**示例:**
```
你: /opsx:ff add-dark-mode

AI:  ✓ Creating proposal.md
     ✓ Creating specs/ui/spec.md
     ✓ Creating design.md
     ✓ Creating tasks.md
     Ready for implementation!
```

#### 3. /opsx:continue - 逐步创建工件

```
/opsx:continue [change-name]
```

当你需要逐步审查和调整时使用,每一步都可以停下来确认。

**示例:**
```
你: /opsx:continue

AI:  Artifact status:
     ✓ proposal    (done)
     ◆ specs       (ready)
     ○ tasks       (blocked)

     Creating specs...
     ✓ Created openspec/changes/add-dark-mode/specs/ui/spec.md
```

#### 4. /opsx:apply - 实施任务

```
/opsx:apply [change-name]
```

根据tasks.md逐个完成实施任务。

**示例:**
```
你: /opsx:apply

AI:  ✓ 1.1 Create ThemeContext
     ✓ 1.2 Add CSS custom properties
     ✓ 2.1 Implement localStorage
     All tasks complete!
```

### 其他重要命令

#### /opsx:explore - 探索式思考

在提交更改前,先调查问题、澄清需求。特别适合不确定具体需求的时候。

```
/opsx:explore [topic]
```

#### /opsx:verify - 验证实施质量

在归档前,验证实现的完整性、正确性和连贯性。

```
/opsx:verify [change-name]
```

#### /opsx:archive - 归档已完成更改

完成更改,同步规格,并归档到历史记录。

```
/opsx:archive [change-name]
```

#### /opsx:bulk-archive - 批量归档

一次性归档多个更改,自动处理规格冲突。

```
/opsx:bulk-archive [change-names...]
```

#### /opsx:sync - 同步增量规格

手动将delta规格合并到主规格(通常在archive时自动执行)。

```
/opsx:sync [change-name]
```

#### /opsx:onboard - 15分钟引导式教程

新用户的首选,通过实际操作快速上手。

```
/opsx:onboard
```

## 实际应用示例:完整的开发循环

让我们通过一个实际例子,看看OpenSpec 1.0的工作流如何运作。

假设我们要为网站添加"暗黑模式"功能:

**Step 1: 创建更改**
```
/opsx:new add-dark-mode
```

**Step 2: 快速生成规划文档**
```
/opsx:ff
```
此时会生成:
- `proposal.md` - 为什么要加暗黑模式
- `specs/` - 功能需求和场景
- `design.md` - 技术实现方案
- `tasks.md` - 实施清单

**Step 3: 实施功能**
```
/opsx:apply
```
逐个完成tasks.md中的任务,代码写完后自动勾选。

**Step 4: 验证质量**
```
/opsx:verify
```
检查是否:
- 所有任务完成
- 所有需求实现
- 代码和设计一致

**Step 5: 归档更改**
```
/opsx:archive
```
将变更移至归档目录,同步规格到主文件。

**完整目录结构:**
```
openspec/
├── changes/
│   └── add-dark-mode/
│       ├── .openspec.yaml
│       ├── proposal.md
│       ├── specs/
│       │   └── ui/
│       │       └── spec.md
│       ├── design.md
│       └── tasks.md
└── changes/archive/
    └── 2025-01-24-add-dark-mode/
        └── [same structure]
```

## 工件结构:清晰的职责划分

OpenSpec 1.0使用4种工件,每种都有明确的职责:

| 工件 | 职责 | 示例内容 |
|------|--------|----------|
| **proposal.md** | "为什么"和"什么" | 业务价值、范围、方法 |
| **specs/** | 需求定义 | ADDED/MODIFIED/REMOVED需求 |
| **design.md** | "如何" | 技术方案、架构决策 |
| **tasks.md** | 实施清单 | 带复选框的任务列表 |

**依赖关系:**
```
proposal ──► specs ──► design ──► tasks
```

这种设计让每个工件都有明确的职责,便于理解和维护。

## 最佳实践:如何高效使用OpenSpec 1.0

### 命令选择指南

| 场景 | 推荐命令 |
|--------|---------|
| 需求明确,快速推进 | `/opsx:ff` |
| 需要逐步审查调整 | `/opsx:continue` |
| 不确定需求,先探索 | `/opsx:explore` |
| 验证代码质量 | `/opsx:verify` |
| 同时处理多个变更 | `/opsx:bulk-archive` |

### 命名规范

好的变更名称能让管理更轻松:

✅ **推荐:**
```
add-dark-mode
fix-login-redirect
optimize-api-response
```

❌ **避免:**
```
feature-1
update
changes
```

### 保持变更专注

每个变更一个逻辑单元,不要把多个不相关功能混在一起。这样更容易审查、回滚和发布。

## 开始使用:15分钟快速入门

OpenSpec 1.0提供了完整的引导式教程,帮助你在15分钟内掌握核心工作流:

```bash
# 安装OpenSpec CLI
npm install -g @openspec/cli

# 初始化项目
openspec init

# 开始引导式教程
/opsx:onboard
```

`/opsx:onboard`会:
1. 分析你的代码库
2. 建议几个可行的改进点
3. 引导你完成完整的开发循环
4. 解释每一步的作用

通过实际操作,你将快速理解:
- 如何创建变更
- 工件的作用和关系
- 如何实施和验证
- 如何归档和总结
