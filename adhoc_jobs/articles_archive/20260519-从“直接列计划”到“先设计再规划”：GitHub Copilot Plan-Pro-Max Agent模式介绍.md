# 从“直接列计划”到“先设计再规划”：GitHub Copilot Plan-Pro-Max Agent 模式介绍

如果你经常让 AI 帮你做规划，大概率踩过同一个坑：它不是不会拆步骤，而是会在前提还没确认的时候，过早地把步骤拆得非常完整。上下文没摸清，关键约束没问明白，方案优劣没比较，计划已经写满一屏。问题不在“不会规划”，而在“规划启动得太早”。

我改造的这版 Plan-Pro-Max 就是冲着这个问题去的。它的核心不是把原生 Plan prompt 写得更长，而是把设计前置、把审批门前移、把回退机制补上：先确认这是不是规划问题，先比较方案，再决定要不要进入实施计划。


## 它到底改了什么

最关键的变化不是“加了更多步骤”，而是重新定义了 Plan agent 的职责边界。原生思路更像“研究一下，然后出计划”；Plan-Pro-Max 则明确改成了“先设计，后计划”。
| 维度 | 原生 Plan 倾向 | Plan-Pro-Max |
| --- | --- | --- |
| 启动方式 | 看完上下文后尽快出计划 | 先分流，先判断这是不是规划问题 |
| 澄清方式 | 可能直接开始列步骤 | 一次只问一个问题，先钉死目标、约束、成功标准 |
| 方案选择 | 容易默认第一反应 | 至少比较 2-3 个方案，并先给最强反方观点 |
| 审批机制 | 常常“没反对就继续” | 用户明确批准前，不进入实施计划 |
| 输出结构 | 直接列步骤 | 先给“已批准设计”，再给步骤、验证、决策 |
| 回退机制 | 设计变化时容易继续硬推 | 改设计就回退设计阶段，改执行细节就原地修计划 |

这里还有两个容易被忽略但很关键的点。

第一，它吸收的是同插件里 [brainstorming skill](https://github.com/iasiv5/m/blob/main/plugins/iasi/skills/brainstorming/SKILL.md) 的 design-first 方法论。简单说，`brainstorming` 负责把模糊需求收敛成设计，Plan-Pro-Max 则把这套思路直接收进一个 agent mode 里，让“先设计再规划”在一个模式里闭环完成。

第二，它没有把 VS Code 的宿主绑定层推翻重来。像 `target`、`tools`、`agents`、`handoffs`，以及 `/memories/session/plan.md` 这些与宿主直接耦合的 frontmatter 约定都被保留下来。换句话说，它改的是行为协议，不是接口契约。
## 它实际是怎么工作的

完整流程是 0 到 7：

0. 任务分流
1. 探索上下文
2. 一次一个问题地澄清
3. 方案比较
4. 分段确认设计
5. 批准门
6. 生成计划
7. 修订与回退

前 5 步负责“别太早出计划”，后 2 步负责“出对计划，并在需求变化时别假装没看见”。

步骤 6 的重点不是“终于开始列步骤”这么简单，而是把计划写成一个有来源、有验证、有决策依据的执行工件。步骤 7 也不是补丁位：它决定 agent 在用户改需求时，到底应该回退到设计阶段，还是只在执行层微调。



## 它最后输出的计划长什么样

```markdown
## 计划：{标题}

{摘要}

**已批准设计**
- 目标、推荐方案和范围边界
- 最强反方观点，以及为什么仍然推荐当前方案

**步骤**
1. ...
2. ...

**相关文件**
- ...

**验证**
1. ...

**决策**
- ...

**开放问题**
1. ...
```

这个结构的价值在于：计划不再像从天而降的任务清单，而是先把“为什么这么拆”写在前面。别人接手时，不用猜设计依据，也不用倒推验证标准。

回退机制在这里也变得具体：

- 如果用户说“不要显式批准门，直接给我计划”，这改的是设计假设，应该回退到设计阶段。
- 如果用户说“README 的同步放到最后做”，这改的是实施顺序，只需要原地修订计划。

这个区分非常重要。没有它，很多所谓的“动态规划 agent”其实只是把所有变化都当成步骤微调，最后把错的设计一路修到更复杂。
## 一个最能说明问题的 before/after 场景

这次改造 `plan-pro-max.agent.md` 本身，其实就是最好的例子。

如果按普通 Plan 的思路，agent 很容易直接进入“改 prompt、改 README、改 metadata、改 changelog”这条执行链。Plan-Pro-Max 则先把路线拆成 3 个方案：轻量增强、设计前置再计划、计划内嵌设计摘要。等“设计前置再计划”被明确批准后，才生成正式实施计划，并把同步面扩展到：

- `m/plugins/iasi/README.md`
- `m/README.md`
- `m/plugins/iasi/.github/plugin/plugin.json`
- `m/.github/plugin/marketplace.json`
- `m/plugins/iasi/CHANGELOG.md`

这就是它和普通 Plan mode 的实际差异：普通 Plan 更快开始改文件，Plan-Pro-Max 更早把边界说清楚。

## 它适合什么场景，不适合什么场景

更适合：

- 跨文件改动
- 非平凡功能设计
- 流程改造和结构重排
- 需要明确验证边界的复杂需求
- 你直觉上觉得“这事能做，但前提不稳”的任务

不适合：

- 小 bug 快修(建议使用Agent Mode)
- 单纯解释代码(建议使用Ask-Pro-Max Mode)
- 只读 review(建议使用Ask-Pro-Max Mode)
- 已经没有设计争议、只差动手实现的超小任务(建议使用Agent Mode)

## 已知局限和前提

- 它的首轮响应会比普通 Plan 慢，因为要先做澄清、方案比较和审批。
- 它依赖用户愿意参与多轮确认；如果需求方一直不给明确边界，流程会卡在设计阶段。
- 它目前把“已批准设计 + 实施计划”写入 `/memories/session/plan.md`，而不是自动回写仓库文档；这是保留和原生 plan mode的handoff机制。 （如果想要落盘，建议使用 /brainstorming + /writing-plan skill 组合技）
- 从 prompt 设计看，它没有硬绑某个模型，但这类多轮、长上下文、需要回退的工作流，会更吃模型的上下文长度和多轮稳定性。


## 一句话总结

Plan-Pro-Max 不是一个“更会写计划”的 agent，而是一个“更会先拦住错误计划”的模式。它真正解决的，不是步骤拆得够不够细，而是计划是不是建立在正确前提上。
