# GitHub Copilot handoff skill 设计详解：清醒时交接

最近这一轮 Agent 工具演进里，有一个现象越来越明显：大家一边在追求更大的上下文窗口，一边又越来越频繁地碰到同一个工程问题，长会话的续接质量开始下降。表面上看，这是上下文容量问题；再往里看，其实更像上下文治理问题。

Hermes Agent 和 Oh-My-OpenCode 最近都把 handoff 做进了工作流。这个变化值得单独拿出来讨论，因为它指向的已经不只是某个命令是否顺手，而是 Agent 正在从“能对话”走向“能交接”。

很多时候，模型并不是不会做，而是上一轮对话里真正重要的东西没有被正确带到下一跳：需求边界、前置决策、验证结果、未完成事项，全都混在一起。等到上下文开始失真，后面的每一步都会变得更贵。

## 现有两种解法，都不够

从目前的产品实践看，主流解法大致分成两类。

第一类是 Auto Compact。ctx 接近阈值，比如 90%，系统自动压缩旧对话，给后续推理腾空间。优点是无感，问题也很明显：压缩算法太黑盒。你不知道压掉了什么，也不知道保留了什么。等它真正触发时，模型往往已经没那么清醒了，这更像系统替用户兜底，而不是一次可控的上下文整理。

第二类是 subagent 隔离。把搜索、求证、局部分析分流出去，避免所有信息都堆在一个主会话里。这种方式当然有效，但也并非没有代价。很多任务需要一条连续主线，强行切成多个 agent，最后只是把“上下文问题”换成了“编排问题”。

也正因为如此，我更关注中间这一档：在系统自动救火之外，给用户一个半自动出口。趁 ctx 还健康、模型还清醒，手动触发一次 handoff，把当前会话整理成一份显式交接稿（人类可见），再开一个新 session 接着干。它保留的不是聊天记录，而是任务语义。

## handoff 和 Auto Compact，不是一回事

很多人会把 handoff 理解成手动 compact，但两者目标完全不同。

| 维度 | Auto Compact（含手动） | Handoff |
| --- | --- | --- |
| 触发方式 | 接近阈值后系统自动触发（或手动触发） | 用户明确想切到新会话时主动触发 |
| 目标 | 给当前会话腾空间 | 给下一个会话准备可直接续接的上下文 |
| 信息来源 | 模型内部压缩当前上下文 | 基于对话、todo、git、关键文件等证据整理 |
| 可见性 | 通常对用户不可见或不可控 | 结果是可读、可改、可复制的交接文档 |
| 可迁移性 | 主要服务当前会话继续推理 | 可跨会话、跨 agent，甚至跨人协作复用 |
| 代价 | 低，几乎无感 | 略高，需要一次明确的整理动作 |

如果把这件事放回实际工程里看，区别很明显：Auto Compact 解决的是“当前会话别爆”，handoff 解决的是“下一个会话别失真”。前者由系统自动触发，重点是省窗口；后者由用户主动触发，重点是保语义。前者通常不可见，后者产出的是可读、可改、可复制的交接文档，甚至可以跨会话、跨 agent 复用。

所以，Auto Compact 是内存告急时的紧急打包，handoff 是头脑清醒时的正式交接。它们不是替代关系，而是兜底和交接两种不同层面的能力。

## GitHub Copilot 版 handoff，需要把哪些原则写清楚

如果把这套思路落到 GitHub Copilot 上，我认为至少有五个设计点需要被明确下来。

第一，触发条件必须足够严格。只有用户明确要“开新 chat 接着做”时，它才应该出场。它不是普通总结，不是状态同步，也不是 changelog。

第二，必须先收证据，再写摘要。可靠的 handoff 不能只靠 agent 对对话的印象来写，而要尽量基于同会话历史、todo、git diff、git status 和必要的关键文件。handoff 的核心不是文笔，而是降幻觉。

第三，用户请求和显式约束宁可少写，也不能被 agent 擅自改写。因为一旦边界被“善意翻译”，下一会话看到的往往就是一个已经变形的需求。

第四，事实、推断和 unknowns 必须分开处理。拿不到证据就写“未知”，不要把合理猜测伪装成已验证事实。

第五，输出必须是一份可以直接启动新会话的模板。里面至少要有用户原始请求、目标、已完成工作、当前状态、待办事项、关键文件、重要决策和续接上下文。Matt Pocock 那套设计里还有一个我很认同的点：如果信息已经稳定存在于 PRD、计划、issue、commit 或 diff 里，就不要重复展开，直接引用即可。

也正因为如此，在 GitHub Copilot 版本里，我坚持把输出模板做成固定骨架，并要求整个 handoff 正文放进单个外层代码块里，方便用户直接复制。

核心结构大致长这样：
```text
交接上下文 / HANDOFF CONTEXT
用户请求（保留原话） / USER REQUESTS (AS-IS)
目标 / GOAL
已完成工作 / WORK COMPLETED
当前状态 / CURRENT STATE
待办事项 / PENDING TASKS
关键文件 / KEY FILES
重要决策 / IMPORTANT DECISIONS
显式约束 / EXPLICIT CONSTRAINTS
建议技能 / SUGGESTED SKILLS
续接上下文 / CONTEXT FOR CONTINUATION
```

这套模板看起来颇为工程化，但恰恰是这种工程化，决定了 handoff 是否真正可用。因为 handoff 的第一职责不是“写得优美”，而是“让下一次续接少走弯路”。格式稳定、层次固定、内容自包含，本质上是在给下一轮的任务启动降低成本。

## handoff 改变的，不只是记忆，而是工作流

从这个角度看，handoff 改变的并不只是记忆管理，而是整个工作流。它逼着我们把一次长会话里的隐性状态显式化：哪些结论已经定了，哪些只是临时猜想，下一步最值得去做的动作到底是什么。

一旦这一层被补上，Agent 续接就不再像碰运气，而更像工程交接。不要等模型已经开始迷糊，才把上下文整理这件事交给系统兜底；更合理的做法，是在它还清醒的时候，把交接权重新交还给用户。

很多时候限制我们的，不是模型不够强，而是我们还没有把“交接”真正做成工程能力。

如果你也经常被上下文爆掉的问题所折磨，大概会很快意识到，这不是锦上添花，而是基础设施问题。相关skill的实现，我已经开源到GitHub （https://github.com/iasiv5/m/tree/main/plugins/iasi/skills/handoff），也欢迎在评论区聊聊：你更希望 handoff 以什么形态出现？一个显式命令、一个 skill，还是一个在 ctx 到 50% 时主动提醒你的半自动入口？

## 发布摘要

这篇文章讨论了一个在 Agent 时代越来越突出的工程问题：长会话并不一定先死于容量，而往往先死于失真。围绕这个问题，文章进一步解释了为什么 Auto Compact 和 subagent 都不足以替代 handoff，以及 GitHub Copilot 为什么需要一套真正面向“下一会话续接”的 /handoff 能力。
