## 1. OpenSpec 1.0 概述

OpenSpec 是一个**规格驱动开发(SDD)**工具,强调在编写任何代码之前,让人工智能和开发者就要构建的内容达成一致。

### 1.1 核心理念

OpenSpec 1.0 基于以下核心设计原则:

- **fluid not rigid** (灵活而非僵化) - 工作流应该适应你的开发流程,而不是强制你遵循固定路径
- **iterative not waterfall** (迭代而非瀑布) - 允许在学习时随时更新工件,而不是一次性完成所有规划
- **easy not complex** (简单而非复杂) - 直观的命令和清晰的结构,降低学习曲线
- **built for brownfield not just greenfield** (适用于现有代码库) - 不仅适合新项目,也能很好地集成到现有代码库
- **scalable from personal projects to enterprises** (可扩展) - 从个人项目到企业级应用都能适用

### 1.2 1.0版本重大变更

OpenSpec 1.0 标志着从实验性到稳定版本的转变。工作流已完全重建为**基于动作的系统**,AI 能理解项目的实时状态——哪些工件存在,哪些可以创建,以及每个动作会解锁什么。

**核心架构转变:**
- 从基于阶段的线性流程转变为基于动作的灵活迭代
- AI 指令从三层动态组装(context + rules + templates)
- 语义化的规格同步机制
- 单个 `.claude/skills/` 目录替换了多个分散的配置文件

### 1.3 破坏性变更

**⚠️ 从 Pre-1.0 迁移时请注意:**

**移除的命令:**
- ❌ `/openspec:proposal` (一次性创建所有工件)
- ❌ `/openspec:apply` (实施变更)
- ❌ `/openspec:archive` (归档变更)

**移除的配置文件:**
- 工具特定文件(`CLAUDE.md`, `.cursorrules`, `AGENTS.md`, `project.md`)不再生成

**升级方法:**
运行 `openspec init` 即可完成升级。现有工作是安全的——活动更改、归档更改和主规格都保留。只有过时的配置文件会被清理(需要确认)。

## 2. 新的OPSX命令详解

OpenSpec 1.0 引入了10个新的OPSX命令,取代了旧版的3个命令。这些命令提供了更灵活、更细粒度的工作流控制。

### 2.1 /opsx:explore - 探索式思考

**用途:**
在提交更改之前,思考想法、调查问题、澄清需求。这是一个无结构要求的探索性对话,帮助你理清思路。

**语法:**
```
/opsx:explore [topic]
```

**参数:**

| 参数 | 必需 | 描述 |
|------|--------|------|
| `topic` | 否 | 你想要探索或调查的主题 |

**功能特性:**
- 开启探索性对话,无结构要求
- 调查代码库以回答问题
- 比较选项和方法
- 创建可视化图表以理清思路
- 可以在思路明确时过渡到 `/opsx:new`

**使用示例:**

```
你: /opsx:explore

AI:  What would you like to explore?

你: How should we handle authentication for mobile app?

AI:  Let me investigate your current auth setup...
     [Analyzes codebase]

     I see you're using session-based auth for web app.
     For mobile, we have three main options:

     1. JWT tokens (stateless, works offline)
     2. OAuth2 (if you need third-party login)
     3. Extend current sessions (simpler, but requires connectivity)

     Your API already has CORS configured. Which direction interests you?

你: Let's go with JWT. Can we start a change for that?

AI:  Ready when you are. Run /opsx:new add-jwt-auth to begin.
```

### 2.2 /opsx:new - 开始新更改

**用途:**
开始新更改。创建更改文件夹结构并使用选定的模式进行初始化。

**语法:**
```
/opsx:new [change-name] [--schema <schema-name>]
```

**参数:**

| 参数 | 必需 | 描述 |
|------|--------|------|
| `change-name` | 否 | 更改文件夹的名称(如果未提供则提示) |
| `--schema` | 否 | 要使用的工作流模式(默认: 来自配置或 `spec-driven`) |

**功能特性:**
- 创建 `openspec/changes/<change-name>/` 目录
- 在更改文件夹中创建 `.openspec.yaml` 元数据文件
- 显示第一个工件模板准备好创建
- 如果未提供则提示输入更改名称和模式

**使用示例:**

```
你: /opsx:new add-dark-mode

AI:  Created openspec/changes/add-dark-mode/
     Schema: spec-driven

     Ready to create: proposal
     Use /opsx:continue to create it, or /opsx:ff to create all artifacts.
```

**目录结构:**
```
openspec/
└── changes/
    └── add-dark-mode/
        └── .openspec.yaml
```

### 2.3 /opsx:continue - 增量创建工件

**用途:**
创建依赖链中的下一个工件。一次创建一个工件以实现增量进度,适合需要逐步审查和调整的工作方式。

**语法:**
```
/opsx:continue [change-name]
```

**参数:**

| 参数 | 必需 | 描述 |
|------|--------|------|
| `change-name` | 否 | 要继续的更改(如果未提供则从上下文推断) |

**功能特性:**
- 查询工件依赖图
- 显示哪些工件就绪 vs 被阻塞
- 创建第一个就绪的工件
- 读取依赖文件以获取上下文
- 显示创建后可用的内容

**使用示例:**

```
你: /opsx:continue

AI:  Change: add-dark-mode

     Artifact status:
     ✓ proposal    (done)
     ◆ specs       (ready)
     ◆ design      (ready)
     ○ tasks       (blocked - needs: specs)

     Creating specs...

     [Reads proposal.md, creates specs based on requirements]

     ✓ Created openspec/changes/add-dark-mode/specs/ui/spec.md

     Now available: tasks
     Run /opsx:continue to create next artifact.
```

### 2.4 /opsx:ff - 快进创建工件

**用途:**
快进工件创建。一次性创建所有规划工件,适合需求明确、准备快速推进的场景。

**语法:**
```
/opsx:ff [change-name]
```

**参数:**

| 参数 | 必需 | 描述 |
|------|--------|------|
| `change-name` | 否 | 要快进的更改(如果未提供则从上下文推断) |

**功能特性:**
- 按依赖顺序创建所有工件
- 通过 todo 列表跟踪进度
- 当所有 `apply-required` 工件完成时停止
- 在创建下一个工件之前读取每个依赖项

**使用示例:**

```
你: /opsx:ff add-dark-mode

AI:  Fast-forwarding add-dark-mode...

     ✓ Creating proposal.md
     ✓ Creating specs/ui/spec.md
     ✓ Creating design.md
     ✓ Creating tasks.md

     All planning artifacts complete!
     Ready for implementation. Run /opsx:apply to begin.
```

### 2.5 /opsx:apply - 实施任务

**用途:**
实现更改中的任务。逐个处理任务列表,编写代码并勾选项目。

**语法:**
```
/opsx:apply [change-name]
```

**参数:**

| 参数 | 必需 | 描述 |
|------|--------|------|
| `change-name` | 否 | 要实现的更改(如果未提供则从上下文推断) |

**功能特性:**
- 读取 `tasks.md` 并识别未完成的任务
- 逐个处理任务
- 根据需要编写代码、创建文件、运行测试
- 用复选框 `[x]` 标记任务完成

**使用示例:**

```
你: /opsx:apply

AI:  Implementing add-dark-mode...

     Reading tasks.md:
     - [ ] 1.1 Create ThemeContext
     - [ ] 1.2 Add CSS custom properties
     - [ ] 1.3 Implement localStorage persistence

     Working on 1.1: Create ThemeContext...
     [Creates src/context/ThemeContext.tsx]

     ✓ 1.1 Complete

     Working on 1.2: Add CSS custom properties...
     [Updates src/styles/globals.css]

     ✓ 1.2 Complete

     ...

     All tasks complete!
```

### 2.6 /opsx:verify - 验证实施

**用途:**
验证实现是否匹配更改工件。检查完整性、正确性和一致性,在归档前发现潜在问题。

**语法:**
```
/opsx:verify [change-name]
```

**参数:**

| 参数 | 必需 | 描述 |
|------|--------|------|
| `change-name` | 否 | 要验证的更改(如果未提供则从上下文推断) |

**功能特性:**
- 检查实现质量的三个维度
- 搜索代码库以获取实现证据
- 报告问题,分类为 CRITICAL、WARNING 或 SUGGESTION
- 不阻止归档,但会暴露问题

**验证维度:**

| 维度 | 验证内容 |
|--------|-----------|
| **Completeness** | 所有任务完成,所有需求已实现,场景已覆盖 |
| **Correctness** | 实现匹配规格意图,边缘情况已处理 |
| **Coherence** | 设计决策反映在代码中,模式一致 |

**使用示例:**

```
你: /opsx:verify

AI:  Verifying add-dark-mode...

     COMPLETENESS
     ✓ All 8 tasks in tasks.md are checked
     ✓ All requirements in specs have corresponding code
     ⚠ Scenario "System preference detection" has no test coverage

     CORRECTNESS
     ✓ Implementation matches spec intent
     ✓ Edge cases from scenarios are handled
     ✓ Error states match spec definitions

     COHERENCE
     ✓ Design decisions reflected in code structure
     ✓ Naming conventions consistent with design.md
     ⚠ Design mentions "CSS variables" but implementation uses Tailwind classes

     SUMMARY
     ─────────────────────────────
     Critical issues: 0
     Warnings: 2
     Ready to archive: Yes (with warnings)

     Recommendations:
     1. Add test for system preference detection
     2. Update design.md to reflect Tailwind usage, or refactor to use CSS variables
```

### 2.7 /opsx:sync - 同步增量规格

**用途:**
**可选命令。** 将 delta 规格从更改合并到主规格。如果需要,Archive 会提示同步,所以通常不需要手动运行。

**语法:**
```
/opsx:sync [change-name]
```

**参数:**

| 参数 | 必需 | 描述 |
|------|--------|------|
| `change-name` | 否 | 要同步的更改(如果未提供则从上下文推断) |

**功能特性:**
- 从更改文件夹读取 delta 规格
- 解析 ADDED/MODIFIED/REMOVED/RENAMED 部分
- 将更改合并到主 `openspec/specs/` 目录
- 保留 delta 中未提及的现有内容
- 不归档更改(保持活动状态)

**使用示例:**

```
你: /opsx:sync

AI:  Syncing add-dark-mode delta specs...

     Reading: openspec/changes/add-dark-mode/specs/ui/spec.md
     Target:  openspec/specs/ui/spec.md

     Changes to apply:
     ✓ ADDED: Theme Selection requirement (2 scenarios)
     ✓ ADDED: Accessibility requirement (1 scenario)

     Merging...
     ✓ openspec/specs/ui/spec.md updated

     Change remains active. Run /opsx:archive when ready to complete.
```

### 2.8 /opsx:archive - 归档更改

**用途:**
归档已完成的更改。完成更改并将其移动到归档文件夹,结束工作流循环。

**语法:**
```
/opsx:archive [change-name]
```

**参数:**

| 参数 | 必需 | 描述 |
|------|--------|------|
| `change-name` | 否 | 要归档的更改(如果未提供则从上下文推断) |

**功能特性:**
- 检查工件完成状态
- 检查任务完成(如果不完整则警告)
- 如果尚未同步,则提供同步 delta 规格
- 将更改文件夹移动到 `openspec/changes/archive/YYYY-MM-DD-<name>/`
- 保留所有工件用于审计跟踪

**使用示例:**

```
你: /opsx:archive

AI:  Archiving add-dark-mode...

     Artifact status:
     ✓ proposal.md exists
     ✓ specs/ exists
     ✓ design.md exists
     ✓ tasks.md exists (8/8 tasks complete)

     Delta specs: Not yet synced
     → Sync now? (recommended)

你: Yes

AI:  ✓ Synced specs to openspec/specs/ui/spec.md
     ✓ Moved to openspec/changes/archive/2025-01-24-add-dark-mode/

     Change archived successfully.
```

**归档目录结构:**
```
openspec/changes/archive/
└── 2025-01-24-add-dark-mode/
    ├── .openspec.yaml
    ├── proposal.md
    ├── specs/
    │   └── ui/
    │       └── spec.md
    ├── design.md
    └── tasks.md
```

### 2.9 /opsx:bulk-archive - 批量归档

**用途:**
一次归档多个已完成的更改。处理更改之间的规格冲突,适合同时处理多个变更的场景。

**语法:**
```
/opsx:bulk-archive [change-names...]
```

**参数:**

| 参数 | 必需 | 描述 |
|------|--------|------|
| `change-names` | 否 | 要归档的特定更改(如果未提供则提示选择) |

**功能特性:**
- 列出所有已完成的更改
- 归档之前验证每个更改
- 检测跨更改的规格冲突
- 通过检查实际实现来解决冲突
- 按时间顺序归档

**使用示例:**

```
你: /opsx:bulk-archive

     - add-dark-mode (8/8 tasks complete)
     - fix-login-bug (3/3 tasks complete)
     - update-footer (2/2 tasks complete)

     Checking for spec conflicts...
     ⚠ add-dark-mode and update-footer both touch specs/ui/

     Inspecting codebase to resolve...
     Both changes are implemented. Will merge in chronological order:
     1. add-dark-mode (created Jan 20)
     2. update-footer (created Jan 22)

     Archive all 3 changes?

你: Yes

AI:  ✓ Archived add-dark-mode
     ✓ Archived fix-login-bug
     ✓ Archived update-footer
     Specs merged: add-dark-mode → update-footer
```

### 2.10 /opsx:onboard - 引导式教程

**用途:**
引导式演练通过完整的 OpenSpec 工作流。使用你的实际代码库的交互式教程,帮助新用户快速上手。

**语法:**
```
/opsx:onboard
```

**功能特性:**
- 带旁白演练完整工作流循环
- 扫描代码库以查找实际改进机会
- 创建带有真实工件的实际更改
- 实施实际工作(小型、安全的更改)
- 归档已完成的更改
- 解释每个步骤

**阶段:**

1. **欢迎和代码库分析** - 介绍OpenSpec并分析你的项目
2. **找到改进机会** - 扫描代码库,提供几个可选的改进点
3. **创建更改** - 使用 `/opsx:new` 开始新变更
4. **编写提案** - 创建 `proposal.md`
5. **创建规格** - 创建增量规格
6. **编写设计** - 创建 `design.md`
7. **创建任务** - 创建 `tasks.md`
8. **实施任务** - 使用 `/opsx:apply` 实现功能
9. **验证实现** - 使用 `/opsx:verify` 检查质量
10. **归档更改** - 使用 `/opsx:archive` 完成工作流
11. **总结和后续步骤** - 总结学习内容,提供进一步学习的方向

**使用示例:**

```
你: /opsx:onboard

AI:  Welcome to OpenSpec!

     I'll walk you through complete workflow using your actual codebase.
     We'll find something small to improve, create a proper change for it,
     implement it, and archive it.

     Let me scan your codebase for opportunities...

     [Analyzes codebase]

     I found a few things we could work on:
     1. Add input validation to contact form
     2. Improve error messages in auth flow
     3. Add loading states to async buttons

     Which interests you? (or suggest something else)
```

## 3. 工作流变化

### 3.1 旧工作流 vs 新工作流对比

OpenSpec 1.0 引入了 **OPSX 工作流程**,这是一个根本性的架构重建,取代了传统的基于阶段的旧工作流程。

**旧工作流程(基于阶段,全有或全无):**

```
PLANNING ────────► IMPLEMENTING ────────► DONE
    │                    │
    │   "无法返回"      │
    └────────────────────┘
```

**问题:**
- 线性流程,一旦进入实施阶段,很难返回修改规划
- 全有或全无的方式,不够灵活
- 无法在学习过程中迭代工件

**新 OPSX 工作流程(基于动作,灵活迭代):**

```
proposal ──► specs ──► design ──► tasks ──► implement
    ▲           ▲          ▲                    │
    └───────────┴──────────┴────────────────────┘
           在学习时随时更新
```

**优势:**
- 基于动作而非阶段,任何时候都可以执行任何操作
- 支持在学习过程中更新工件
- 工件依赖关系作为指导,而不是门禁
- 更加灵活,适应真实的开发节奏

### 3.2 关键变化对比表

| 方面 | 旧工作流程 (`/openspec:*`) | OPSX 工作流程 (`/opsx:*`) |
|------|---------------------------|------------------------|
| **结构** | 一个大型提案文档 | 具有依赖关系的离散工件 |
| **工作流程** | 线性阶段: 计划 → 实施 → 归档 | 灵活的动作 - 随时执行任何操作 |
| **迭代** | 返回很困难 | 在学习时更新工件 |
| **定制** | 固定结构 | 模式驱动(定义自己的工件) |
| **AI指令** | 静态提示 | 从context + rules + templates动态组装 |

## 4. 工件结构

每个更改文件夹包含指导工作的工件,每个工件都有明确的职责:

| 工件 | 路径 | 目的 | 内容 |
|--------|------|------|------|
| **Proposal** | `proposal.md` | "为什么"和"什么" | 捕获意图、范围和方法 |
| **Specs** | `specs/` | Delta规格 | 显示 ADDED/MODIFIED/REMOVED 需求 |
| **Design** | `design.md` | "如何" | 技术方法和架构决策 |
| **Tasks** | `tasks.md` | 实现清单 | 带有复选框的任务列表 |

**完整的更改文件夹结构:**

```
openspec/changes/<change-name>/
├── .openspec.yaml       # 元数据文件
├── proposal.md           # 提案文档
├── specs/               # 增量规格
│   └── <capability>/
│       └── spec.md
├── design.md            # 设计文档
└── tasks.md             # 任务清单
```

**工件依赖关系:**

```
proposal ──► specs ──► design ──► tasks ──► implement
```

## 5. 最佳实践

### 5.1 命令选择指南

| 情况 | 使用命令 | 说明 |
|--------|---------|------|
| 需求明确,准备构建 | `/opsx:ff` | 一次性生成所有规划工件,快速进入实施阶段 |
| 探索中,想要审查每一步 | `/opsx:continue` | 逐步创建工件,每一步都可以审查和调整 |
| 想要在规范之前迭代提案 | `/opsx:continue` | 先完成proposal,再继续后续工件 |
| 时间压力,需要快速移动 | `/opsx:ff` | 快速生成所有工件,节省时间 |
| 复杂变更,想要控制 | `/opsx:continue` | 精细控制每一步,确保质量 |

**经验法则:**
如果你能预先描述完整范围,使用 `/opsx:ff`。如果你正在弄清楚需求,使用 `/opsx:continue`。

### 5.2 何时更新 vs 开始新变更

**更新现有变更当:**
- 相同的意图,精炼的执行
- 范围缩小(MVP优先,其余稍后)
- 学习驱动的纠正(代码库不是你预期的)
- 基于实施发现的设计调整

**开始新变更当:**
- 意图根本改变
- 范围爆炸到完全不同的工作
- 原始变更可以独立标记为"完成"

**决策流程:**

```
┌─────────────────────────────────────┐
│     这是相同的工作吗?          │
└──────────────┬──────────────────────┘
               │
   ┌──────────────────┼──────────────────┐
   │                  │                  │
   ▼                  ▼                  ▼
相同的意图?      >50% 重叠?      原始可以
相同的问题?     相同的范围?        在没有这些变更的情况下"完成"?
   │                  │                  │
┌────────┴────────┐  ┌──────┴──────┐   ┌───────┴───────┐
│                 │  │             │   │               │
YES               NO YES           NO  NO              YES
│                 │  │             │   │               │
▼                 ▼  ▼             ▼   ▼               ▼
更新            新 变更 更新       新 变更 更新          新
```

### 5.3 保持变更专注

每个变更一个逻辑工作单元。

**为什么重要:**
- 更容易审查和理解
- 更清晰的归档历史
- 可以独立发布
- 如有需要,简化回滚

**示例:**

❌ **不好 - 一个变更包含太多内容:**
```
add-auth-system-improvements
  - Add 2FA
  - Update password policy
  - Improve error messages
  - Add social login
  - Update session timeout
```

✅ **好 - 多个专注的变更:**
```
add-two-factor-authentication
improve-password-policy
improve-auth-error-messages
add-social-login-support
update-session-timeout
```

### 5.4 在归档前验证

使用 `/opsx:verify` 在关闭变更前捕获不匹配。

**验证的三个维度:**
1. **完整性** - 所有任务完成,所有需求实施,场景覆盖
2. **正确性** - 实施与规范意图匹配,边缘情况已处理
3. **连贯性** - 设计决策在代码中反映,模式一致

**为什么重要:**
- 在归档前发现问题,避免长期的技术债
- 确保代码和文档的一致性
- 提高代码质量和可维护性

### 5.5 清楚地命名变更

好的名称使 `openspec list` 有用。

**命名规范:**
- 使用动词开头: `add-`, `fix-`, `update-`, `improve-`, `remove-`
- 简洁描述变更内容
- 使用连字符分隔单词
- 使用小写字母

**示例:**

✅ **好的命名:**
```
add-dark-mode
fix-login-redirect
optimize-product-query
implement-2fa
update-footer-layout
```

❌ **避免的命名:**
```
feature-1          # 不明确
update              # 更新什么?
changes             # 太泛泛
wip                # 应该临时使用
bugfix              # 没有说明哪个bug
```

### 6.1 新用户入门流程

   ```
   AI:  Creating proposal...

   ```

   ```

        You now understand the core workflow:
        /opsx:new → /opsx:ff → /opsx:apply → /opsx:archive
   ```

### 6.2 项目配置

配置 OpenSpec 行为每个项目。

**配置文件位置:**
```
openspec/config.yaml
```

**示例配置:**

```yaml
# openspec/config.yaml
schema: spec-driven

context: |
  Tech stack: TypeScript, React, Node.js
  API conventions: RESTful, JSON responses
  Testing: Vitest for unit tests, Playwright for e2e
  Style: ESLint with Prettier, strict TypeScript

rules:
  proposal:
    - Include rollback plan
    - Identify affected teams
  specs:
    - Use Given/When/Then format for scenarios
  design:
    - Include sequence diagrams for complex flows
```

**配置说明:**
- `schema`: 使用的工作流模式(默认: spec-driven)
- `context`: 项目的上下文信息,AI会使用这些信息生成更相关的内容
- `rules`: 工件特定的约束和指导原则

### 6.3 自定义模式

创建自定义工作流程模式,满足特定团队的流程需求。

**创建新模式:**

```bash
# 从头开始创建新模式(交互式)
openspec schema init my-workflow

# 或分支现有模式作为起点
openspec schema fork spec-driven my-workflow

# 验证模式结构
openspec schema validate my-workflow
```

**示例 schema.yaml:**

```yaml
name: research-first
artifacts:
  - id: research
    generates: research.md
    requires: []

  - id: proposal
    generates: proposal.md
    requires: [research]

  - id: specs
    generates: specs/
    requires: [proposal]

  - id: design
    generates: design.md
    requires: [specs]

  - id: tasks
    generates: tasks.md
    requires: [design]
```

**使用自定义模式:**

```bash
# 创建更改时指定模式
/opsx:new my-change --schema research-first
```

### 6.4 增量规格格式

增量规格是OpenSpec 1.0的核心概念,使用语义标记表示变更类型。

**格式示例:**

```markdown
# Delta for Auth

## ADDED Requirements

### Requirement: Two-Factor Authentication
The system MUST require a second factor during login.

#### Scenario: OTP required
- GIVEN a user with 2FA enabled
- WHEN user submits valid credentials
- THEN an OTP challenge is presented

## MODIFIED Requirements

### Requirement: Session Timeout
The system SHALL expire sessions after 30 minutes of inactivity.
(Previously: 60 minutes)

#### Scenario: Idle timeout
- GIVEN an authenticated session
- WHEN 30 minutes pass without activity
- THEN the session is invalidated

## REMOVED Requirements

### Requirement: Remember Me
(Deprecated in favor of 2FA)
```

**归档时会发生什么:**

1. **ADDED** 需求被追加到主规格
2. **MODIFIED** 需求替换现有版本
3. **REMOVED** 需求从主规格中删除
