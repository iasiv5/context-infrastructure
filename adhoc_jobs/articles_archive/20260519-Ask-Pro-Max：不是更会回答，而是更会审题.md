# Ask Pro Max：不是更会回答，而是更会审题

## 摘要：
> Ask Pro Max 想解决的不是"回答不够长"或者"语气不够狠"，是另一个更根本的问题：很多 AI 在问答场景里太容易顺着用户的问题一路答下去，却不先检查这个问题本身是不是就带偏了。

***

前阵子看到一个很典型的case：

「这次故障大概率是配置问题吧？」

AI 很顺利接住，并开始讲配置项怎么查、常见错误有哪些、环境差异怎么排查。逻辑完整，表达清楚，看着没什么毛病。

只是最后排查下来，根因是上游服务超时，和配置没有半毛钱关系。

AI 不是不会回答。而是它从第一句话开始，就在为你提到的「大概率」做推导。

这就是我重写 Copilot Ask 模式的原因。我想给 Agent 加的，除了更好的回答能力，还有一个更关键的前置动作：回答之前，先判断这个问题值不值得按原来的思路回答。

***

## 原生 Ask 不弱，但定位不一样

原生 Ask Mode 的定位其实挺清楚：解释型 agent。

你问一个函数在干什么、一个 API 怎么用、一段代码的流程、几个模块之间怎么交互，它都能答得不错。这些问题本来就需要解释能力。

但分析型问题不一样。比如"这个判断站得住吗""这次故障更可能坏在哪""这个设计合理吗""这个 PR 真的没问题吗"——这些需要的不是先解释，而是先审查。

原生 Ask 更像解释器，Ask Pro Max 更像分析器。

***

## Ask Pro Max 补了什么？

我把这个能力拆成三层。不是什么经典框架，只是我自己用下来觉得缺的东西。

**第一层：问题审查**

先拆事实、假设和未知，别直接把用户的输入当做前提。

因为用户的一句话里经常会混三种东西：已确认的事实、个人的推测、还有隐含的结论方向。大多数 AI 会把它当一整块直接回答。

Ask Pro Max 会先拆一下，比如：

```
用户提问：
"这个接口变慢，是不是数据库的问题？"

拆解：
- 已确认：接口响应变慢（需要确认范围和时间）
- 推测：根因是数据库（目前只是候选）
- 未知：是否只影响特定接口，是否伴随缓存 miss / 上游超时

建议的下一步：
1. 看接口级监控，确认影响范围
2. 对照数据库 / 上游 / 缓存时延
3. 若仅单接口，优先回溯最近代码改动
```

这一步看着只是更谨慎。但很多问题不是到第十步才歪的，是第一句话就歪了。

**第二层：对抗验证**

找出最可信的反方观点，分析完再决定结论还站不站得住。

很多所谓"分析"其实就是把第一反应讲得更加完整。Ask Pro Max 会强迫自己先做一件“反人性”的事情——找反例。

```
用户提问：
"这个 PR 应该没问题吧？"

先不给结论。找反面：
- 如果改了共用函数，影响面可能比 diff 大
- 可读 ≠ 行为兼容，隐式依赖最容易漏
- 没覆盖关键分支，无法证明安全

当前判断：
没看到明显致命问题。但"可以继续审" ≠ "已经没问题"。
置信度：中等
原因：只有 diff，没有测试和运行证据
```

重点不在挑刺。是避免把"看起来合理"说成"已经成立"。

**第三层：换结构回答**

解释型问题、判断型问题、调试问题，需要的答案形状不一样。Ask Pro Max 会切换回答结构，而不是统一用一种"解释口吻"处理。

```
用户提问：
"为什么 CI 偶发失败？"

最可能的解释：
- 某个依赖或测试存在 flakiness

其他说得通的解释：
- runner 资源争用
- 外部服务波动
- 并行或缓存策略变化

建议的下一步：
1. 是否集中在同一个 test / job
2. 是否与外部依赖异常时间重叠
3. 再看 runner / cache

置信度：中等
原因：'偶发'更像分布噪声，不像稳定缺陷
```

先拆问题，找反面，最后再给答案。

## 不是更凶的 prompt，是更清晰的规则

很多人看过 Ask Pro Max 的定义文件后，以为我只是塞了一段更狠的 prompt。

我确实也参考过一些类似的指令，比如：
> "不要先赞同我，如果我错了直接指出来。"
> "不要只依赖我提供的信息，要自己独立判断。"
但只是加这种程度的指令，拿到的一般是一个语气更冲的 AI，不是我想要的效果。

所以，我把"态度"翻译成了"规则"。Ask Pro Max 落地的其实是这几条硬约束：

- 不迎合用户
- 不把猜测说成事实
- 先给最强反方
- 不知道就承认不知道
- 结论带置信度（high、medium、low 或 unknown）

好的 prompt 不需要更强势，只需要更少歧义。

***

## 判断力不等于攻击性

"更有判断力"容易被理解成"更冲"。但这两件事没关系。

我在 Ask Pro Max 里做了两种风格的分流。默认是平衡风——直接、清晰、克制。用户明确要求锐评的时候，才切到锋利模式。

该拆前提的时候敢拆，该收结论的时候收得住，这才是重点。语气不是。

***

## 什么时候用哪个 Mode？

信息型问题可以用 Ask，判断型问题用 Ask Pro Max。

| 场景 | Ask | Ask Pro Max |
| --- | --- | --- |
| 查定义 / API / 控制流 | ✅ | ❌ |
| 设计评估 | ❌ | ✅ |
| 故障排查 | ❌ | ✅ |
| PR review | ⚠️ | ✅ |
| 快速拿个答案 | ✅ | ❌ |

两者有个共同点：都是只读模式，不动代码。
Ask Pro Max 在大部分场景其实都有更优表现。
