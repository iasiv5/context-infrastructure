# 从行为反推 Harness 应该如何构建

很多人设计 Agent，习惯先考虑“我要接什么工具”：是 RAG、MCP，还是 Sandbox 和 Hooks？这个顺序往往是本末倒置的。真正有效的做法是：先定义你希望模型稳定表现出的行为，再反推需要什么 Harness（驾驭层）去补齐模型单靠自己做不到的部分。
这也就是 Viv Trivedy 提到的核心设计模式（Working backwards from behaviour）：

> behaviour we want (or want to fix) 
-> harness design to help the model achieve this
Harness 就像是一座座跨越鸿沟的“桥”。大模型自己过不去的坎，完不成的事情，Harness 帮它搭桥过去：

- **缺乏持久化状态？** 文件系统和 Git 就是那座桥，让它拥有真实的工作区。
- **光说不练假把式？** Bash 和代码执行环境就是那座桥，让它能真正写代码并运行。
- **操作环境不安全？** Sandbox（沙箱）就是那座桥，保证执行时的绝对安全。
- **缺乏最新知识？** Web Search 和 MCP 就是那座桥，补上训练截止后的数据。
- **记不住执行纪律？** Hooks 和 Tests 拦截系统就是那座桥，把“记得检查”变成“系统强制检查”。

这句话真正厉害的地方，在于它把 Harness 从毫无头绪的“功能清单”变成了有的放矢的**行为补偿系统**。用这个视角看，判断一个组件值不值得加，标准就很简单：如果你说不清它具体在保障哪种行为，它大概率就不该存在。

所以，设计 Agent 最重要的问题从来不是“还能接什么新技术”，而是“我希望它稳定做对什么，而模型为什么做不到”。

先定义行为，再设计桥，这才是最专业、也最省力的路径。
