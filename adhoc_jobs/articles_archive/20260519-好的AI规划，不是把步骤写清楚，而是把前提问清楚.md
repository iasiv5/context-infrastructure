# 我重写了 Copilot 的 Plan 模式，只为拦住那些“看起来很对”的错计划

> AI 规划最常见的失败，不是步骤不够细，而是前提没问清。Plan-Pro-Max 想做的，不是让 AI 更会写计划，而是先拦住那些建立在错误前提上的计划。

---

很多人对 AI 规划有一个误解。

以为它会拆步骤，就等于它会做规划。

其实不是。

AI 最容易翻车的地方，往往发生在第一步之前。

目标没钉死。  
约束没问清。  
成功标准没确认。  
它已经开始拆 1、2、3、4 了。

这就是我重做 GitHub Copilot 里 Plan 模式的原因。

我想解决的，不是“它写计划还不够漂亮”。

我想解决的是另一件更麻烦的事：

> 它太容易在前提没确认时，就开始规划。

所以这版我给它起名叫 Plan-Pro-Max。

一句话概括，就是：

> 先设计，再规划。

## 它到底改了什么？

这次改的核心，不是加更多步骤，不是堆更多规则，也不是把 prompt 写得更长。

真正变的是一件事：

**Plan agent 的职责边界，被我重写了。**

原生 Plan 更像这样：

> 看上下文，想一会儿，然后尽快给计划。

Plan-Pro-Max 则是另一种逻辑：

> 先证明设计成立，再允许计划出现。

差异可以直接看表：

| 维度 | 原生 Plan 倾向 | Plan-Pro-Max |
| --- | --- | --- |
| 启动方式 | 看完上下文尽快出计划 | 先分流，先判断这是不是规划问题 |
| 澄清方式 | 容易直接列步骤 | 一次只问一个问题，先钉死目标、约束、成功标准 |
| 方案选择 | 默认第一反应 | 至少比较 2-3 个方案，并给出最强反方观点 |
| 审批机制 | 没反对就继续 | 用户明确批准前，不生成实施计划 |
| 输出结构 | 直接列步骤 | 先写已批准设计，再写执行步骤 |
| 回退机制 | 变化时继续硬推 | 改设计就回退，改执行才微调 |

如果要把这张表压缩成一句话，那就是：

> 我把“刹车”，装在了“计划”前面。

很多 AI 不是不会规划，而是太急着规划。

## 这不是换个说法，而是换了工作流

很多“升级版 prompt”，本质上只是把同一套东西讲得更复杂。

Plan-Pro-Max 不是。

它至少改了两层。

第一层，它把同插件里 [brainstorming skill](https://github.com/iasiv5/m/blob/main/plugins/iasi/skills/brainstorming/SKILL.md) 的 design-first 方法论直接收进了 agent mode。

也就是说，它不是在计划阶段补几句澄清，而是从机制上要求：先把模糊需求收敛成设计，再决定要不要展开执行计划。

第二层，它没有把宿主契约整套推翻。

像 target、tools、agents、handoffs，以及把结果写入 /memories/session/plan.md 这些和 VS Code 宿主绑定的约定，都还在。

换句话说，它改的是行为协议，不是接口契约。

这点很关键。

因为真正难的，从来不是把流程说得更漂亮，而是让 agent 变聪明的同时，不把现有挂载方式全部打碎。

## 它到底怎么工作？

完整流程是 0 到 7：
```text
0. 任务分流
1. 探索上下文
2. 一次一个问题地澄清
3. 方案比较
4. 分段确认设计
5. 批准门
6. 生成计划
7. 修订与回退
```

你也可以把它粗暴理解成一句话：

> 前 5 步踩刹车，后 2 步才给油门。

真正值钱的，不是它会不会往后写，而是它知不知道什么时候该停住。

### 1. 不是所有问题，都值得进 planning

第一步不是提问，而是分流。

如果用户本质上是在问实现、修小 bug、读代码、做只读 review，那就不该硬套 planning 流程。

很多 agent 表现差，不是能力不够，而是模式一开始就选错了。

### 2. 一次一个问题，把前提钉死

我一直不喜欢那种一口气甩 5 个澄清问题的做法。

看起来勤奋，实际很虚。

Plan-Pro-Max 的做法更笨一点，也更稳一点：

- 先确认目标
- 再确认约束
- 最后确认成功标准

一次只推进一个关键前提。

因为计划翻车，很多时候不是步骤少了，而是问题问少了。

### 3. 不许把“第一反应”直接当答案

Plan-Pro-Max 不允许一上来就推荐唯一解。

它会先摆出 2 到 3 个可行方案。

更重要的是，它会先说出最强反方观点。

这个设计背后的逻辑其实很简单：

> 如果它说不清为什么不选别的方案，它大概率也没资格自信地推荐当前方案。

这一步会慢一点，但能过滤掉大量“看起来很顺，其实没比较”的假思考。

### 4. 没有明确批准，就不生成实施计划

这是我最看重的一道门。

不是“你没反对，我就继续”。

而是：

> 用户明确批准前，不生成实施计划。

这一步的意义，不是流程感，而是把那些“前提还没定、计划却已经写满一屏”的错觉，直接挡在门外。

## 它给你的，不再只是一个任务清单

传统计划最大的问题，是太像待办列表。

你看得到步骤，但看不到为什么这样拆。

Plan-Pro-Max 最终给出的计划，大概长这样：
```markdown
## 计划：{标题}

{摘要}

**已批准设计**
- 目标、推荐方案、范围边界
- 最强反方观点，以及为什么仍然推荐当前方案

**步骤**
1. ...
2. ...

**相关文件**
- ...

**验证**
1. ...

**决策**
- ...

**开放问题**
1. ...
```

这个结构最有价值的地方，不是更完整，而是它先写“为什么这么做”，再写“怎么做”。

这意味着别人接手时，不需要倒推设计依据，也不用猜验证边界。

## 最容易被忽略，也最不能缺的，是回退机制

很多所谓“动态规划 agent”的问题，不是不会修步骤，而是用户一改需求，它根本不知道自己该回哪一层。

Plan-Pro-Max 的判断原则只有一条：

> 用户改的是设计前提，还是执行路径？

比如：

- “不要显式批准门，直接给我计划。” 这改的是设计假设，要回退到设计阶段。
- “README 的同步放到最后做。” 这改的是实施顺序，只需要原地修计划。

别小看这个区分。没有它，agent 往往会把所有变化都当成“步骤微调”。

最后就会出现一种特别典型的失败：

> 错的设计，被一步步修得越来越复杂。

## 一个最能说明问题的 before / after

这次改造 plan-pro-max.agent.md 本身，就是最好的例子。

如果按普通 Plan 的路径走，事情通常会很快滑进这条链路：
```text
改 prompt
→ 改 README
→ 改 metadata
→ 改 changelog
```

看上去推进很快，但只要前面的设计偏一点，后面每一步都在放大返工成本。

Plan-Pro-Max 的路径不一样。

它先摆出 3 个方案：

- 轻量增强
- 设计前置再计划
- 计划内嵌设计摘要

等“设计前置再计划”被明确批准后，才会生成正式实施计划。

这时，影响面才会被清晰展开到：
```text
m/plugins/iasi/README.md
m/README.md
m/plugins/iasi/.github/plugin/plugin.json
m/.github/plugin/marketplace.json
m/plugins/iasi/CHANGELOG.md
```

差别其实就一句：

> 普通 Plan 更早开始改文件，Plan-Pro-Max 更早把边界讲清楚。

## 它适合什么场景，不适合什么场景？

更适合它的，是这些任务：

- 跨文件改动
- 非平凡功能设计
- 流程重构和行为改造
- 需要明确验证边界的复杂需求
- 那种“看起来能做，但你直觉上觉得前提不稳”的任务

不太适合它的，是这些任务：

- 小 bug 快修
- 单纯解释代码
- 只读 review
- 已经没有设计争议、只差执行的超小任务

说得再直一点：

> 风险在“前提不稳”，就用 Plan-Pro-Max。风险在“赶紧动手”，就别把规划模式开太重。

## 代价也很真实

Plan-Pro-Max 不是银弹。

它买来的不是更快，而是更稳。

所以它一定会付出代价：

- 首轮响应更慢，因为要先澄清、比较、审批
- 强依赖用户参与确认，边界不给清，流程就会卡住
- 默认写入 /memories/session/plan.md，不会自动回写仓库文档
- 更吃模型的上下文长度和多轮稳定性

如果任务本来就很小，这种稳未必划算。

但只要任务一复杂，这种稳就会开始变得很值钱。

## 一句话总结

Plan-Pro-Max 不是一个“更会写计划”的 agent。

它是一个**更会拦住错误计划的模式**。

它真正解决的，不是步骤够不够细。

而是：

> 这份计划，究竟是不是建立在正确前提上。

如果你也经常遇到那种“计划越写越完整，方向却越走越歪”的情况，那你真正缺的，可能不是更多步骤，而是**更可靠的前提**。
