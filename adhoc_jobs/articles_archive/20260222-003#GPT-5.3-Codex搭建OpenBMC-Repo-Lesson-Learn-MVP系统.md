# GPT-5.3-Codex搭建OpenBMC Repo Lesson Learn（MVP）系统

**导读**：从一次 U-Boot 编译报错，到一套可复用的团队知识管理系统——记录 GitHub Copilot 如何帮我完成从"修 Bug"到"建系统"的完整过程。

---

## 一、问题起源：U-Boot.bin 超限报错

事情要从几天前说起。

在[《新增IASI-2700 OpenBMC Machine的踩坑记录》](前天公众号文章链接)中，我分享了为 KIMI K2.5 添加新机器配置的折腾过程。当时遇到一个编译错误：

```
ERROR: obmc-phosphor-image-1.0-r0 do_generate_static:
Image '/home/iasi/workspace/openbmc/build/iasi-2700/tmp/deploy/images/iasi-2700/u-boot.bin'
is 485424 bytes too large!
```

**U-Boot.bin 大小超限**。

这个报错看起来简单，实际排查起来却卡了两天。用 TRAE.CN + GLM-5 尝试自动修复，模型虽然定位到了"U-Boot 配置被覆盖"的大致方向，但始终给不出正确的解法——一直在那儿"转圈圈"。

切换到 **GitHub Copilot 的 GPT-5.3-Codex** 后，情况完全不同。

把 bitbake 报错信息直接贴给 LLM，**一次性解决**。代码改动非常克制，具体变动见这条 Commit：

🔗 [https://github.com/iasiv5/openbmc/commit/8eae173dd9412b34497f0c3c94ceba88bed31971](https://github.com/iasiv5/openbmc/commit/8eae173dd9412b34497f0c3c94ceba88bed31971)

---

## 二、意外发现：Copilot 的"经验内存"机制

Bug 修好了，但真正引起我注意的，是 Copilot 在修复过程中自动创建的一个文件：

📄 `openbmc-include-collison.md`

这是一个**经验内存文档**，记录了刚才修复 Bug 的 lesson learn。

我立刻追问 Agent 几个问题：

| 问题 | 答案 |
|------|------|
| 文件保存在哪？ | 虚拟路径 `/memories/repo/...`，不属于工作区，无法直接链接 |
| 何时生成？如何生效？ | 即时创建，跨会话保存上下文；首 200 行自动加载至后续会话 |
| 版本管理？ | 未纳入 Git，不影响构建流程 |

这个机制让我眼前一亮：**AI 在帮我把"踩过的坑"记下来**。

---

## 三、从"个人记忆"到"团队资产"

但这里有个问题——这个记忆文件存在 Agent 的虚拟空间里，**只有我自己能用**。

如果团队其他成员遇到同样的问题，他们享受不到这份经验。新人入职，还是得从零开始踩一遍坑。

这让我想到一个长期想做的工程：**把经验教训真正沉淀到 Git 仓库中**。

于是打开 GitHub Copilot Plan 模式，提出了具体需求：

> 设计并实现一个将 Lesson Learn 整合到 Git 仓库的系统方案：
> 1. 结构化管理机制，渐进式披露
> 2. 经验教训清单，优化元数据与检索
> 3. AGENTS.md 作为全局提示词注入点
> 4. 无缝集成 Git 工作流
> 5. 清晰的使用指南和维护规范
> 6. 元数据标准化，支持搜索/分类/版本控制
> 7. 权限控制，敏感经验适当隔离

---

## 四、MVP 设计：先做减法，快速落地

进入 Plan Mode 的 Ask User Question 环节，我刻意做了简化：

| 决策项 | MVP 选择 | 理由 |
|--------|----------|------|
| 落地范围 | meta-iasi layer | 先验证，再推广 |
| 评审流程 | 直接提交，跳过 Gerrit | 降低初期摩擦 |
| 敏感分级 | 只分级不分仓 | 开源仓库，简化设计 |
| 质量校验 | 自动检查 | 经验质量从"娃娃"抓起 |
| 文档位置 | AGENTS.md 放仓库根目录 | 全局生效，不递归 |

Agent 评估完可行性和风险后，直接 **Start implementation**。
