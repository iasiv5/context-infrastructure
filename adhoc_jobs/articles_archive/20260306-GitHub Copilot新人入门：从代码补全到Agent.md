# GitHub Copilot新人入门：从代码补全到Agent

很多开发者第一次装上 GitHub Copilot，最先记住的能力往往只有一个：代码补全。

它确实好用。写循环、补样板、续几行熟悉逻辑，顺手、直接、立竿见影。但问题也恰恰出在这里。很多人从此就把 Copilot 固定成了一个“更聪明的补全插件”，结果装了很久，真正用出来的能力却只是一小部分。

于是就出现了一个很常见的现象：有人觉得 Copilot 越用越顺手，有人却觉得“也就那样”。差别通常不在于谁的提示词更花哨，而在于谁有没有弄清楚 GitHub Copilot 最新这套交互到底是怎么分层的。

如果按现在新版 GitHub Copilot 的实际形态来看，代码补全是一层；而补全之外的核心交互，基本都已经收进了 Agent Mode 里。在 Agent Mode 下面，你再去选择 Ask、Plan、Agent 这三种不同的工作方式。

会补全，不等于会用 Copilot；真正的分水岭，是你会不会在 Agent Mode 里选对工作方式。

## 一、先别急着谈技巧，先把 GitHub Copilot 的两层结构分清楚

如果用现在这版 GitHub Copilot 的实际界面来概括，它更像是“两层结构”：

- 第一层，是代码补全。
- 第二层，是 Agent Mode。

代码补全负责“写代码时的即时续写和建议”。

Agent Mode 则负责“补全之外的大部分交互任务”。而进入 Agent Mode 之后，你再根据任务性质，选择 Ask、Plan、Agent 这三种不同方式。

也就是说，现在更准确的理解方式不是“我要用 Chat 还是 Agent”，而是“除了补全之外，我进入 Agent Mode 以后，这件事更适合 Ask、Plan，还是 Agent”。

补全最适合已经知道要写什么、只想提高输入效率的场景。比如补一个循环、补一个熟悉 API 的调用框架、补一段常规数据处理。这类任务的特点是边界清晰、目标明确，越轻量的入口越高效。

而 Agent Mode 里这三种方式，则分别对应三件不同的事：

- Ask：先问、先理解、先澄清。
- Plan：先拆解、先定义步骤、先对齐边界。
- Agent：直接开始执行、修改、验证和推进任务。

简单改动先别急着上重模式，才能保持高效率。

## 二、很多人用不好 Copilot，不是不会提问，而是没看懂 Agent Mode 里的分工

日常开发里，最容易犯的错误不是“不会写提示词”，而是把 Agent Mode 里的 Ask、Plan、Agent 当成一回事。

一句话续写，明明补全最快，却非要切进 Agent Mode 反复对话；本来只是想理解一段代码，却直接开 Agent 去跨文件改动；任务边界还没想清楚，就跳过 Plan 直接进入执行。这些用法看起来都在“充分使用功能”，实际上却在不断抬高协作成本。

你可以用一个更符合现状的判断方式做第一轮筛选：

- 只是一小段代码续写，**优先补全**。
- 需要理解、提问、解释、对比，**进 Agent Mode 后优先 Ask**。
- 需要先把需求拆开、把步骤列清、把边界讲透，**进 Agent Mode 后优先 Plan**。
- 需要真正修改文件、跑命令、根据结果继续推进，**进 Agent Mode 后再用 Agent**。

如果把这套逻辑理解清楚，那么补全负责“快写出来”，Ask 负责“先问明白”，Plan 负责“先想清楚”，Agent 负责“真正做下去”。这层关系一旦想清楚，后面很多判断都会自然顺下来。

## 三、先把 Ask 用顺手，再谈 Plan 和 Agent

很多人一开始就想测试 Copilot “到底有多强”，于是直接拿一个复杂需求去试。结果不是中途失控，就是因为预期过高而产生挫败感。

更稳的方式，是先把 Agent Mode 里最轻的一档用顺手，也就是 Ask。

Ask 最适合的，往往是这些低风险、高回报的任务：

- 解释一段你没看懂的代码。
- 重写一个函数，让逻辑更清晰。
- 给出测试点、边界条件和断言思路。
- 分析一条报错，先判断它属于语法、依赖、运行时还是业务逻辑问题。
- 比较两种写法或两种方案的取舍。

这一阶段最重要的，不是“马上执行”，而是“**先把问题问明白、讲明白、收束明白**”。

很多人以前会把这类任务理解成“聊天能力”，但在现在这版 GitHub Copilot 的实际界面里，更准确地说，这是 Agent Mode 里的 Ask 在承担的工作。

## 四、稍微复杂一点的任务，别急着执行，先切到 Plan

这是我最建议新人尽早建立的习惯。

稍微复杂一点的任务，先用 Plan Mode 把需求聊清楚，再切 Agent Mode 开始写代码。原因并不复杂：复杂任务最容易出问题的地方，往往不是“不会写”，而是“一开始就没定义清楚到底要写什么”。

很多返工，看起来发生在执行阶段，根子其实都埋在计划阶段。你一开始说得含糊，后面即使 AI 写得很勤快，也只是更快地偏离目标。

什么时候该先开 Plan？通常有这几种信号：

- 需求本身还有歧义。
- 你知道要改很多地方，但还没想清顺序。
- 任务里隐含了验收标准、边界条件或潜在风险。
- 你担心直接开改会引发较大返工。

在 Plan Mode 里，真正值得聊清楚的，不是“先写哪一行代码”，而是这些问题：**目标是什么、会影响哪些模块、哪些地方需要先确认、最后以什么标准算完成**。

需求越模糊，越别急着写；先把问题定义清楚，后面的速度才有意义。

## 五、真正动手的时候，再把 Agent 打开

当一个任务已经完成了 Ask 的澄清，也经过了 Plan 的拆解，并且同时满足“多步骤、跨文件、需要验证结果”这几个条件时，Agent 这档执行模式的价值才会真正体现出来。

它适合的，不是“帮我补一个函数”，而是“围绕一个明确目标，把整条执行链推进下去”。这包括理解上下文、修改文件、运行命令、根据报错继续修复、最后把结果收束到可审阅状态。

也正因为如此，Agent 的效果从来不只是模型问题，还取决于前面的 Ask 和 Plan 是否做扎实，目标是否清晰、边界是否明确、验收是否可判断。

适合交给 Agent 的任务，通常长这样：

- 给现有模块补一个小功能，并完成相关联修改。
- 修一组彼此相关的测试，而不是只修一条报错。
- 做一次中等规模重构，并验证是否引入回归。
- 围绕一个明确目标推进一条带执行反馈的任务链。

不适合直接开 Agent 的任务，也同样明显：

- 只改一两行代码。
- 需求本身还没想清楚。
- 你自己都说不清验收标准。
- 你根本不准备检查结果。

不是所有任务都值得自动化，边界清楚、步骤想清、目标讲明的任务，才适合交给 Agent。

## 六、想让 Ask、Plan、Agent 都更靠谱，先把上下文补够

很多人抱怨 Copilot “不够懂项目”，但问题往往并不在模型，而在上下文没有给够。

AI 并不会天然知道你们团队的目录习惯、命名偏好、技术栈约束和工程边界。如果这些信息没有被明确提供，它就只能用通用经验来猜。

一个更稳的做法，是按由浅到深的顺序逐步补上下文：

第一步，先给项目规则。用 copilot-instructions.md 或者 AGENTS.md 文件，把项目约定、编码规范、目录结构偏好讲清楚。

第二步，再补专门能力。如果你经常重复做某类任务，可以考虑用 agent skills 或定制代理把经验沉淀下来。

第三步，最后再接外部工具。确实需要访问 API、数据源或专用工具时，再考虑 MCP。它很强，但也带来更高的配置和学习成本。

想让 AI 更像队友，先给它上下文，再期待它给你结果。无论你现在用的是 Ask、Plan 还是 Agent，这条都成立。

## 七、别只顾着好用，版本、权限、隐私这些边界要先看明白

很多“Copilot 不好用”的抱怨，最后查出来都不是能力问题，而是环境问题。

正式开始之前，至少先确认四件事：

- 订阅或权限是否真的开通。
- VS Code 和 Copilot Chat 是否是最新可用版本。
- 你是否知道自己正在使用预览能力。
- 你是否清楚隐私条款与遥测设置。

特别是在团队或企业环境里，权限开通、数据合规、遥测策略都不应该被放到最后再考虑。真正成熟的使用方式，从来不是“先跑起来再说”，而是把可用性和可控性一起看。

## 八、一条更符合现状的 7 天上手路径

如果你不想一下子学太多，最稳的方式不是猛冲，而是按节奏推进。

第 1 到 2 天，只用补全和 Ask。目标不是马上提多少效率，而是先熟悉“描述问题”和“收束需求”这件事。

第 3 到 4 天，继续用 Ask 做解释、改写、测试辅助和报错分析。重点是体会“提问和澄清”比单纯补全多了什么。

第 5 到 6 天，挑一个小型多文件任务，先用 Plan 把需求、步骤和验收标准聊清楚，再交给 Agent 实施。

第 7 天，补一条项目级 custom instructions，观察加了项目上下文之后，Ask 的回答、Plan 的拆解和 Agent 的执行贴合度有没有明显变化。

先学会提问，再学会规划，最后才是把任务自动推进下去。

## 写在最后

对新人来说，GitHub Copilot 最值得尽早建立的，不是某个零散技巧，而是一套清晰的协作节奏：

简单续写，交给补全；需要理解，先用 Ask；任务变复杂，切到 Plan；真正动手时，再开 Agent；无论哪种模式，最后都要检查结果。

这套节奏越早内化，你就越不容易在 AI 工具变得更强大的时候，被“什么都能做”这件事反过来拖累。

工具会越来越强，但判断力不会自动变强。真正高效的开发者，不是把所有功能都用一遍的人，而是永远知道此刻该用哪一档、为什么用这一档的人。

GitHub Copilot 给了你更多选择，但选择本身，从来都是你的责任。
