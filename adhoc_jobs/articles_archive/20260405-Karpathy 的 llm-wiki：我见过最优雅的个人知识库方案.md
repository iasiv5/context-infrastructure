Karpathy 的 llm-wiki：我见过最优雅的个人知识库方案
前几天刷 GitHub，看到 Karpathy 发了一个 Gist，标题很简洁——"llm-wiki"。点进去一看，我直接愣住了。
不是因为它有多复杂，恰恰相反——是因为它用一个极其朴素的想法，解决了一个困扰我很久的问题：
个人知识库到底该怎么维护
？
用过 Notion、Obsidian、Logseq 的人都知道，建立一个知识库很容易，但维护它简直是灾难。笔记越积越多，交叉引用永远来不及更新，矛盾的观点没人标注，最后整个库变成一个没人想碰的垃圾场。
Karpathy 的这个方案，给了我一个完全不同的思路。
核心洞察：RAG 是错的（至少对个人知识库来说）
我们目前处理"LLM + 文档"的主流方案是 RAG——上传一堆文件，每次提问时 LLM 检索相关片段，然后基于这些片段生成答案。NotebookLM、ChatGPT 文件上传、大部分 RAG 系统都是这个套路。
Karpathy 指出了这个方案的根本问题：
LLM 每次都在从零开始"重新发现"知识
。
你问一个需要综合五篇文档的复杂问题，LLM 得找到这五个片段、拼凑它们、建立关联，然后才能回答。而且下次再问一个相关的问题，它又得重来一遍。没有任何积累。
这不是知识库，这是
一次性搜索引擎
。
Karpathy 的方案完全不同：不要在查询时才去原始文档里捞信息，而是让 LLM 
持续地、渐进地构建和维护一个 wiki
——一个结构化的、互相链接的 markdown 文件集合，位于你和原始文档之间。
每当你添加一个新的资料源，LLM 不是简单地索引它等以后检索，而是读取它、提取关键信息、整合进现有 wiki——更新实体页面、修订主题摘要、标注新旧数据的矛盾、加强或挑战已有的综合分析。
知识只编译一次，然后
持续保持更新
。
这句话是整个方案的核心
：The wiki is a persistent, compounding artifact.
 交叉引用已经建好了，矛盾已经标注了，综合分析已经反映了你读过的所有东西。每添加一个新资料源、每问一个问题，wiki 都在变得更丰富。
说实话，看到这里我已经被说服了。
三层架构：极其清晰的分层设计
Karpathy 给出的架构只有三层，但每一层的职责划分非常精准。
第一层：Raw Sources（原始资料
）
你精心收集的原始文档——文章、论文、图片、数据文件。这些文件是
不可变的
，LLM 只读取不修改。这是你的"真相之源"。
第二层：The Wiki（知识库本体
）
LLM 生成的 markdown 文件目录。摘要页、实体页、概念页、对比分析、概览、综合论述——全部由 LLM 创建和维护。LLM 拥有这一层的完整控制权，你只负责阅读。
Karpathy 描述了一个很有画面感的工作场景：一边开着 LLM Agent，一边开着 Obsidian。LLM 根据对话做编辑，你在 Obsidian 里实时浏览结果——跟链接、查图谱视图、读更新后的页面。
Obsidian 是 IDE，LLM 是程序员，wiki 是代码库
。
这个比喻太精准了。
第三层：The Schema（模式定义
）
一个配置文件（用 Claude Code 就是 
CLAUDE.md
，用 Codex 就是 
AGENTS.md
），告诉 LLM 这个 wiki 的结构规范、命名约定，以及在做资料摄取、回答问题或维护 wiki 时该遵循什么工作流。
这个文件是关键——它把 LLM 从一个通用聊天机器人变成了一个
训练有素的 wiki 维护者
。你和 LLM 随着时间共同迭代这个配置，找到适合你领域的最佳实践。
三个操作：Ingest、Query、Lint
整个系统只有三个核心操作，但每个都经过深思熟虑。
Ingest（摄取）
你往原始资料库丢一个新文档，告诉 LLM 处理它。一个典型的流程是这样的：LLM 读取文档、跟你讨论关键发现、在 wiki 里写一个摘要页、更新索引、更新整个 wiki 中相关的实体和概念页面、在日志里追加一条记录。
一个资料源可能会触碰 10-15 个 wiki 页面
。
这个数字很关键。它说明这个过程不是简单的"存一下"，而是真正的
知识整合
——新信息被编织进已有的知识网络。
Karpathy 个人偏好逐个摄取资料源，并且保持参与——读摘要、检查更新、引导 LLM 关注什么。但也可以批量处理，取决于你的风格。
Query（查询）
你对着 wiki 提问。LLM 搜索相关页面、阅读它们、综合出带引用的答案。答案的形式可以多种多样——markdown 页面、对比表格、幻灯片（Marp）、图表（matplotlib）。
但这里有一个关键洞察
：好的答案可以被保存回 wiki 作为新页面。
一次你要求的对比分析、一段深入的分析、一个你发现的关联——这些都是有价值的，不应该消失在聊天历史里。通过这种方式，你的探索和摄取一样能在知识库中
持续复利
。
Lint（维护检查）
定期让 LLM 对 wiki 做一次健康检查：页面之间有没有矛盾？有没有被新资料源取代的过时论断？有没有没有入站链接的孤立页面？有没有重要概念被提到但没有自己的页面？有没有缺失的交叉引用？有没有可以通过网络搜索填补的数据空白？
这个设计让知识库
不会随着规模增长而腐化
——这在传统个人 wiki 方案里是无解的难题。
两个关键文件：index.md 和 log.md
除了三层架构和三个操作，还有两个特殊的文件帮助 LLM 和你自己导航 wiki。
index.md
 是内容导向的目录——wiki 里每个页面的链接、一行摘要、可选的元数据（日期、资料源数量）。按类别组织（实体、概念、资料源等）。LLM 在每次摄取时更新它。回答查询时，LLM 先读 index 找到相关页面，再深入阅读。Karpathy 说这个方法在中等规模（约 100 个资料源、几百个页面）下工作得
出奇地好
，完全不需要基于向量嵌入的 RAG 基础设施。
log.md
 是按时间排列的日志——摄取、查询、维护检查的记录。每个条目用一致的格式开头（比如 
## [2026-04-02] ingest | 文章标题
），这样就可以用简单的 Unix 工具解析：
grep "^## \[" log.md | tail -5
 立刻看到最近 5 条记录。
这两个文件的设计哲学我很喜欢
——用最简单的工具解决问题
。不需要数据库，不需要搜索引擎，只需要 markdown 文件和 Unix 命令。
为什么这能 work？
Karpathy 给了一段我认为是整篇 Gist 里最精辟的话：
维护知识库最乏味的部分不是阅读或思考——而是记账。更新交叉引用、保持摘要最新、标注新数据何时与旧论断矛盾、维护几十个页面的一致性
。人类放弃 wiki 是因为维护负担的增长速度超过了价值增长速度。
LLM 不会无聊，不会忘记更新一个交叉引用，可以在一次操作中触碰 15 个文件
。 知识库保持维护状态，因为维护成本接近于零。
人的工作应该是策划资料源、引导分析方向、提出好问题、思考这一切意味着什么。LLM 的工作是其他所有事情。
这个分工模型让我想到一个类比：你是一个投资人，LLM 是你的分析师团队。你决定看什么赛道、关注哪些标的，分析师们负责读财报、建模型、做对比、更新数据库。区别是，这个分析师团队不知疲倦、不会离职、而且可以同时在 15 个文件上做更新。
和 Memex 的精神关联
Karpathy 在最后提到了 Vannevar Bush 1945 年提出的 Memex 概念——一个个人的、精心策划的知识存储系统，文档之间通过"联想路径"连接。Bush 的愿景更接近 llm-wiki，而不是今天的 Web：私有的、主动策划的，文档之间的连接和文档本身一样有价值。
Bush 没解决的问题是谁来做维护。LLM 解决了。
这让我想到一个有趣的视角：从 1945 年到 2026 年，人类花 80 年等到了一个能帮我们维护个人知识库的智能体。Bush 提出了问题，Karpathy 给出了 2026 年的答案。
我的看法
说实话，读完这个 Gist 我最大的感受是：
这个方案太"显然"了，但恰恰因为太显然，才没人想到
。
我们过去几年在 RAG 方向上投入了巨大精力——向量数据库、嵌入模型、检索策略、重排序算法——但所有这些工作都在解决"如何从原始文档中实时提取信息"的问题。Karpathy 的洞察是：
与其每次都从原始材料重新提取，不如编译一次，持续维护
。
这就像编程里的解释执行和预编译的区别。RAG 是解释执行——每次运行都从源码开始。llm-wiki 是预编译——源码编译一次，以后直接运行编译产物，只在源码更新时重新编译。
一旦你用这个视角看，很多之前纠结的问题就自然消解了：
•
知识库规模增长后质量下降
？ Lint 机制保证一致性。
•
交叉引用维护不过来
？ LLM 一次更新 15 个页面，成本接近于零。
•
不同文档之间的矛盾没法追踪
？ 摄取时就标注，不等查询时才发现。
•
查询结果没法复用
？ 好的答案直接存回 wiki。
当然，这个方案也有局限。它目前更适合中等规模的知识库（几十到几百个资料源），对于企业级的大规模应用，可能还是需要更复杂的搜索基础设施。Karpathy 自己也提到了这一点——当 wiki 增长到一定规模，index.md 可能不够用，需要引入像 qmd 这样的本地搜索引擎。
但作为一个
个人知识管理的范式
，我认为 llm-wiki 是目前我见过的最优雅的方案。它不依赖复杂的基础设施，不需要向量数据库，不需要 API——只需要一个 LLM Agent、一个文本编辑器、和一堆 markdown 文件。
工具链极其简单，但思路的杠杆率极高。
