# AI 总在返工？先看懂 Matt Pocock 的 grill-me 和 grill-with-docs

如果你最近已经开始用 Claude Code、Copilot、Cursor 这一类 agent 写代码，应该很容易碰到一种熟悉的挫败感：模型明明不弱，执行也很快，最后交出来的东西却总差一点意思。更准确地说，不是代码质量差，而是方向从一开始就歪了。

很多人会把这个问题归结成 prompt 不够长、上下文不够多、模型还不够强。但我最近越看越觉得，AI coding 里真正昂贵的错误，往往不是“不会写”，而是“没对齐就开工”。你以为自己已经讲清楚了，agent 也确实开足马力往前冲，半小时后你才发现，边界没说透，术语没统一，关键取舍也没谈明白。

Matt Pocock 这套 skill 最值得看的地方，就在这里。他没有先去追求更花哨的自动化，而是先把起手式反过来：**别急着让 AI 写，先让 AI 问。**

这篇文章也是我准备写的 AI 编程工作流系列的第一篇。先不急着谈 to-prd、to-issues、tdd 这些后续环节，我们先从 Matt 的这一组入口 skill 写起，看看他为什么会把 `grill-me` 和 `grill-with-docs` 放在整套工作流的最前面。

## 一、grill-me：它不是产出工具，而是“对齐工具”

如果只看 `grill-me` 的 prompt，你会发现它几乎极简到了有点离谱。核心意思其实就五条：

1. 把用户的方案一层层问透，不放过每个关键分支。
2. 顺着决策树往下走，先解决依赖，再谈后面的选择。
3. 每问一个问题，同时给一个推荐答案，逼着讨论进入具体取舍。
4. 一次只问一个问题，保证对话能推进，而不是甩出一屏问号。
5. 如果答案其实能从代码库里找出来，那就直接去查，不要浪费人类带宽。

这五条听起来不复杂，但它们解决的是一个很真实的问题：很多需求不是没有想，而是“以为自己想明白了”。一旦 agent 开始追问，你才会发现，原来你脑子里的“很清楚”，其实只是一个模糊的轮廓。

比如你说“做一个更灵活的评论系统”，`grill-me` 不会直接帮你写数据库表，而是继续追着问：灵活具体指什么？是权限更细，审核更强，还是支持嵌套回复？谁能删除评论？删除是软删还是硬删？匿名用户算不算参与者？

这类追问的价值，不在于“模型很会聊天”，而在于它帮你把模糊想法压成可执行决策。它本质上是一个对齐器，不是一个生成器。

所以 `grill-me` 很适合这些场景：

- 方案讨论还处在早期，问题没被说清楚。
- 你想压测一个设计，看有没有漏掉边界条件。
- 讨论对象不一定是代码，也可能是产品、流程、文章结构，甚至是一次分享提纲。

它有一个特别重要的特点：**没有副作用**。不写文档，不改代码，不创建任何工程资产。它交付的是“更清楚的共识”，而不是“更多的文件”。

## 二、为什么到了编码场景，光有 grill-me 还不够

问题在于，真实的软件项目和一次性的方案讨论不是一回事。

在编码场景里，最耗时的往往不是“想不出来”，而是“同样的概念每次都要重新解释一遍”。今天你说 `Order`，明天另一个 session 里 agent 又把它理解成 `Purchase`；你以为 `Customer` 和 `User` 是两个实体，模型却在实现时把它们揉成一个概念。结果就是：对话越来越长，术语越来越飘，返工越来越贵。

这也是 Matt 后来为什么明确说，自己已经不再把 `grill-me` 当作编码场景里的默认起手式。不是 `grill-me` 失效了，而是纯对话这件事，一旦进入长期维护的软件项目，就不够了。

因为软件工程不只需要“问透”，还需要“沉淀”。

你需要一种机制，把已经对齐过的语言固定下来，把关键但少数的决策记录下来，并且在后续 session 里不断复用，而不是每次从头讲一遍。于是，`grill-with-docs` 就出现了。

## 三、grill-with-docs：把“审问”升级成“审问 + 共享语言 + 决策沉淀”

如果说 `grill-me` 解决的是“你到底想要什么”，那么 `grill-with-docs` 解决的就是“这个项目以后都该怎么说、怎么记、怎么延续”。

它保留了 `grill-me` 最核心的交互方式：一次一个问题、逐层逼近共识、必要时自己去查代码。但它又额外引入了几件非常工程化的事情：

1. 如果你使用的术语和项目已有定义冲突，它会当场指出来。
2. 如果你的表述模糊，它会逼你把词收紧，而不是放任歧义继续扩散。
3. 它会用具体场景和边界 case 压测你的说法，不接受空泛正确。
4. 当你描述“系统现在就是这样工作的”时，它会去代码里交叉验证。
5. 一旦某个术语被谈清楚，它会马上更新 `CONTEXT.md`，而不是等会话结束后再整理。
6. 只有遇到真正高杠杆、难逆转、值得说明原因的决策时，它才建议写 ADR。

这里面我最认同的不是“文档变多了”，而是它对文档的克制。`grill-with-docs` 并不想把所有讨论都写成 spec，它想沉淀的只有两类高价值资产：

- `CONTEXT.md`：统一语言，减少每个新 session 的歧义税。
- `docs/adr/`：只记录少数关键架构决策，避免未来的人对着代码反复问“为什么要这么做”。

尤其是 `CONTEXT.md` 这件事，很多团队其实长期低估了它的价值。它不是需求文档，不是实现草稿，也不是项目百科。它更像是一个极度克制的术语表：这个项目里哪些词是正式词汇，哪些说法应该避免，哪些概念之间存在稳定关系。

对人类协作来说，这已经很重要；对 AI 协作来说，它更关键。因为 agent 最容易漂移的，恰恰不是语法，而是命名和语义。一旦共享语言不稳定，你每一次新对话都像在重新训练一个“懂一点项目黑话，但又没完全懂”的临时同事。

## 四、一个更成熟的点：ADR 不是越多越好

很多人第一次看到“文档化”这个方向，容易本能地走向另一个极端：那就多写点、多记点、多归档点。

这里也顺手解释一下 ADR 是什么。ADR 全称是 Architecture Decision Record，你可以把它理解成“架构决策记录”：不是写需求，也不是写设计细节，而是把那些重要、难逆转、以后别人看代码时会问“为什么这么做”的决定，顺手记一笔原因。

Matt 这一套成熟的地方在于，他对 ADR 的态度非常克制。不是有决定就写，也不是讨论完就建文件，而是至少同时满足三个条件，才值得记录：

1. 这个决定以后很难反悔，改动代价高。
2. 如果没有背景说明，后来看代码的人大概率会困惑。
3. 当时确实存在真实取舍，而不是顺手拍脑袋选了一个默认项。

这个门槛非常关键。因为工程文档真正的风险，从来不是“不够多”，而是“太多但没杠杆”。大家最怕的不是没有 ADR，而是目录里躺着三十篇没人再看的 ADR，真正重要的决定反而淹没在模板里。

`grill-with-docs` 的思路刚好反过来：只记录那些足以跨越时间、跨越 session、跨越人员交接的决定。换句话说，它要的是密度，不是数量。

## 五、grill-me 和 grill-with-docs，到底怎么选

| 维度 | grill-me | grill-with-docs |
| --- | --- | --- |
| 定位 | 通用型对齐工具 | 工程型对齐工具 |
| 适用场景 | 非代码方案、早期讨论、轻量评审 | 软件项目、多人协作、长期维护 |
| 核心机制 | 对话式审问 | 对话式审问 + 共享语言 + 文档沉淀 |
| 是否依赖项目上下文 | 基本不依赖 | 明显依赖代码库和领域语言 |
| 产出物 | 共识本身 | `CONTEXT.md` 和按需创建的 ADR |
| 上手成本 | 很低 | 略高，需要接受 DDD 式纪律 |

如果你只是想把一个想法问清楚，或者你聊的根本不是代码，`grill-me` 依然很好用。它没有过时，也没有“被淘汰”，只是它更适合通用的思考场景。

但如果你已经进入真实工程，特别是这些情况：

- 一个仓库会被多个 agent 或多个 session 反复接手。
- 项目里存在稳定但容易混淆的业务术语。
- 你希望后续的实现、交接、评审都建立在统一语言之上。

那 `grill-with-docs` 更像默认答案。

## 六、真正值得抄作业的，不是 prompt，而是 Matt 的工作流

很多人看到这两个 skill，第一反应会是：“哦，又是两个 prompt 技巧。”

我觉得这恰恰看小了。Matt 真正厉害的地方，不是写了两个 prompt，而是把 AI coding 的起手式、沉淀方式和执行链路串成了一条工作流。

在他的思路里，更完整的路径大概是这样：

```text
grill-with-docs -> to-prd -> to-issues -> tdd
```

这四步背后的意思非常清楚：

1. **grill-with-docs** 先把问题定义清楚，把术语和边界对齐。
2. **to-prd** 再把已经对齐好的共识收敛成正式需求，不让讨论结果继续漂移。
3. **to-issues** 把 PRD 拆成可以抓取、可以分发、可以验证的执行单元。
4. **tdd** 最后再进入实现阶段，用更强约束的方式把代码落地。

如果讨论的不是编码场景，这条链路的第一步当然也可以换成 `grill-me`。但无论你选哪一个入口，Matt 的核心思想都没变：**先把问题定义对，再让 agent 执行快。**

这其实也是我准备继续写 AI 编程工作流系列的原因。Matt 这套东西很适合当起点，因为它把一个常被忽略的问题讲得很清楚：**AI 编程最贵的不是写得慢，而是在错误方向上写得太快。**

后面我还会继续写更轻量的“先 PLAN 后执行”，或者像 superpowers 这样的不同流派。但不管工具怎么变，第一步大概率都绕不开同一件事：先把问题说清楚，再让 agent 开工。

如果你最近也总在返工，不妨先试一次最简单的改变：别急着让它写，先让它问。

如果你想亲手试一遍，安装 Matt 的 skills 只要一行命令：

```bash
npx skills@latest add mattpocock/skills
```

装完之后，别先急着跑那些最会“出代码”的 skill。拿一个真实需求，先过一轮 `grill-me` 或 `grill-with-docs`，你会很快感觉到差别：真正省下来的，不是几分钟 prompt 时间，而是后面整段返工时间。
