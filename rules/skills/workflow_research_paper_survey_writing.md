# 科研论文调研与写作工作流

## 元数据

- **类型**: Workflow
- **适用场景**: 针对科研论文（或技术 report）进行调研、生态位分析和面向读者的写作
- **创建日期**: 2026-03-25
- **来源**: 论文写作 session 的经验提炼

## 这是什么

一套从调研到成稿的完整流程，专门用于把一篇（或一组）科研论文转化为面向技术从业者的中文分析文章。

它和单纯的论文摘要有两个根本区别：第一，写作顺序按读者关心程度排列，而不是按论文章节顺序；第二，分析不止于论文本身的 claim，还要把论文放进产品生态和技术栈里定位。

## 什么时候用

- 读完一篇论文后需要写分析或分享
- 需要判断一篇论文对实际产品/工作流的影响
- 需要把论文内容传达给懂技术但没读原文的人

不适用的情况：纯学术综述（那种需要覆盖几十篇文献的 survey），或者只需要一句话总结的场景。

## 成功标准

一个合格的产出需要同时通过三个测试：

1. **五段测试**：一个了解一半背景的技术读者，读完前五段后能说出这篇论文改变了什么、为什么值得关注、还有什么没被验证。如果前五段还在讲背景或方法细节，说明排序有问题。

2. **三层可分辨测试**：随机抽一段话，读者能判断这是论文自己的 claim、外部验证/上下文信息、还是我们自己的判断。如果三层混在一起，说明标注不够。

3. **生态位测试**：读完后读者能回答：这篇论文解决的是哪个 bottleneck，在它之前人们怎么绕过这个问题，它在 stack 的哪一层。如果这些问题在文中找不到答案，说明生态位分析缺失。

## 核心写作排序：按重要性，不按论文顺序

这是这个 workflow 最重要的规则。论文作者的叙述顺序是为 reviewer 设计的（背景 → 方法 → 实验 → 结论）。我们的读者不是 reviewer，他们需要的顺序完全不同：

**第一层：发生了什么，为什么重要（前 3 段内必须交代完）**

用一两句话说清楚论文做了什么，然后立刻回答：这对谁有什么具体后果。后果要具体到可以想象的场景，比如"之前需要 8 张 A100 跑 3 天的任务，现在单卡 4 小时能完成"，而不是"大幅降低了计算成本"。

**第二层：它解决的是哪个痛点，之前怎么办的**

读者需要 anchor——在这篇论文出现之前，做同一件事的人用什么方案，那些方案的代价是什么。这一层建立的是参照系，让读者能判断新方案的改进幅度。

**第三层：它是怎么做到的（直觉版）**

先用类比或直觉解释核心机制，让读者建立心理模型。比如"它不是在 training 阶段压缩模型，而是在 inference 阶段动态跳过不需要的计算路径"。形式化的数学描述放在这之后，或者放进单独的技术细节小节。

**第四层：证据有多强，边界在哪里**

实验覆盖了哪些场景，没覆盖哪些。作者自己承认的局限是什么，社区的反应是什么。如果有第三方复现或质疑，放在这里。

**第五层：生态位分析**

这篇论文在更大的技术版图里占什么位置。详见下方的生态位分析框架。

## 调研流程

### 第 1 步：读论文，提取骨架

读原文（或 abstract + introduction + experiments + conclusion），提取四样东西：

- **核心 claim**：论文说自己做到了什么（用一句话）
- **方法直觉**：不看公式，它的核心 idea 能不能用一句类比说清
- **实验覆盖**：在什么数据集/任务/规模上测试了，基线是什么
- **作者自己承认的局限**：通常在 conclusion 或 limitations 小节

把这四样写进 scratchpad。

### 第 2 步：搜索外部反应

用 Tavily 搜索论文标题、作者名、关键方法名。关注三类信息：

- **社区讨论**（Twitter/X、Reddit、HN）：有没有人复现、质疑、或者指出未被注意的细节
- **同行评议**（OpenReview、NeurIPS/ICML reviews）：如果有公开 review，看 reviewer 的主要 concerns
- **后续工作**：有没有人在这篇论文基础上改进，或者把它集成进了产品

这一步可以派 sub-agent 并行搜索，但搜索维度要明确拆分。把关键发现和 URL 补进 scratchpad。

### 第 3 步：搜集生态位分析所需的上下文

这一步要回答的不是"论文说了什么"，而是"在这篇论文之前，这个领域的状态是什么"。具体搜索：

- 论文自己引用的 baseline 方法（它比较的那些对手）
- 做同一件事的商业产品或开源项目
- 相邻领域的替代路径（比如一篇关于模型压缩的论文，替代路径可能是更便宜的 API pricing）

### 第 4 步：形成判断，区分三层

在 scratchpad 里把所有信息按三层整理：

- **论文自己的 claim**：作者说了什么，实验支持到什么程度。这一层只陈述事实
- **外部验证与上下文**：社区反应、第三方复现、reviewer 意见、相关产品动态。这一层提供论文之外的参照
- **我们的判断**：基于前两层，我们认为这篇论文的实际影响有多大，置信度多高，哪些 claim 值得保留哪些需要打折

三层之间必须有明确的标记或段落分隔，不能混写。

## 生态位分析框架

这是区分论文总结和论文分析的关键。以下五个问题必须逐一回答：

**1. 它解决的是哪个 bottleneck？**

用具体的约束条件描述，不要用"性能不足"之类的泛称。好的回答像是"7B 参数以下的模型在 multi-step reasoning 任务上的准确率不到 40%，导致无法在端侧部署可用的 agent"。

**2. 在它之前有哪些替代路径？**

列出已有的解决方案（包括论文和产品），说明每条路径的代价。比如"方案 A 需要 8x 显存，方案 B 牺牲了 30% 准确率，方案 C 依赖特定硬件"。

**3. 它是在创造新能力，还是把已有能力的成本打下来？**

这个区分至关重要。创造新能力意味着之前做不到的事情现在能做了（0→1）。成本压缩意味着之前只有少数人能做的事情现在更多人能做了（专家→大众）。两者的战略含义完全不同：前者开辟新市场，后者重新分配已有市场。

**4. 它位于 stack 的哪一层？**

明确定位：model layer / runtime & inference / infrastructure / data pipeline / product UX / org workflow。一篇论文可能跨层，但通常有一个主要的作用层。定位在哪一层决定了它的影响传导路径——越底层的改进，影响面越广但传导越慢。

**5. 如果它成立，会改变哪些相邻系统、产品或工作流？**

这是最有实际价值的问题。比如一篇让小模型在 reasoning 上接近大模型的论文，如果成立，直接影响的是端侧 agent 产品、edge inference 框架、以及依赖大模型 API 的 SaaS 的定价策略。

## 成稿模板

以下是推荐的输出结构。具体的小节标题可以根据论文内容调整，但顺序不要变。

```markdown
# [论文简称]：[一句话说清楚它改变了什么]

## 核心发现

[2-3 段：它做了什么、具体后果是什么、对谁影响最大。
不要在这里解释方法。]

## 背景：这个问题之前怎么解决

[2-3 段：在这篇论文之前，做同一件事的人面对什么约束，
用什么替代方案，那些方案的代价是什么。]

## 核心方法（直觉版）

[先用类比或直觉说清楚核心 idea，
再用 1-2 段说形式化细节。
如果方法特别复杂，可以单开一个"技术细节"小节。]

## 证据与边界

[实验覆盖了什么、没覆盖什么。
社区反应。第三方验证情况。
明确标注：以下是论文 claim / 以下是外部验证 / 以下是我们的判断。]

## 生态位

[回答上面五个生态位问题。
这一节的价值是帮读者判断"我该投入多少注意力跟进这件事"。]

## 判断

[我们的整体评估。这篇论文值多少注意力，
置信度如何，哪些条件下结论会翻转。]
```

## Review Checklist

成稿后逐条检查：

**排序**
- [ ] 前三段是否回答了"发生了什么"和"为什么重要"
- [ ] 方法细节是否出现在背景和影响之后
- [ ] 是否存在读者需要先读完后面才能理解前面的段落

**认知负担**
- [ ] 每个关键概念第一次出现时是否有具体的例子或类比
- [ ] 是否有连续超过两段的纯抽象描述（没有具体例子穿插）
- [ ] 数字是否有参照系（"3倍"——相对于什么的3倍？）

**三层分离**
- [ ] 随机抽一段，能否判断它属于 paper claim / 外部验证 / 我们的判断
- [ ] 是否存在把论文 claim 直接当作已验证事实来陈述的段落

**生态位完整性**
- [ ] 是否回答了 bottleneck 是什么
- [ ] 是否列出了替代路径
- [ ] 是否判断了新能力还是成本压缩
- [ ] 是否定位了 stack 层级
- [ ] 是否分析了对相邻系统的影响

**风格（对照 COMMUNICATION.md）**
- [ ] 是否有"大幅提升""显著改善"之类没有参照系的形容
- [ ] 是否使用了论文腔（"本文提出""实验表明"作为句子开头）
- [ ] 是否违反了正向陈述原则（用否定句式代替直接说明）

## 常见失败模式

**1. 论文顺序陷阱**

按 introduction → method → experiments → conclusion 的顺序写。读者在第三段还不知道这篇论文为什么值得读。修复方法：写完初稿后检查前三段，如果还在讲背景或方法，把结论和影响提到最前面。

**2. 抽象堆叠**

连续多段都在说"提高了效率""降低了成本""增强了能力"，但没有一个具体的数字或场景。读者的大脑在第二段就开始滑过去了。修复方法：每个 claim 后面紧跟一个具体场景或数字。

**3. 论文 claim 与已验证事实混淆**

把论文在自己的实验设置下得到的结果，写成了普遍成立的结论。比如论文在 MMLU 上提升了 5%，但写成了"在推理能力上全面超越"。修复方法：每次引用论文数据时标明实验条件。

**4. 生态位分析缺失**

把论文讲清楚了，但没有回答"所以呢"。读者知道了它做了什么，但不知道它在更大版图里的位置。修复方法：强制回答五个生态位问题，即使某些问题的答案是"目前无法判断"。

**5. 官方叙事搬运**

直接用论文 abstract 的话术组织文章。论文的 abstract 是写给 reviewer 看的，强调 novelty 和 contribution，但读者需要的是 significance 和 context。修复方法：把论文 abstract 当作信息来源而不是叙事框架。

**6. 社区反应过度加权或过度忽略**

一种错误是把 Twitter 上的热议当作验证；另一种是完全忽略社区讨论，只看论文本身。修复方法：社区反应是信号不是证据，需要标注来源和置信度，但不能跳过。
